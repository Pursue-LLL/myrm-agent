# api/config/

## 架构概述

Omni-Config 读写与预检 HTTP 层。上级文档：[../_ARCH.md](../_ARCH.md)。

## 文件清单

| 文件 | 地位 | 职责 | I/O/P |
|------|------|------|-------|
| `__init__.py` | 入口 | 配置管理 API | ✅ |
| `artifact_mappings.py` | 模块 | 工件类型映射 API 端点 | ✅ |
| `router.py` | 路由 | 配置服务 API 路由层。处理 HTTP 请求，进行 Pre-flight Validation 强类型校验；`searchServices` 保存前执行 legacy role→priority 迁移并校验 manifest slug、enabled selectable、priority 唯一。浏览器 hot-reload 经 `get_configured_browser_pool()` 初始化 pool。Telegram onboarding 端点来自 `telegram_onboarding.py`，经 `router.include_router` 挂载；以 `Credentials` 结尾的配置保存后经 `services/channels/credential_reload.py` 的 `reload_channel_credentials` 热加载对应渠道。**Second Brain preset**：`GET/POST /onboarding/second-brain/{status,apply}` — 复用 `second_brain_assistant` 模板 + `read_it_later` + `wiki_morning_delta` blueprint + default vault seed；apply 成功 message 含 seed 文件计数；status 发现 preset agent 已删则清 config；apply 带 FileLock 409；持久化 `secondBrainPreset` checklist。**Vision health**：`POST /vision-health` — `extract_vision_fallback_model_config` 判定是否配置；`build_vision_fallback_engine_from_providers` 构建完整 failover 链并对 1×1 PNG 做 `describe_image_b64` 探活；失败字符串或异常时 `healthy=false`；成功时返回配置 primary `model` 与实际 `resolved_model`（failover 成功且与 primary 不同时）；Settings「Test vision chain」按钮消费。**Video health**：`POST /video-health` — `extract_video_fallback_model_config` + `build_video_fallback_probe_engine_from_providers` 对 video 链做 1×1 PNG 连通性探活；Settings「Test video chain」按钮消费。**Proxy health**：`POST /test-proxy` — `TestProxyRequest` 校验 `proxy_url` 格式、scheme 与 IMDS/link-local 黑名单；可选 `target_url`；经 harness `probe_proxy_health` 执行轻量连通性探活；脱敏凭据并返回 `healthy`、`latency_ms`、`error`；Settings 模型服务「Test Proxy」消费。**Local model test**：`POST /test-local-model` — 经 `create_litellm_model` 发送最小请求，`asyncio.wait_for` 硬截止（`_LOCAL_MODEL_TEST_TIMEOUT_S` = 12 s，低于 Settings UI 的 15 s 请求中止，保证失败以分类消息返回）；到期报告为「无响应，模型可能仍在加载或地址有误」，与提供方侧的连接超时区分；其他异常经 `_classify_local_model_error` 映射为面向用户的消息；隐私路由「本地模型」测试按钮消费。 | ✅ |
| `telegram_onboarding.py` | 路由 | `POST /onboarding/telegram-assistant/apply`：Telegram onboarding 原子编排端点（令牌校验 + 凭据落盘 + DM 策略 + 默认 Agent 绑定 + 失败回滚）；助手解析交给 `telegram_onboarding_agent.py`，发生在任何配置写入之前，其 `409 + TELEGRAM_ONBOARDING_IN_PROGRESS`（供前端无感重试）与 `422` 原样透传且不触发回滚（回滚会用本请求的旧快照覆盖并发引导刚保存的配置）；令牌校验失败返回 `400`，分类取自 `channels/providers/telegram/api_core.py` 的 `getme_failure_reason`：Bot API 拒绝令牌为 `TELEGRAM_TOKEN_REJECTED`，其余（连接、超时、代理、限流）为 `TELEGRAM_UNREACHABLE`，原因脱敏后写 WARNING 日志，供前端区分提示；请求可带 `proxy`：非空值经 harness 的 `normalize_proxy_url` 归一、`validate_proxy_url` 校验（不可用返回 `422 + TELEGRAM_PROXY_REJECTED`），令牌校验经它发出，通过后才随凭据落盘，留空沿用已保存的代理）。失败回滚会恢复凭据、渠道配置、话题绑定并清理本次新建的 Agent；凭据保存后经 `reload_channel_credentials` 热加载渠道。`TELEGRAM_UNREACHABLE` 的详情另带 `viaProxy`（本次校验是否经由代理，含已保存的代理），前端据此区分提示。 | ✅ |
| `telegram_onboarding_agent.py` | 模块 | Telegram onboarding 的助手解析步骤 `resolve_or_create_telegram_agent`：同名且可绑定渠道的 Agent 确定性复用（search 模式的不可绑定，同名时回退到「名称 (General)」），否则创建；进程内锁加基于 `state_dir` 的按名称跨进程 FileLock 防重，避免并发重复创建；锁被占用抛 `409 + TELEGRAM_ONBOARDING_IN_PROGRESS`，空白名称抛 `422` | ✅ |
| `pricing.py` | 路由 | 模型四维单价矩阵与 Prompt Cache 经济学数据只读查询 API。提供 `GET /model-pricing`，从 LiteLLM 权威数据提取以 $/1M tokens 计价的输入、输出、Cache 读写单价及节省率。 | ✅ |
| `privacy_preview.py` | 路由 | 隐私保护「试一试」：`POST /privacy-preview` 接收一句话与表单里的处理方式、自定义规则（字段与对话请求同名），经 harness `preview_privacy_policy` 返回识别级别、处理方式、模型实际会收到的文本（被拦截时为 null）与无法生效的自定义模式 `ineffective_patterns`（句子可为空：有规则时无需等用户输入句子即可查询）。规则随请求而来、不读不写已保存设置、不落日志；仅正则层，不含深度扫描；同步路由，伪匿名化时用一次性临时存储，不触碰真实假名映射。 | ✅ |
