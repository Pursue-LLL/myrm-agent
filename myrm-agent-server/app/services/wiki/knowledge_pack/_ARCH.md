# Knowledge Pack 模块架构说明（L3 · _ARCH.md）

## 1. 模块定位与职责（POS）
`app/services/wiki/knowledge_pack/` 是智能体每轮知识包前置主动注入（`KnowledgePackProactiveInjectionPerAgentTurn`）的核心领域模块。
负责在每轮 Agent 交互前，按会话或 Agent 绑定的外挂知识库提取与问题相关的段落（相关度门槛）、做 Jaccard 跨库语义去重与严格 Token/字符预算硬截断，检索超过 150ms 就放弃本轮注入。

## 2. 架构设计原则与约束
1. **0 冗余数据库实体**：复用既有的 `shared_contexts` 表与 `Agent.memory_policy` 配置字段，不增加无用表。
2. **Prompt Cache 布局隔离**：动态检索结果仅注入 HumanMessage 前置信封，System Prompt 保持静态不变。
3. **预算截断与硬限制**：最多 3 个关键段落，单段 ≤ 200 字符，总字符 ≤ 600 字符。
4. **150ms 超时降级**：超过 150ms 的检索返回空结果、不注入，对话照常进行。每轮把所有共享库交给专用扫描线程池（`_SCAN_EXECUTOR`，至多 4 个线程，与默认线程池隔离）里的一个线程按序扫描，`asyncio.wait_for` 到点就放弃等待：慢文件系统或慢挂载既不会拖住这一轮，也不会卡住事件循环；超时的扫描在线程里自行结束，结果丢弃（不写业务数据；目录可写时，只读打开 WAL 索引会留下 `-shm` / `-wal` 附属文件）。永不返回的挂载每轮钉住一个扫描线程，最多钉满专用池的 4 个，之后各轮在到点时降级为空，还没开始的排队扫描随超时取消；进程里其他 `asyncio.to_thread` 的调用方不受影响。扫描耗时由问题长度与查询词数上限（原则 7）、索引规模和只在没有索引页面的库上运行的第 2 层（原则 9）约束。
5. **Jaccard 相似度去重**：相似度 ≥ 0.70 的重复段落直接剔除，确保信息高增益。
6. **发布门禁（两道）**：第一道经 harness 的 `search_published_index` 只读打开 vault 的 FTS 索引，draft、blocked 与 sidecar 行在匹配查询内就被排除，排名与 `LIMIT` 只数已发布页面，草稿再多也挤不掉已发布页面；没有发布元数据表的旧索引整体按已发布读取。第二道在读页面文件时：读到的每份页面文本再过 harness 的 `resolve_publish_status`（索引可能落后于文件），draft 与 blocked 页整页跳过（索引命中的页面也一样，页面文件才是发布状态的依据），读不出的页面、页面文件落在库外的页面（原则 10）同样整页跳过；只有完全没有页面文件的索引行（如 raw 来源）才用索引里存的文本。缺失或未知的状态按已发布处理，与 wiki 全局约定一致。片段取自去掉 frontmatter 的正文。
7. **查询词确定性**：问题只读前 1000 个字符。去掉 harness 的停用词（`STOP_WORDS`）后取最靠前的 16 个词：字母数字词与相邻汉字二元组，按出现位置排列、各取一次；不足 2 个字符的词只在没有更长的词时才用。停用词在取上限之前就去掉，客套话（「请问能不能帮我……」）不会挤掉主题词。同一个问题在任何进程里都得到同一条 `OR` 查询，词的取舍不依赖集合的迭代顺序；两层读同一份词表。
8. **相关度门槛与置信度**：索引对任何问题都返回排名最高的页面，不管问题有没有答案。两层都给每个页面挑出「标题加段落」得分最高的一段（同分取靠前的一段），只在它命中至少 2 个不同的查询词（问题只有 1 个词时要 1 个），且有 3 个词、或有 1 个词在标题里时，才留下，不达标的页面不注入，所以库里没有答案的问题大多不注入片段。置信度就是命中词数占查询词数的比例，两层同一个定义，跨库排序不取决于库的绑定顺序；一个页面最多占一个片段名额，一篇长文挤不掉别的页面。字母数字词按整词计（`me` 不在 `memory` 里），4 个字符以上的词可以是更长词的开头（`agent` 在 `agents` 里）；汉字词按子串计。这是词面规则，不是语义判断：问题与页面碰巧共享 2–3 个常见词时仍会放行，去停用词只覆盖中英文。
9. **第 2 层只服务没有索引页面的库**：索引里有页面的库由索引作答，空答案也算——为读 15 个页面而列出上万个文件，代价高于它能找到的。索引文件缺失、读不出来、解析到库外（原则 10）、或里面没有任何页面行（`raw:` 待编译原文行与 sidecar 行不算页面行）时，第 2 层按文件名取前 15 个 markdown 文件（`heapq.nsmallest`，不排序整个目录列表），读哪些页面不取决于文件系统的列举顺序，每个页面返回得分最高的一段，跨页面的排序与预算交给选择器。不能只看索引文件在不在：任何 `WikiIndexer` 构造时都会创建索引文件，不管有没有填过；所以第 1 层返回空时，再由 harness 的 `index_has_pages` 判断索引里有没有页面行（多开一次只读连接，页面行的定义与图查询共用 `concept_rows_filter`）。索引里有页面、但有些页面只在磁盘上的库，这一层不会扫到那些页面：共享库由提供方维护，要提供方重建索引之后那些页面才可被检索（`POST /wiki/reindex-vectors` 只重建当前智能体自己的库）。
10. **共享库由外部写入，本服务只读**：共享库（`wiki_root()/shared/<id>`）是只读库，由部署方挂载提供，本服务不写它，也不信任里面的路径：索引文件和页面文件都必须解析到库内（harness 的 `is_within_boundary`，解析符号链接后比较），否则不读。索引文件是指向库外的符号链接时，整库按没有索引走第 2 层；索引给出的页面名带 `..`、或页面文件是指向库外的符号链接时，该页整页不注入，不退回用索引里存的文本（页面文件才是发布状态的依据，读不到就无法验证）。两层都把被拒的路径连同库路径记为 WARNING（路径以 `%r` 转义，文件名里的换行写不进日志）。完全没有页面文件的索引行（如 raw 来源）不在此列，用索引里存的文本。库所在目录不可写（只读挂载）时，FTS 索引以 `mode=ro&immutable=1` 打开，WAL 模式的索引在只读卷上也读得了；代价是 WAL 附属文件里尚未检查点的行读不到，提供方发布前应先做检查点；SQLite 此时认定文件不会变，提供方在挂载期间也不能再写这个索引，否则读取会报错或返回不一致的行。目录可写时不加 `immutable`，这些行照常可见。

## 3. 模块内部文件清单与接口职责

| 文件名 | 地位 | 核心职责 | 输入 (INPUT) | 输出 (OUTPUT) |
| :--- | :--- | :--- | :--- | :--- |
| `__init__.py` | Facade 门面 | 聚合导出模块内所有核心契约与算法 | 内部各子模块 | 统一向外暴露稳定 API |
| `schemas.py` | Core 实体 | 定义 KnowledgePackConfig, RelevantSnippet, ProactiveKnowledgeResult | 无 | 强类型数据传输对象 (DTO) |
| `query_terms.py` | 辅助 | 问题的查询词与相关度：`search_terms` 去停用词后按出现顺序取前 16 个词，`carried_terms` 数一段文本带有几个词，`paragraph_relevance` 给「标题加段落」打相关度并设门槛，`tokenize_text` 供去重 | harness 的 `STOP_WORDS` | `MAX_QUERY_CHARS`、`ordered_terms`、`tokenize_text`、`search_terms`、`carried_terms`、`paragraph_relevance` |
| `selector.py` | Pipeline 引擎 | 层 1 用查询词建 OR 查询、只读 FTS 索引取已发布页面，层 2 只扫没有索引页面的库的 markdown；两层每个页面取 `paragraph_relevance` 得分最高的一段、达门槛才留并把得分作置信度；索引文件与页面文件都限在 vault 内（库外的页面整页不注入并记 WARNING），页面再过发布门禁并剥离 frontmatter；Jaccard 语义去重、硬预算截断；所有库每轮在专用扫描线程池的一个线程里按序扫描并受超时约束 | schemas, query_terms, harness 的 `search_published_index`、`index_has_pages`、`is_within_boundary`、`resolve_publish_status` 与 `parse_frontmatter` | ProactiveKnowledgeResult |
