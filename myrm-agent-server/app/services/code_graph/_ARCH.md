# code_graph 模块架构

## 职责定位
本地、零外部服务依赖的代码结构索引：把工作区内的 Python 与 TypeScript/JavaScript 源文件解析为符号、调用点、继承和导入关系，存入 SQLite，供 Agent 工具 `code_graph_tool` 按结构提问（符号定义、调用方、被调用、子类、导入方、直接调用它的测试）。

三条贯穿全模块的事实：

- 调用点的被调用者只记录调用处的原文（`Name` 或点分属性链），不解析到具体定义。因此 `callers` 按「整串相等」或「最后一段同名」匹配，每行用 `match`（`exact` / `name`）标明，并由 `count_definitions` 给出同名定义数；同名定义数大于 1 时，`match=name` 的行只是候选。
- 索引按文件指纹增量同步：`index_directory` 可以反复运行，目录没变时只有一次文件列举和每个文件一次 `stat`；每解析 `INDEX_BATCH_FILES` 个文件或累计 `INDEX_BATCH_BYTES` 字节源码就落库一次（首次索引与大批改动一样；解析结果的大小随源码体积增长，所以不只按个数切），内存里只留一批解析结果，同一索引库的同步在进程内串行。
- 抽取结果就是索引内容：文件指纹没变就不会重新解析，所以任何改变表结构或抽取结果的修改都必须递增 `models.INDEX_FORMAT_VERSION`。索引库文件名带这个版本（`<工作区路径哈希>.v<版本>.db`），换版本就是换一个新库从头索引，`agent_tool.py` 在打开库之前删除同一工作区其他版本的库文件（含 WAL 文件）。`tests/services/code_graph/test_code_graph_extraction_golden.py` 把一组样本的抽取结果指纹与版本号绑在一起：抽取结果变了而版本没递增，测试失败。

## 核心文件清单
- `models.py`: 数据模型（`SymbolNode`、`CallEdge`、`InheritanceEdge`、`ImportEdge`、一个文件的解析结果 `ParsedFile`、同步统计 `IndexStats`、调用点可以指名的符号种类 `DEFINITION_KINDS`），以及 Python 与 JS/TS 两个抽取器共用的模块名规则 `module_name_for`（由相对索引根的路径得到点分名，同名文件位于不同目录时限定名不会冲突）。
- `ast_extractor.py`: Python 符号与调用抽取器，用原生 `ast`，一次迭代遍历：`if`、`try`、`with` 内的定义与导入同样被找到；每个调用只记给最内层的函数，模块层与类体里的调用记给模块名，装饰器、默认值、基类表达式在定义时执行，所以记给外层；只有直接位于类体内的函数是 `method`，嵌套函数是 `function`；不是合法 Python 的源码让 `extract()` 返回 `False`。导入记录的是导入语句读到的名字，写法与索引里的模块名相同：绝对导入照原文，相对导入按本文件所在目录还原（`src/pkg/mod.py` 里的 `from . import util` 记为 `src.pkg.util`，`pkg/__init__.py` 里的 `from .core import run` 记为 `pkg.core.run`），点数越过索引根的相对导入不指向索引里的任何模块，不记录。
- `js_ts_extractor.py`: TypeScript/JavaScript 抽取器，用 tree-sitter 语法树（`.ts` 用 typescript 语法，`.tsx`、`.jsx`、`.js` 用 tsx 语法），接口与 Python 抽取器一致。符号：函数声明（含生成器、`export default function Name`）、绑定到 `const` / `let` / `var` 的箭头函数与函数表达式、类（声明、抽象类、绑定到变量的类表达式）、类的方法、构造函数、访问器与值为箭头函数的类属性（均为 `method`）、嵌套的具名函数；对象字面量的成员与匿名函数不是符号；`line_end` 是声明节点的结束行。调用：标识符或成员链形式的 `call_expression` 与 `new_expression`，被调用者文本沿用 Python 的点分链规则，调用位置记在被调用的名字上；调用归属最内层的非类作用域，类体、装饰器与参数默认值里的调用记给外层，模块层记给模块名；`extends` 记基类原文（`React.Component`），`implements` 不记。用游标迭代遍历语法树一次，每个节点的开销与嵌套深度无关；不用 QueryCursor，因为它每个节点的开销随树深增长（15 万层括号要 35 s，且全程持有 GIL），同时打开超过 32,767 个匹配时会静默丢匹配（4 万个链式调用只留下 32,767 个）；语法有错的文件按能解析出的部分抽取，`extract()` 总是返回 `True`。不抽取导入，`importers` 只覆盖 Python。
- `graph_store.py`: SQLite（WAL）存储。`files` 表保存每个文件的指纹，符号、调用、继承、导入四张表按文件归属；`apply_changes` 在一个事务内先删除已消失与已改动文件的全部行，再写入新的解析结果（符号只存位置与文档注释，不保存源码文本；`reset` 在写事务内判断，只在尚无任何文件记录时清空整库以接管没有来源记录的旧库，已有文件记录时不清，所以一次运行不会清掉别的运行已落库的批次）；新库切换到 WAL 时遇到并发会重试（`_enable_wal`），多个 Agent 同时打开同一工作区不会失败；所有 `LIKE` 查询都转义 `_` 与 `%`，名字按字面匹配；`resolve` 的 `路径:行号` 目标返回包含该行的符号，范围小的在前，范围相同时模块排在最后。`get_importers` 收一组前缀，每个前缀是一次相等加 `imported_symbol` 索引上的一段范围（`前缀.` 到 `前缀/`，`/` 是 `.` 的下一个字符），只命中前缀本身与它之内的名字，大小写敏感；前缀不超过 15 个时走这个索引（实测约 0.3 ms），16 个起 SQLite 改为扫描整张导入表（6.5 万至 6.8 万行，实测 65 至 197 ms），所以候选模块多的名字比普通查询慢两个数量级以上；`count_definitions` 按符号种类计数，默认函数、方法和类；`get_python_module_names` 返回全部 Python 模块名，供 `import_alignment.py` 使用。`get_tests_calling` 只返回按路径约定（位于 `tests/`、`test/`、`__tests__/` 目录，或文件名为 `test_*.py`、`*_test.py`、`*.test.ts`、`*.spec.ts` 等）判定为测试文件内的直接调用点。
- `import_alignment.py`: `importers` 的查询词与索引里导入文本的对齐，纯函数 `importer_scope`。索引里的模块名由文件路径得到（`src/pkg/util.py` 是 `src.pkg.util`，`pkg/__init__.py` 是 `pkg.__init__`），源码里的导入文本以导入根为起点（`pkg.util`）。查询词最长的、是某个模块名的开头部分（等于它，或在点边界上是它的后缀，包不带 `.__init__`）就是被问的模块，其余部分是模块内的名字（`pkg.util.helper`）；查询词里整段的 `__init__` 不参与匹配（`resolve` 把 `pkg/__init__.py` 里定义的 `Thing` 叫 `pkg.__init__.Thing`，源码里写的是 `pkg.Thing`）；查询词本身始终在范围内，所以按源码里的写法提问在任何布局下都能命中。模块还按它在 `src` 目录之下的写法搜（`src.pkg.util` 同时按 `pkg.util` 搜）：`src` 是单凭路径就能判定的导入根，换成别的目录会把同名第三方包的导入也算进来（本地的 `app/redis.py` 不该拿走所有 `import redis`）；这个短写法要求没有别的模块也叫这个名字，且第一段不是标准库模块名。名字对应多个模块（`models`）时，全部候选都搜（最多 `MAX_SCOPE_MODULES`，即 50 个），并在 `ImportScope.modules` 里如实返回，不合并也不猜。
- `service.py`: `CodeGraphService` 门面。`index_directory` 的文件清单来自 harness 的 `WorkspacePathIndexer`（git 仓库走受限 `git ls-files`，只列工作区子树；否则遍历目录；遵循忽略规则），只收 `SOURCE_SUFFIXES`，排除 `EXCLUDE_DIRS`、符号链接与特殊文件、超过 `MAX_SOURCE_BYTES` 的文件；`.py` 交给 Python 抽取器，其余后缀交给 JS/TS 抽取器；用 `(mtime_ns, size)` 判定新增、改动与删除，无法读取、或不是合法 Python 的文件计入 `skipped_files`，且不记指纹，每次运行都会重试；文件清单触及枚举上限时 `IndexStats.truncated` 为真（超出的文件不被索引）；读取时去掉 UTF-8 BOM；解析结果每累积 `INDEX_BATCH_FILES`（500）个文件或 `INDEX_BATCH_BYTES`（8,000,000）字节源码调用一次 `apply_changes`，只有第一批清掉没有来源记录的旧条目，已删除的文件最后统一处理，中途失败后已落库的文件带着指纹，下一次运行只解析其余文件；同一索引库（按库路径）的 `index_directory` 在进程内持锁串行，被取消的工具调用留下的线程还在运行时，下一次调用等它结束并复用已落库的文件。随后提供 `resolve`、`definition`、`callers`、`callees`、`implementors`、`importers`、`tests_calling` 七种查询，以及 `definition_count`（可按符号种类计数）与 `importer_scope`（查询词在索引里指哪些 Python 模块、哪些导入文本属于它；`importers` 用它的前缀查询）。
- `agent_tool.py`: Agent 工具 `code_graph_tool`，参数是动作 `action` 与查询词 `query`。动作与 `service.py` 的七种查询一一对应；每次调用先同步索引再查询，结果最多 50 行，附 `total`（匹配总数，不是显示的行数）、`definitions` 与 `notes`（文件清单被截断、超出上限、同名定义、`importers` 的名字对应多个模块、未索引文件、无结果时的建议；`importers` 的每个回答都说明只索引了 Python 的导入，所以 TypeScript/JavaScript 的导入方要用 grep，它返回空也不代表没人导入）；清单被截断时 `notes` 明说部分文件未索引、查不到不代表没有，改用 grep。超过 50 行时再附 `by_file`（匹配最多的前 `MAX_DISTRIBUTION_FILES`，即 10 个文件各有多少个匹配，数的是全部匹配而不是显示的行）与 `more_files`（还有多少个文件没列出），让调用方看出被截掉的行落在哪些文件；`callers` 与 `tests_calling`（`_Action.call_sites`）经 `_order_call_sites` 先列能到达定义的行：一般是 `match=exact` 的行（调用文本与查询词完全相同），`match=name` 的行排在后面；不带点的名字在索引里只有方法定义时反过来，先列 `match=name` 的行（带接收者的调用），因为裸调用到不了方法；各组内部按文件路径与行号；`importers` 的名字对应多个模块时，`notes` 列出前 5 个候选。索引库位于持久卷的 `code_graph/` 下，文件名是工作区路径哈希加 `INDEX_FORMAT_VERSION`，不写入工作区。`append_code_graph_tool` 仅在用户启用了预置技能 `repo-call-graph` 且 Agent 有工作区时挂载；工具描述与参数 schema 是常量，不含工作区路径或统计，不影响提示词缓存。

## 已知限制
- JS/TS 只记录标识符与成员链形式的调用：括号、下标形式的被调用者、`super()`、`import()` 与标签模板不记录；只有签名没有函数体的声明（`.d.ts`、函数重载签名）不产出符号；`.mjs`、`.cjs` 不在 `SOURCE_SUFFIXES` 内。
- tree-sitter-typescript 有解析不了的写法：类型参数里的 `typeof import('x')`（vitest 的 `importOriginal<typeof import('x')>()` 与 `vi.importActual<typeof import('x')>()`）、类型参数里带对象类型的调用（`apiRequest<{ a: string; b?: string }>(url)`）。遇到时只丢这一处的调用（夹着这种调用的 `vi.mock` 回调还会多算一个参数），文件其余部分照常抽取。`scripts/dev/check_code_graph_js_ts_accuracy.py` 把抽取结果与 TypeScript 编译器逐文件比对；取本仓库前端 `src` 的工作目录（目录在持续改动，数字会漂移；最近一次 4,821 个文件）：符号 10,219 个，召回与精确率均 100.00%；调用点 238,596 个，召回 99.92%（漏 186 个：`importOriginal` 146、`vi.importActual` 25、参数个数记错的 `vi.mock` 12、其余 3）、精确率 99.99%（多记 13 个：12 个是上述 `vi.mock`、1 个在语法错误的文件里）；类继承 40 个全部一致；135 个文件含 tree-sitter 语法错误，漏记的 163 个在其中。命中要求行号、被调用者文本、归属函数与参数个数全部相等；符号的取法与调用的归属是我们定的规则，比对只说明解析没有走样，不说明规则最优。
- 具名定义最多嵌套 `MAX_SCOPE_DEPTH`（32）层，更深的定义不是符号，其中的调用记给最深的一个：限定名重复每一层外层的名字，1 MB 文件嵌套 7.6 万层曾占用 5 至 6.5 GB 内存。
- JS/TS 解析没有超时：`MAX_SOURCE_BYTES` 限定单文件 1 MB。20 种 1 MB 以内的对抗性形状（深层括号、数组、泛型、三元、JSX、未闭合括号、链式调用、参数里的调用、嵌套定义等）实测每个文件 0.02 至 6.6 s（机器负载约 50；有一次读数 10.9 s，重测为 2.2 s）。最慢的是未闭合泛型 `f<a<a<…`，耗时在 tree-sitter 解析本身而不在遍历。解析持有 GIL：1 MB 的 `f<a<a<…` 解析 2.4 s，期间同进程的其他线程整体停顿 2.3 s（机器负载约 33）；这样的输入只能人为构造，前端 `src` 与浏览器扩展的 4,839 个真实源文件解析最慢 71 ms。不设超时：py-tree-sitter 0.25 的 `Parser.timeout_micros` 已弃用，`progress_callback` 返回 `False` 时会让进程崩溃；超时的文件不记指纹，每次同步都要再等满一次超时，而不设超时时，病态文件只在指纹变化时付一次代价。
- `tree-sitter` 固定在 `>=0.25.2,<0.26`：0.26.0 读取 `Point.row` / `.column` 时少一次引用计数（py-tree-sitter#472、#500 的分析），遍历语法树读取 `Point.row` 时约三分之一的运行段错误（#505 的复现）；上游称 master 已修复，尚无包含修复的发布版；放开版本前必须确认已发布的版本包含修复。
- 大小与修改时间都没变的改写不会被发现。
- 同一目录下同名的 `.ts` 与 `.js`（例如提交了编译产物）限定名相同，后写入的覆盖先写入的符号。
- 索引库约为源码体积的 4 倍（harness 仓库 45.1 MB 源码对应 185.7 MB），按工作区路径存放，不随工作区删除而清理。
- 不是合法 Python 的文件（例如 Python 2）得不到任何符号。
- 文件清单受 `WorkspacePathIndexer` 的文件数上限约束，超出部分不被索引；触及上限时工具结果的 `notes` 会提示，此时「没有调用方」只是未确认。
- 每次调用都先同步一次：未变化的前端 `src`（4,824 个文件，macOS）再次同步实测中位约 0.5 s（交替运行 6 次，范围 0.35–0.76 s；机器负载偏高，数字会漂移）。
- 首次索引大型仓库需要数秒到数十秒，之后只处理变化的文件；首次调用受 Agent 工具默认 60 s 超时与最多 2 次尝试约束，超时后索引线程在后台继续，下一次尝试等它结束并复用成果；两次都超时则本次调用报错，之后每次调用（各有 2 次尝试）最多再等约 121 s，索引在后台跑完后即可直接使用。
- 串行只在进程内；两个进程同时首次索引同一个库时各自解析一遍，最终结果一致，只是重复耗时。
- 超过一批（500 个文件或 8 MB 源码）的同步不是单个原子事务：同步进行中，不持有同步锁的读者可能看到新旧混合的图；`code_graph_tool` 在查询前先等待同步完成，不受影响。
- 结果最多 50 行：`callers`、`tests_calling` 先列 `match=exact` 的行（不带点的名字只有方法定义时先列 `match=name` 的行）、再按文件路径与行号取前 50 行，`implementors` 按类名取前 50 行，被截掉的行不可见，只能从 `by_file` 看出它们在哪些文件；这三个动作按最后一段名字匹配，限定名返回同样的行，只能在关心的目录里用 grep 缩小；`resolve` 与 `importers` 用限定名可以缩小，`callees` 按行号取前 50 行。每个动作超过上限时给出的建议由 `agent_tool.py` 的 `_Action.cut_hint` 自述，新增动作必须填写；动作看不到、索引里却有的那部分由 `_Action.gap` 在每个回答里说明（目前只有 `importers`：看不到 JS/TS 的导入）；预置技能 `assets/prebuilt_skills/repo-call-graph/SKILL.md` 只指向 `notes`，不复制各动作的建议。排序是启发式：不带点的名字，裸调用（`match=exact`）只可能到达函数或类，带接收者的调用（`match=name`）才可能到达方法，所以只有方法定义的名字先列 `match=name` 的行；带点的查询（如 `Foo.build`）的 `exact` 行是 `Foo.build(...)` 形式的调用，能到达类方法与静态方法，一律 `exact` 优先。实测（目录在持续改动，数字会漂移）：server 工作区超过 50 行的 `callers` 查询名有 459 个，其中只有方法定义又有裸调用的 37 个，这 37 个名字前 50 行里带接收者的行数合计：`exact` 优先 941，路径顺序 1,447，`match=name` 优先 1,669（上限 1,668；`select` 多出 1 行，是 SQLite 的 `LIKE` 不区分大小写，把 `discord.ui.Select` 也匹配进来）；harness 的 582 个里有 59 个：1,810、2,367、2,722。`match=name` 优先比 `exact` 优先多出的 728 行里，`time`、`set`、`scalars`、`json`、`is_file`、`get`、`exists`、`append` 这 8 个与库方法同名的名字各占满 50 行，所以这个顺序只保证可能的调用方排在前面，不保证真正的调用方在其中。带点的类限定查询中超过 50 行且只有方法定义的，server 36 个、harness 39 个，前 50 行里的 `exact` 行合计 520 与 231，与全部 `exact` 行的上限一致；路径顺序下是 344 与 153。对有函数或类定义的名字、以及索引里没有定义的内置与三方名字，`exact` 优先是否比路径顺序更有用，没有实测依据。`by_file` 与 `more_files` 使一个被截断的 `callers` 答案增加 121 至 149 个 token（原本约 2,060 至 2,330 个，tiktoken `cl100k_base`）。
- `importers` 只覆盖 Python 的直接导入语句。`from pkg import Thing` 记在 `pkg.Thing` 名下，所以经包的 `__init__.py` 转出的名字算在这个包下，不算在 `Thing` 定义所在的模块下（找 `Thing` 的使用处用 `callers`）；`importlib.import_module("x")`、`__import__` 等动态导入看不到。能由路径判定的导入根只有 `src`：脚本目录里的 `import mail_client`（文件在 `scripts/mail_client.py`）只能按这个写法提问才命中，用路径名 `scripts.mail_client` 提问找不到它。名字对应多个模块时（server 工作区的 `models` 有 26 个）所有候选的导入方混在一个答案里，`notes` 说明候选数与前 5 个，用更长的名字缩小；超过 `MAX_SCOPE_MODULES` 个时只搜前 50 个，`notes` 另行说明。与独立的 AST 解析逐对比对（server 工作区 5,844 个、harness 6,148 个 Python 文件；固定种子随机抽样：各 150 个模块的路径名，harness 另有 67 个模块去掉 `src.` 的写法，各 100 个包的 `pkg.__init__` 写法，以及 `resolve` 以限定名给出的、定义在 `__init__.py` 里的 50 个与 88 个函数和类）：命中的导入语句与真值逐条相同，召回与精确率均为 100.00%（server 17,899 对，harness 53,452 对）。真值与实现共用别名模型（只认路径名与 `src` 目录之下的名字），所以比对说明对齐、相对导入还原与 SQL 范围查询没有走样，不说明规则最优。被导入的 430 个包与 29 个定义在 `__init__.py` 里的符号（harness 为 507 个与 36 个）按 `resolve` 给出的名字都能查到。名字解析读取全部 Python 模块名，server 的 5,844 个约 10 ms，harness 的 6,148 个约 15 ms；一般查询 13 至 16 ms；候选模块多的名字更慢，因为前缀到 16 个起 SQLite 扫描整张导入表：server 的 `models`（26 个候选）约 117 ms，`types`（18 个）约 130 ms，harness 的 `types`（156 个候选，只搜 50 个）约 177 ms。

## 架构边界
属于 Server 业务层提供的预置代码智能能力，不侵入 Harness 核心执行框架；对 Harness 只使用公开的 `WorkspacePathIndexer` 与持久卷根路径；JS/TS 解析依赖第三方原生扩展 `tree-sitter` 与 `tree-sitter-typescript`。Agent 侧的挂载点在 `app/ai_agents/general_agent/factory.py`（导入或构建失败只记 WARNING，Agent 少这一个工具，创建不受影响），工具层级登记在 `tools/_tool_layer_bootstrap.py`（EXTERNAL）。

权限：工具按读取工作区文件归类。`tools/_tool_layer_bootstrap.py` 经 harness 的 `declare_external_tool` 把 `code_graph_tool` 声明为 `file_read`（只读、可并发、幂等；调用在工具自己的锁上排队，索引是工作区之外的缓存），所以默认与只读配置下调用不需要审批，只读回合的工具收窄也不会剔除它。查询词的参数名叫 `query`，不与权限引擎按文件路径检查的参数名（`FILE_ARG_KEYS`，含 `target`、`path`）重名：以 `.db`、`.env`、`.key`、`.pem`、`.sqlite` 结尾的限定名（`app.core.db`、`Settings.key`）与以 `..` 开头的相对路径形状的查询词不会被当成文件路径而要求审批；`tests/services/code_graph/test_code_graph_governance.py` 钉住这一点。预置技能 `repo-call-graph` 在 frontmatter 声明 `required_permissions: [file_read]`（`prebuilt_sync` 把它写进目录快照），用户启用技能时授权一次；技能边界守卫据此放行 `code_graph_tool` 以及技能步骤里的 `file_read_tool`、`grep_tool`。
