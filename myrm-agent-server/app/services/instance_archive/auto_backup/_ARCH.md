# services/instance_archive/auto_backup/

## 架构概述

本地/桌面实例的**定时整实例备份**（默认关闭）。业务策略层：决定**何时备、备到哪、留几份、连续失败如何告知用户**。导出流水线完全复用手动「创建备份」的 `export_jobs.ExportJobManager`（同一份 `build_export`、同一个单飞闸门），所以产物与手动备份是同一种文件，恢复走既有的「从备份恢复」导入流程，本目录不实现恢复入口。

核心约束（代码为准）：

- **默认关闭，仅本地/桌面**：云端沙箱的数据在托管卷上，`get_auto_backup_service` 返回 `None`，API 报告 `supported=false`，前端不渲染卡片。非标准目录布局同理（`policy.is_standard_layout`）。
- **绝不带密钥**：以 `LOCAL_USER_ID` 导出，`config_key` 与口令均为空；备份是未加密的普通文件，界面如实告知。
- **「完成」的语义**：文件已落到目标位置、manifest 读得回、大小一致、已刷盘。这证明「写好且结构可读」，不是 payload 全量哈希校验；恢复时的校验仍是权威。界面写「最近一次备份」，不写「已验证」。
- **读不到的数据项不算备份完成**：导出遇到无法列出的目录、无法读取的文件时，会把这些路径随结果带回（`ExportResult.unreadable`，与「导出途中已不存在」的文件区分：后者是正常的并发变化，不计入）。这样的运行记为失败 `backup_incomplete`，不记成功，也不清零连续失败，告警走同一条连续失败路径；已经产出的归档仍然保留，改名为 `…-YYYYMMDD-HHMMSS.incomplete.zip`，用户能恢复它收下的那部分，而不是什么都没有。`.incomplete.zip` 不匹配完整备份的文件名模式，所以不计入保留份数、不进备份列表、不影响到期判断；同一实例只留最新一份，下一次完整备份成功后清掉，裁剪永不碰完整备份。
- **文件夹是「已备份」的唯一事实**：不记「上次成功」。最近一次备份的时间与大小、是否到期、是否严重逾期、保留份数，全部从目标文件夹里本实例的文件推导；用户手动删光文件或换到另一个文件夹，下一次检查看到的就是真实状态，不会因为一条陈旧记录而误判已受保护。持久化的运行状态只剩 `last_attempt_at`、连续失败数与最近错误码（失败退避所需）。
- **文件名带本实例标记**：`myrm-auto-backup-{tag}-YYYYMMDD-HHMMSS.zip`（UTC）。`tag` 是首次使用时随机生成的 8 位十六进制，存于独立的 `auto_backup_instance.json`（RUNTIME 类，恢复不覆盖；只在文件不存在时写入一次，读取失败不会重新生成，设置文件读不出来也不会连带改写它）；不用主机名（`localhost`、WSL 等会撞名）。多台设备共用同一个同步文件夹或 NAS 共享时，各自只列出、只裁剪带自己标记的文件，不会互相删备份。云端记忆备份的文件名也用这同一个标记（`services/memory/backup/remote_sync`），一个实例只有一个标记；生成标记的锁是模块级的，不同的 store 对象同时首次使用也只会生成一个。
- **目标位置**：状态目录之外任意可写位置；状态目录之内只允许 `{state}/backups/`（策略分类为 LOCAL_HISTORY，不进归档、不被导入换入或清扫），其余位置一律拒绝。
- **保留策略只动自己的文件**：只匹配本实例标记的 `.zip`、`.incomplete.zip` 与遗留的 `.partial`，手动下载、其他归档、其他实例的备份、符号链接永不列出、永不删除；完整备份成功后才裁剪完整备份（并清掉被它取代的 `.incomplete.zip`），失败与不完整的运行不会减少用户已有的完整备份，且刚写好的那份永不被裁掉。
- **日期在未来的文件**（时钟曾被拨快后又校正）既不算「最近一次备份」（否则会让备份停摆到那个日期），也不被自动删除（时钟临时回拨时，真实备份会暂时看起来在未来）；它只占一个保留名额。记录的**尝试时刻**同理：晚于当前时间的尝试视为不存在（`schedule._attempt_so_far`），既不顶替读不到的文件夹，也不让失败后的重试被推迟到时钟追上它为止，下一次每小时检查即可重试；读不到的文件夹遇到这种尝试没有可依托的参考，会在下一次检查尝试备份，写入不可用即记为失败。
- **设置不随备份走**：`{state}/instance_archive/auto_backup.json` 与 `auto_backup_instance.json` 属 RUNTIME 类，恢复只改数据，不改保护数据的计划，也不改变哪些备份属于本实例。
- **换目录即换视角**：新位置没有本实例的备份，首份立即到期；换回已有近期备份的位置则不重复备份。换目录或重新开启会清零连续失败（退避属于旧位置）；运行中途被换走的目录，其失败不计入新目录。
- **到期由文件夹里最新的备份推导**：应用关闭期间错过的备份在下次每小时检查时补做；连续失败不足 3 次时间隔 30 分钟即可重试，第 3 次失败起回落到所选频率，不会对长期损坏的目标反复冲击。写入时目标若不可用即记为失败（`backup_dir_*`；不回答的文件夹记为 `backup_write_failed`），走连续失败告警路径。
- **读不到的文件夹是「未知」，不是「空」**：列举失败（`OSError`：外置盘被拔出、网络共享离线、权限被拒）时，视图标记 `reachable=false`（API `folder_available=false`），备份列表与最近一次为空，但这不代表备份不存在。此时到期与逾期以**最近一次成功尝试**的时刻为准（`schedule.reference_moment`），拔掉移动硬盘不会被当成「没有备份」而立刻制造失败与告警；到了该备份的时间才尝试，写入不可用即记为失败。最近一次尝试失败过（连续失败数大于 0）时没有可依托的参考，按退避重试。可以读到但被用户清空的文件夹仍是「空」，立即到期。前端对此显示「暂时无法访问备份文件夹」，不写「尚无备份」。
- **不回答的文件夹也是「读不到」，不拖垮共享线程池，也不让无人值守的备份无声停摆**：目标可以是 NFS/CIFS/FUSE 共享，服务端失联时硬挂载的调用会无限阻塞且无法中断。
  - **为什么要守卫**：走 `asyncio.to_thread` 的默认线程池时，设置页运行中每 2 秒一次的轮询各会永久占掉一个工作线程，池满后所有用这个池的功能（IM 附件、wiki、记忆、技能、插件、看板等）一起排队；定时备份的预检若直接访问文件夹，运行位永不释放，既无失败记录也无告警。
  - **守卫**：列举，以及保存、立即备份、定时备份的创建与可写探测（`destination.prepare_destination_guarded`），都经 `folder_guard.FolderGuard`（服务与运行器共用同一个实例）：单条私有 daemon 线程逐个执行，调用方最多等 10 秒，超时抛 `FolderUnresponsive`（`OSError`）；正在执行的调用卡住超过超时后，后续调用立即失败而不是各等 10 秒；等不及而放弃的排队调用永不执行。用 daemon 是因为解释器退出时会等待线程池线程，卡在内核里的线程会让应用无法关闭。经 `call` 进入守卫的只有放弃也无害的幂等短操作（列举、创建目录、写探测文件）；长搬运见下面的「搬运守卫」。刚失联的前 10 秒内，轮询各占一个池线程直到超时，峰值约 5 个，之后新的调用不再占用池线程。
  - **结果**：列举超时按「读不到」处理（`reachable=false`）；创建与探测超时一律映射为 `backup_write_failed`（文案要求确认文件夹可用后重试，不叫用户换文件夹；与没有写权限的 `backup_dir_not_writable` 区分）。保存与立即备份被拒绝，保存时不写任何设置；定时备份约 10 秒内记为一次失败并释放运行位，其后按常规退避与连续失败告警处理，共享恢复后的下一次检查自动补做。
  - **失败归属**：运行器判断失败是否属于已被换走的目录时只比较设置里的路径（`destination_path`，不做 `resolve`），否则记录失败时会再次访问失联的文件夹而永远记不下来。
  - **边界**：每次短操作都要超过 10 秒才应答的慢共享，按一次失败记录；搬运不受这个 10 秒限制，按下一条的进展判断。
  - **搬运守卫（拷贝中途失联）**：预检通过之后，把归档移入目标并读回校验是一次受守卫的搬运（`FolderGuard.call_progressing`），用运行器持有的第二个守卫实例，不与上面 10 秒的短调用共用工作线程，所以长拷贝不会让 2 秒一次的状态轮询排队超时。
    - **按进展判断**：拷贝每读一块源数据（上一块已写完）向 `Pulse` 报一次进展，**连续 `TRANSFER_STALL_SECONDS`（300 秒）读不到下一块**才放弃，没有总时长上限。
    - **分段刷盘**：拷贝每写满 `_SYNC_EVERY`（64 MiB）就向目标刷一次盘。NFS 这类网络共享的客户端会把写入攒在本机，直到被要求刷盘才发出；不分段的话，整份归档的发送集中在最后一次不报进展的 `fsync` 里，健康但偏慢的共享会被误判为失联。每次刷盘返回后的下一次读取即报进展，所以窗口的含义是「300 秒内共享至少消化了 64 MiB」，约 0.2 MiB/s；慢于这个速度的共享与失联无法区分。300 秒与 64 MiB 都没有做基准测试，分段刷盘在真实 SMB/NFS 共享上的开销也没有实测。
    - **放弃的结果**：抛 `FolderUnresponsive`，走既有的 `backup_write_failed` 分支，释放运行位，前端零改动。卡住期间的下一次运行在同一守卫上立即失败，不会叠起第二个拷贝线程。
    - **迟到的拷贝不留痕**：线程无法从外部终止，所以被放弃的拷贝在每次读取、每次发布（`os.replace`）之前、读回校验之后检查 `Pulse` 并中止：清理 `.partial`，不发布；若已经发布则撤回，保证「搬运放弃 ⇒ 不留新文件」。唯一留下新文件的失败是 `backup_incomplete`，且这份文件是有意保留的 `.incomplete.zip`，不是被放弃的拷贝。
    - **裁剪不返回**只记 warning：裁剪是列举加删除，属于与预检同类的短调用，经 10 秒的短守卫，不占用搬运守卫的 300 秒等待，所以已记完成之后运行位不会再被多占 5 分钟；备份已完整，不记失败，也不丢已完成的状态。源归档删除失败（放弃的拷贝仍占着文件，Windows 上无法删除）只记日志，不覆盖已记录的结果，由导出目录的 6 小时清扫兜底。
    - **睡眠不是失联**：等待方自己被冻结（机器睡眠；Windows 的 `time.monotonic()` 含睡眠时间，Linux 与 macOS 不含）时重置计时，不把休眠误判为目标无进展。
- **同一时刻只有一次运行**：判断是否忙与占用运行位（`service._spawn`）在事件循环里无 `await` 地一气完成；立即备份与每小时 tick 即使同时通过各自的前置检查，也只有一个能启动，另一个得到 `ExportBusyError` 或 `False`。
- **连续失败提示**：第 2 次连续失败时发一次 `HEALTH_ALERT`（`component=instance_backup`），成功即重置；事件总线非线程安全，告警经 `call_soon_threadsafe` 交回启动运行的事件循环。
- **只暴露稳定机器码**：`backup_dir_invalid`、`backup_dir_inside_state`、`backup_dir_not_writable`、`backup_write_failed`、`backup_unreadable`、`backup_incomplete`、`insufficient_space`、`export_failed`；文案全部在前端 locale。

## 文件清单

| 文件 | 地位 | 职责 | I/O/P |
|------|------|------|-------|
| `__init__.py` | 门面 | 导出服务、调度入口与前后端共用常量 | ✅ |
| `models.py` | 核心 | 设置/运行状态/备份文件契约、保留份数边界、实例标记格式、稳定错误码异常（无 I/O） | ✅ |
| `store.py` | 核心 | 设置与运行状态的单文件 JSON 持久化（整体重写 + 锁，读到异常内容回落默认并钳到边界）；实例标记另存独立文件，首次使用时生成一次（锁为模块级，同一实例的所有 store 对象共用） | ✅ |
| `destination.py` | 核心 | 目标文件夹解析（默认 `{state}/backups/instance`；`~用户名` 无法确定家目录时保持原样，由预检按 `backup_dir_invalid` 拒绝，而不是让每个调用方抛 `RuntimeError`）、校验、创建与可写探测；`prepare_destination_guarded` 经守卫执行同一件事，不回答的文件夹映射为 `backup_write_failed`（服务与运行器唯一的预检入口） | ✅ |
| `retention.py` | 核心 | 带实例标记的文件命名（完整备份 `.zip` 与不完整副本 `.incomplete.zip`，后者不匹配前者的模式）、列举（最新在前；文件夹读不出时抛 `OSError`，不当作空）、最近一次备份（忽略未来日期）、裁剪（仅限本实例的文件：`prune` 裁完整备份并清不完整副本，`prune_incomplete` 只留最新一份不完整副本、不碰完整备份；读不出则不裁） | ✅ |
| `folder_guard.py` | 核心 | 访问备份文件夹的有界守卫：单条私有守护线程逐个执行，`call` 最多等超时时间，`call_progressing` 按进展等待长搬运（连续无进展超时才放弃，无总时长上限；等待方自身被冻结时重置计时），`Pulse` 汇报进展并在被放弃后令操作收尾；卡住后后续调用立即失败，已放弃的排队调用不执行，空闲即退出。不让失联的共享拖垮共享线程池 | ✅ |
| `schedule.py` | 核心 | 纯规则：由参考时刻（可读时为文件夹里最新备份，读不到时为最近一次成功尝试）判断是否到期、是否严重逾期，以及告警阈值（不读时钟；晚于传入的当前时间的尝试时刻视为不存在） | ✅ |
| `runner.py` | 核心 | 一次备份：经守卫预检目标 → 导出 → 刷盘 → 经搬运守卫移入目标并读回校验（同卷 rename，跨卷 `.partial` 复制并每 64 MiB 向目标刷一次盘；300 秒消化不了一段才放弃，放弃后的拷贝不发布、已发布则撤回）→ 导出带回读不到的数据项时改以 `.incomplete.zip` 留存并记 `backup_incomplete` → 记录尝试 → 经守卫裁剪（卡住只记 warning）；失败记录不抛出（目标不回答也在守卫超时内记为失败），已被换走目录的失败丢弃（只比较设置里的路径，不碰文件系统） | ✅ |
| `service.py` | 核心 | API 与调度器的统一入口：视图（备份列表与最近一次均读自文件夹，并标明文件夹是否读得到）、应用设置（保存后若到期则立即备份；对文件夹的列举与探测经 `folder_guard`，并与运行器共用同一个守卫；运行器另持长搬运专用的守卫）、手动立即备份、每小时 tick（占用运行位的检查与占用在事件循环里原子完成）、告警发布 | ✅ |

## 依赖方向

`app/api/instance_archive/auto_backup.py` 与 `app/lifecycle/schedulers.py` → 本目录 → `app/services/instance_archive/{export_jobs,models,policy}` → `myrm_agent_harness.infra.state_archive`。`services/memory/backup/remote_sync/state.py` 只读取本目录的实例标记（`AutoBackupStore.tag()`）。本目录不依赖 API 层；父包不依赖本目录（`export_jobs` 只暴露 `done` / `is_busy` / 注册表供其使用）；harness 不感知本目录。
