# channels/providers/email/

## 架构概述

Email 渠道 Provider（IMAP 轮询入站 + SMTP 出站）。一轮轮询取哪些邮件、怎样交给入站管线、下一轮从哪里接着取拆入 `poll.py` Mixin，入站解析（附件、转发邮件、HTML 转 Markdown、线程头）拆入 `inbound.py` Mixin，渠道本体只负责凭证、生命周期、轮询循环与 SMTP 发送。上级文档：[../_ARCH.md](../_ARCH.md)。

- **每个 IMAP / SMTP 连接都传 `ssl.create_default_context()` 与 30 秒套接字超时**（上下文每次连接现建，不缓存；IMAP 经 `_connect_imap` 一处建立）：服务器证书与主机名被校验，企业网络兼容设置决定信任什么；对不应答的服务器，连接与每次读取 30 秒后放弃，不会让轮询线程与健康检查无限阻塞。标准库在没传上下文时用不校验的默认上下文，全局策略碰不到它；`tests/architecture/test_tls_single_trust_source.py` 对 `app/` 与 `assets/`（预置技能脚本）里缺上下文关键字的 `SMTP_SSL`、`IMAP4_SSL`、`.starttls` 调用报错，只查传了上下文，关键字名是否写对（`imaplib` 要 `ssl_context=`，`smtplib` 要 `context=`）由调用点的测试用 `autospec` 替身钉住：渠道是 `tests/channels/providers/email/test_email_connections.py`，预置邮件技能脚本是 `tests/assets/test_imap_smtp_email_script.py`（另对本机监听口做真实握手）。

- **服务器拒绝的 IMAP 命令不当成数据，被拒绝取信的邮件不丢**（`imap.py` 的 `require_ok`、`refusal`，`poll.py` 的 `_read_batch`）：`imaplib` 只对 BAD 抛异常，NO 作为状态返回、拒绝文本落在数据的位置。选 INBOX 与搜索被拒时抛 `imaplib.IMAP4.error`（带服务器原话），由 `reconnect_loop` 记 warning 并退避重试；单封邮件的取信被拒时记 warning 并结束本轮，高水位 `_last_uid` 停在这封之前、下一轮重新取它——跳过它会让后面的邮件把高水位推过去、这封信永久丢失。代价：服务器持续拒绝某一封时，每一轮轮询都停在它前面并记 warning，直到服务器肯给它或它被移走。预置邮件技能脚本的 `mail_client.transport.require_ok` 是同一契约的另一份实现（脚本是独立资产，不能导入 `app`）。守护用例：`tests/channels/providers/email/test_email_channel_imap_refusal.py`。

- **一封读不了的邮件不拖垮整个邮箱，一封中途失败的邮件不连累它前面已读到的邮件，积压按先来后到取完**（`poll.py` 的 `_read_batch`、`_parse_or_skip`；`inbound.py` 的 `_text`、`_decode_header`、`_to_text`）：轮询是重连循环里的无限重试（`reliability/reconnect.py`），所以只要同一封邮件让解析抛异常，每一轮都会在同一处失败、后面的邮件永远收不到。入站解析沿用标准库的旧策略 `compat32`（对头部值的原样透传不变），只处理它的几种不可读输出：头部含原始 UTF-8 字节（RFC 6532 合法）时解析器返回 `email.header.Header` 而不是 `str`，`_text` 把它按字节解码，`str` 原样返回；字符集名 Python 没有编码器（`unknown-8bit`、`x-unknown`）时 `_to_text` 按 UTF-8 读，正文、转发正文与内嵌图片引用的解码都经它；被截断的 base64 编码词让标准库抛 `HeaderParseError`，`_decode_header` 把这样的值原样返回；编码词旁的文字保留自己的空格，相邻编码词之间的空白不属于文本（`Re: =?utf-8?b?5Y+R56Wo?=` 读成 `Re: 发票`，两个相邻编码词直接连成一个词）。仍然抛出的邮件分两类处理：磁盘类 `OSError`（写满、临时目录不可写）会随磁盘恢复而消失，所以 `_parse_or_skip` 原样抛出；其余异常视为邮件自身的问题，重取预期只会再失败，由 `_parse_or_skip` 记一条带 UID 与回溯的 warning 后跳过，高水位照常越过它（不记主题与正文）。发件人写的文件名不会产生 `OSError`（见下一条），所以走重试的是磁盘本身的故障。一封邮件在取信、解析或落盘时失败（磁盘错误、连接中断）就结束本轮，而不是丢掉整轮：它之前已读到的邮件照常交付，高水位停在其中最后一封，下一轮从失败的这封重取；它之前什么都没读到时抛出，由重连循环退避重试。高水位只越过已读到或被跳过的邮件，在取信线程里只写一次（本轮结束时，含抛出），所以它越过的邮件一定在本轮返回的列表里（或被跳过）。守卫用例按失败位置（第一封、中间、最后一封）与失败类型（磁盘、连接、读不了）组合断言每封邮件恰好交付一次，另有一例用不存在的临时目录造出真实的磁盘错误。读到的邮件交付之前不算处理完，见下一条；进程重启后高水位归零、重新按 `(UNSEEN)` 取最新 20 封，已被取走（取信用 `RFC822`，按 RFC 3501 它会把邮件标为已读）却没来得及交付的邮件不会再出现。每轮最多新取 `_MAX_NEW_PER_POLL`（20）封，还没确认的邮件另算、会再给（见下一条）：稳态取高水位之后最旧的 20 封，积压在后续几轮里按顺序取完（`UID n:*` 在 n 超过邮箱末尾时仍答最新一封，所以先滤掉不大于高水位的 UID 再排序；RFC 3501 没有规定 SEARCH 结果的顺序，所以排序也不依赖服务器），首次轮询没有高水位，仍只取最新 20 封未读。守护用例：`tests/channels/providers/email/test_email_inbound_malformed.py`、`test_email_channel_poll_batch.py`。

- **取走的邮件交付之前不算处理完，一次只跑一轮轮询，服务器给邮箱重新编号时从头读起**（`poll.py` 的 `_poll_round`、`_fetch_new_emails`、`_read_batch`、`_renumbered`，`imap.py` 的 `uidvalidity`）：服务器在取信时把邮件标为已读（`RFC822`，RFC 3501 §6.4.5），高水位 `_last_uid` 在取信线程里前进，交付却发生在事件循环里的 `_emit_inbound`，三者之间没有确认。所以每个 UID 在取信之前记入 `_unconfirmed`，被交付（`_poll_round` 里入站管线对它做出了接受或丢弃的决定）、被跳过（读不了）或服务器上已没有它（取信返回空）时才移除；下一轮的批次是 `_unconfirmed` 与本轮搜索选中的邮件合并、按 UID 升序一起取。停止或重载把交付取消、磁盘写满、连接在应答到达前中断，邮件下一轮都会再给：交付被取消时高水位已被取信线程推过这些邮件，高水位为 0（进程启动后到第一封邮件处理完之前）时轮询按 `(UNSEEN)` 找邮件、服务器已把取走的邮件标为已读，两种搜索都找不到它们，只有 `_unconfirmed` 记得；失败而高水位停在它之前时，邮件本来就在 `UID n+1:*` 的范围内，`_unconfirmed` 与之重合、不改变结果（取信被拒的 UID 也留在集合里，下一轮本来就会取它）；搜索没有结果时也要处理 `_unconfirmed`，所以「没有未读」不提前返回。入站管线对一封邮件抛异常（`_poll_round` 里的 `except Exception`）时记一条带 UID 与回溯的 warning（不记主题与正文），这封邮件视为处理过，后面的邮件照常交付，不会每一轮都卡在同一封上；取消（`CancelledError`）不确认，下一轮再给；真实的 `_emit_inbound` 没有让出事件循环的点（限流等待取的是没有争用的锁，去抖窗口默认 0 且生产代码从不设置，派发到总线是 `put_nowait`），所以取消只会落在轮询路径上的三处等待，这是对当前实现的判断：等取信线程（`_poll_round` 里的 `asyncio.to_thread`，邮件已被取走、靠 `_unconfirmed` 再给）、轮询间隔的睡眠（`_poll_once`）、出错后重连退避的睡眠（`reliability/reconnect.py` 的 `reconnect_loop`）；后两处没有正在交付的邮件，退避发生在取信线程抛出之后，取信到一半抛出的那封仍留在 `_unconfirmed` 里，取消后在同一个实例上重新启动，下一轮再给；管线一侧的这条处理由会挂起的替身管线覆盖。一次只跑一轮：取消交付不会停下 `asyncio.to_thread` 里的取信线程，`reload_channel` 又复用同一个渠道实例，所以新一轮可能在旧线程还在跑时开始；`_fetch_new_emails` 用非阻塞的 `_poll_lock`（`threading.Lock`）判断，拿不到锁就返回空列表、下一轮接着取，既不占用线程池里的工作线程，也不会读到与旧线程相同的邮件、把高水位写回得更低。UID 只在发布它的 UIDVALIDITY 之下有意义（RFC 3501 §2.3.1.1，服务器迁移邮箱或从备份恢复时可能换一个值）：`select` 之后读一次（`imaplib` 把它存成读一次就被取走的未标记应答，所以只读这一次，且只认 bytes），与上一次记下的值不同就记 warning，把高水位与 `_unconfirmed` 归零、重新按 `(UNSEEN)` 取最新 20 封，已交付过的邮件，只要它的 Message-ID 还在入站管线记着的最近 1024 条里，就被入站管线挡住（`app/channels/core/inbound_pipeline.py` 的 `_emit_inbound`；这份记录在内存里，默认的 LRU 模式只按容量淘汰、没有时限，进程重启后为空）；服务器没给值就不比较，也不会冲掉记下的值。不保证的 [读码]：进程退出或崩溃（高水位、`_unconfirmed` 与记下的值都只存内存，已取走但尚未交付的一批邮件（可能多于 20 封，见下文），重启后的 `UNSEEN` 搜索找不到它们，进程停机期间发生的重新编号也读不出来）；交付之后的兜底是路由器的入站日志（`app/channels/reliability/inbound_journal.py`），它只在两处写入：一轮开始时（`app/channels/routing/pipeline/turn.py` 的 `_journal_inbound`）、优雅停止时闸门里还没开始一轮的消息（`app/channels/routing/pipeline/lifecycle.py` 的 `stop`），一轮结束时确认删除（优雅停止时被取消的那一轮也在这时删除，所以不重放；按 `stop` 的文档串，其聊天会收到重发请求的提示，是否送达邮件发件人没有核实），启动时由 `app/channels/core/gateway.py` 的 `_recover_journal` 重放没确认的条目，条目自写入起 600 秒内有效（`_DEFAULT_TTL_SECONDS`）；所以崩溃后在有效期内重启，崩溃时被打断的那一轮里的邮件会重放，而已交付、却还在总线队列里或在闸门里没开始一轮的邮件不在日志里，服务器又已把它们标为已读，会丢；优雅停止时也有一段：网关先停路由器，渠道要等出站排空之后才关（`app/channels/core/gateway.py` 的 `stop`），这段时间邮件渠道仍在轮询，交给总线的邮件没人取，总线停止时队列被丢弃（`app/channels/core/bus.py` 的 `stop`），同样不在日志里，这一段多长没测；入站队列已满时 `app/channels/core/bus.py` 的 `_handle_inbound` 丢弃消息，只记 warning，同样不在日志里。一批可能比 20 封多：待再给的邮件加上本轮新取的最多 20 封。守护用例：`tests/channels/providers/email/test_email_channel_poll_cursor.py`、`test_email_channel_poll_delivery.py`，其假服务器 `email_inbox.py` 按 RFC 3501 建模（取 `RFC822` 置已读、`(UNSEEN)` 跳过已读、UIDVALIDITY 是读一次的应答，取信线程可被 `on_fetch` 钩子挂住）。

- **附件按发件人写的样子识别、命名与落盘**（`inbound.py` 的 `_is_attachment`、`_embedded_ids`、`_name_headers`、`_attachment_filename`、`_safe_suffix`、`_save_attachment`、`_save_attachments`）：是否算附件按 RFC 2183（处置类型大小写不敏感）判断——`Content-Disposition: attachment` 一律算；非文本且带文件名的部分，无论处置是 `inline`、缺省，还是只有 `Content-Type; name=` 给了名字，也算；文本部分给自己起名仍是正文；HTML 里用 `cid:` URL 引用的内嵌图片（邮件签名的 logo）不算（RFC 2392，Content-ID 按原样与 `%` 解码后两种写法比对）。整封邮件本身就是一个非文本附件（单部分的 PDF，扫描仪常见的写法）时，它自己就是附件，而不是被当文本解码成乱码塞进正文；单部分的文本邮件仍是正文，不论它的处置怎么写。文件名经 `_name_headers` 取出（头部含原始 UTF-8 时标准库给的是 `Header`，会被读成替代字符，所以先按字节解码），再解码 RFC 2047 编码词，取不到名字时叫 `attachment`；RFC 2231 的写法由标准库解码。`MediaAttachment.filename` 是解码后的原名；落盘路径只保留原名扩展名里 `.` 加 1–16 位字母数字的部分，否则不留扩展名，因为文件名由发件人决定，扩展名会进入路径、给 Agent 的提示词与文件系统的长度限制：超长扩展名让创建临时文件抛 `OSError`，含 NUL 抛 `ValueError`，`;touch x` 之类原样进入视频附件的提示词。展示名保留原样：下游用它的后缀路由文档提取，`services/files/content_extraction.py` 在建临时文件之前先检查后缀属于受支持集合。一封邮件的附件在其余部分都解析完之后才落盘（`_parse_email` 先收集待存的部件，最后由 `_save_attachments` 写），全部写成或全部不留：写入失败时删掉本邮件已写的文件与失败的那个，解析在落盘之前抛出的邮件不会留下任何文件，因为失败的邮件会被重读，留下的文件会在每次重试时再写一遍。预置邮件技能脚本的 `mail_client/message.py` 是同一契约的另一份实现（脚本是独立资产，不能导入 `app`）。守护用例：`tests/channels/providers/email/test_email_inbound_attachments.py`。

## 文件清单

| 文件 | 地位 | 职责 | I/O/P |
|------|------|------|-------|
| `__init__.py` | 入口 | Email channel provider package facade (re-exports EmailChannel for the registry's lazy loader). | ✅ |
| `channel.py` | 模块 | Email channel: credentials, lifecycle, the poll loop and SMTP sending over certificate-verified connections (delegates one poll round to `poll.py`, MIME assembly to `outbound.py`). | ✅ |
| `poll.py` | 模块 | Email polling mixin: the batch one IMAP poll takes from INBOX, its hand-over to the inbound pipeline and where the next resumes. Opening INBOX or searching it being refused is an error with the server's reason; a refused fetch is retried by the next poll; a poll takes at most 20 new messages (the oldest after the high-water mark, the newest on the first poll), skips one the parser cannot read, and ends at one that fails for another reason (a disk error, a dropped connection) after delivering the messages before it. A message is offered again by every poll until the inbound pipeline has decided about it, so a stop, a reload or a failure does not lose what the server has already marked read; the pipeline failing on one message does not hold back the others; one poll runs at a time. A server that announces another UIDVALIDITY is read from its start. | ✅ |
| `imap.py` | 模块 | IMAP conversation helpers shared by the poller and the health check: the RFC 2971 client ID, the reading of a server's reply (a refusal is an error carrying the server's words, never data) and the UIDVALIDITY a server announced when INBOX was selected. | ✅ |
| `inbound.py` | 模块 | Email inbound: RFC 822 message to InboundMessage conversion. Multipart bodies, HTML-to-Markdown cleaning, thread headers, automated-sender filtering and forwarded-message parsing; raw UTF-8 headers, unknown charset names and cut-off encoded words are decoded instead of failing the message. Attachments are recognised however the sender wrote the disposition (or only the Content-Type name), named by their decoded file name and saved under a plain extension only; a non-text message that is one attachment is attached. The files of a message are written once the rest of it has been read, all of them or none. | ✅ |
| `outbound.py` | 模块 | Email outbound: loads attachments (local files or SSRF-validated downloads, size-capped) and assembles the multipart MIME message. Attachments that cannot be loaded are returned separately so the channel reports them instead of dropping them. | ✅ |
| `forward.py` | 模块 | Forwarded email detection and structured parsing. Separates user annotation from original email content, detects Gmail/Outlook/QQ separators and MIME message/rfc822 format. | ✅ |
