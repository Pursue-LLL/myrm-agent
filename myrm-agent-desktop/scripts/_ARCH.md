# myrm-agent-desktop/scripts 模块架构

[INPUT]
- myrm-agent-frontend（POS: build-frontend.sh 构建 standalone）
- src-tauri/（POS: cargo-check、launch contract 静态校验）

[OUTPUT]
- 本地构建脚本、CI 分形文档门禁、发版验签辅助

[POS]
桌面仓 scripts/ 根。发版编排主流程在 monorepo 根 scripts/ci/desktop-release/。

## 架构概述

桌面仓本地构建与发版验签辅助脚本。由 `myrm-agent-desktop/_ARCH.md` 引用；CI 桌面流水线见 [../../scripts/ci/desktop-release/_ARCH.md](../../scripts/ci/desktop-release/_ARCH.md)。

## 文件清单

| 文件 | 平台 | 职责 | I/O/P |
|------|------|------|-------|
| `check-fractal-docs.ts` | CI | 分形文档门禁：6 静态 + 递归根自动发现 `_ARCH [POS]` + 2 递归根目录扫描 + 17 核心 `[INPUT]` + 核心安全文件与 `permissions/autogenerated/*.toml` 全量 git 跟踪检查 + 命令清单/ACL 一致性校验 | ✅ |
| `check-fractal-docs.test.ts` | CI | 门禁单元测试 | — |
| `ci/fractal_docs_baseline.txt` | CI | 递归扫描 grandfather 清单（`--write-baseline` 维护） | — |
| `ci/cargo-check.sh` | CI | 以 `TAURI_CONFIG` 清空 `bundle.resources` 与 `bundle.externalBin`（不依赖 sidecar 目录、前端构建产物与 Node.js 运行时；`tauri-build` 对缺失的声明文件连 `cargo check` 也报错）→ `cargo check --locked` + 平台无关单测（`config::tests`、`runtime::product_origin`、`runtime::sidecar_path`、`runtime::node_runtime`、`app::chain`、`ipc_security::acl_tests`、`app::autostart`、`utils::data_dir` 等） | — |
| `ci/verify-launch-contract.sh` | CI | 静态校验 Launch Contract（含 `frontend-start-failed` / `backend-start-failed` shell 处理；前端桌面就绪预算 `DESKTOP_BACKEND_HEALTH_MAX_ATTEMPTS` × 轮询间隔必须大于壳的 `BACKEND_STARTUP_TIMEOUT`） | — |
| `fetch_node_runtime.py` | 双平台 + CI + 前端 dev | 取回钉死版本的 Node.js 运行时，有两个使用者共用同一份钉死版本：① 壳启动内置 Next，写成 Tauri `externalBin` 期望的 `src-tauri/binaries/myrm-node-<目标三元组>[.exe]`；② 前端 dev server（`myrm-agent-frontend/scripts/node-runtime.ts`）在本机没有可用 Node 时用 `--output-dir` + `--name node` 取到自己的 `.myrm/node`。从 nodejs.org 官方归档下载（用系统 `curl`，信任系统证书库；`MYRM_NODE_DIST_URL` 可指向镜像，镜像不受信，靠 SHA-256 兜底）、校验 `node_runtime.json` 钉死的 SHA-256（不符即拒绝，不留残件）、只抽出 node 可执行文件、在本机平台上运行 `--version` 核对钉死版本；已是钉死版本则零下载返回。不带 `--target` 时目标取 `rustc` 报告的 host，没有 `rustc` 就按本机平台识别，本机没有钉死的运行时则报错并提示自行安装 Node.js。三个构建 job 在 `tauri-action` 之前各跑一次，本地开发 `cargo tauri dev/build` 前跑一次（`./myrm-dev desktop sidecar` 已包含）；契约见 `tests/architecture/test_desktop_node_runtime.py`（桌面侧）与 Dev Gate 套件里的 `test_node_runtime_fetch.py`（dev server 侧） | ✅ |
| `node_runtime.json` | CI | 钉死的 Node.js 版本与每个构建目标的官方归档 SHA-256；换版本只改这个文件，换完由契约测试核对每个目标都有下载定义与校验和 | — |
| `build-frontend.sh` | Unix | 从 desktop 根解析 monorepo 路径，在 `myrm-agent-frontend/` 执行 `build:tauri`（或 `dev` 模式 `bun run dev`）；standalone 已存在则跳过构建 | ✅ |
| `verify-signing.sh` | Unix (macOS) | `.app` / `.dmg` 产物的签名验证，必须给 `--level`：`sealed`（ad-hoc 签名即可）查 `codesign --verify --deep --strict` 与 `codesign -dv`，`.dmg` 只读挂载后验里面的 `.app`，没有封印的包（Gatekeeper 报“已损坏”的那种）在这里失败；`notarized` 在 `.app` 上再加 `spctl --assess` 与 `xcrun stapler validate`，`.dmg` 只做后两项；失败计数作为 exit code。`desktop-release.yml` 的 `build-macos-arm` 在 `tauri-action` 之后、烟测之前调用：配置了 `APPLE_ID` 用 `notarized`，否则用 `sealed`；门禁 `test_desktop_macos_signing.py` | ✅ |
| `verify-signing.ps1` | Windows | 已签名安装包的 Authenticode 验证（与 `verify-signing.sh` 对称）；尚无工作流调用，配置签名证书后再接入 | ✅ |
| `inset-app-icon.py` | 双平台 | 从 `myrm-agent-frontend/public/brand` 源图生成 PWA/Tauri/tray 图标；托盘部分把前景层交给 `tray_status_icons.py`；维护者手动运行 | ✅ |
| `tray_status_icons.py` | 双平台 | 托盘图标整套资源的唯一生成点：黑色模板字形 `tray_icon@2x.png`，以及在字形右下角加徽标的 `tray_icon_busy@2x.png`（绿色圆点）与 `tray_icon_degraded@2x.png`（琥珀色三角）。macOS 模板图标只按透明度绘制，徽标靠轮廓区分，周围镂空一圈透明光环避免并进字形；颜色留给不走模板的平台；只产出托盘实际加载的 `@2x` 尺寸；契约见 `tests/architecture/test_desktop_tray_icon.py` | ✅ |

## 约束

- Python 仅 `inset-app-icon.py` 与 `tray_status_icons.py`（品牌图标生成，依赖 Pillow）和 `fetch_node_runtime.py`（Node.js 运行时取包，仅标准库）；后端或 sidecar 打包见 `sidecar/build.py`
- 发版编排脚本在仓库根 `scripts/ci/desktop-release/`，不在本目录
