### 症状

1. [实测] 真实工厂下，`MemorySearchPolicy()` 与 `MemorySearchPolicy(allow_shared_write=False)`（server 给外部渠道构造的策略）产出的 `memory_save_tool` 定义逐字相同：描述带 `**WRITE TARGET**` 段，参数带 `write_target`（枚举 `bound` / `shared`）；EN 814 token、ZH 833 token（`o200k_base` 对 wire JSON 计数）。
2. [实测] 同一个调用 `{"content": "My timezone is UTC+8", "category": "knowledge", "write_target": "shared"}`，在默认 web 链（`global, agent:writer, conversation:c-1`）上：默认策略写进 `global`，外部渠道策略写进 `agent:writer`，两者回执都是 `Knowledge stored (ID: …)`，模型无从得知被改写。落点随命名空间链变化，见「落点实测」。
3. [实测] 模型会选它：`MiniMax-M3.1-Flash-Preview`（温度 0.5，短轨迹：先调检索得到「无相关记忆」，再决策一次）面对「请记住我的时区是 UTC+8，我所有的 Agent 都应该知道这一点」，默认表面 10/10 次带 `write_target=shared`；只删描述里的 WRITE TARGET 段、参数不动，仍有 7/10 次。

### 根因 [代码]

- 模型可见的 save 表面有两处不读 `allow_shared_write`：描述里的 `**WRITE TARGET**` 段是 `MEMORY_SAVE_CORE_{EN,ZH}` 的最后一段，随核心描述无条件输出；参数是 `@tool("memory_save_tool", …, args_schema=MemorySaveInput)`，`write_target` 常驻。
- `allow_shared_write` 只在保存协程里读一次：不允许且 `write_target == "shared"` 就改成 `bound`（现 `save_tool.py:232`）。
- server 对外部渠道构造 `allow_shared_write=False`（`myrm-agent-server/app/ai_agents/general_agent/tool_setup/memory.py:92-96`），save 工具经该文件 `:128` 交给智能体。
- 与 2026-11-05 的 search 问题（`70b0fef2ae`，`memory_search_tool` 的 corpus 参数与描述不随检索策略变化）同一类：策略只管工具层放行什么，不管模型被告知什么。

### 修复了什么

1. WRITE TARGET 段移出 `MEMORY_SAVE_CORE_*`，成为独立常量 `MEMORY_SAVE_WRITE_TARGET_{EN,ZH}`；`build_memory_save_tool_description` 只在 `policy.allow_shared_write` 时把它接在核心之后（`_memory_agent_tool_descriptions.py:136-137`）；删除 `MEMORY_SAVE_TOOL_DESCRIPTION{,_EN,_ZH}` 三个别名（save 描述按策略组合，不再有固定常量）。
2. `save_tool.py` 新增 `memory_save_input(policy)`（`:85-87`）：允许共享写入时返回 `MemorySaveInput`，否则返回 `_BoundOnlySaveInput`（`:81`）——`write_target` 改为 `SkipJsonSchema` 字段，不出现在 schema 里，仍被接受、默认 `bound`；`@tool` 的 `args_schema` 用它（`:209`）。
3. 保存协程里的压回逻辑不动，作为模型仍传 `shared` 时的最后一道防线（`:232`）。
4. 默认策略与 MCP 的描述、schema 不变（88 个模型可见面逐字节相同）。
5. 文档：`MEMORY_SYSTEM.md`、`agent_surface/_ARCH.md`、`memory_agent_tools/_ARCH.md`。

### 没有解决 / 遗漏（截至 2026-11-07 晚）

1. 外部渠道里用户明说「所有 Agent 都应该知道」时，请求依旧无法满足（外部渠道不写共享区是设计）：改前模型会选 `shared` 并得到 `stored`，改后模型没有这个选项、写进绑定命名空间。模型对用户的最终回复是否因此更准确，没有测（验证只到工具调用）。
2. `write_target` 对 preference / instruction / rule 本来就不起作用：[实测] 三类调用都不把 `write_target` 交给 manager（`save_tool.py` 只有 `_save_knowledge`、`_save_event` 传它），这条没有动。早期消融（英文、中文，数据在会话临时目录、未入库）里模型共发出 270 次 `shared`，其中 161 次的类别是这三类；默认渠道的描述仍把 `shared` 写成对所有类别通用的选项。
3. 模型仍传 `shared`（沿用历史调用、别的提供方）时，工具照旧压成 `bound`，回执仍是 `Knowledge stored`，没有「已改写」的提示：保留这条路径是为了不让调用因校验失败而重试，没有改回执。
4. 项目会话里两个目标落在同一处，见 `MEMORY-20261107-02`。
5. 真实模型验证的范围：只在本地网关的 deepseek v4.1 flash 上跑（英文、单步、检索已预先回答「无相关记忆」）；MiniMax 候选面没有跑（服务商套餐额度用尽，错误码 2056，没有买额度、没有换 key）；中文没有跑；token 门禁只覆盖英文。
6. 没有核实：同一会话中途切换渠道的行为、外部渠道里 `shared` 写入的生产频率、压回逻辑当初的设计意图、外部渠道里主人自己的私聊也被禁止 `shared` 是否本意（判定只看渠道名，`tool_setup/memory.py:92`，没找到理由的文档或提交说明）、真实检索（落点核实用的是桩存储，只证明落点，不证明召回）。

### 踩坑

1. 只改描述不够：删掉 WRITE TARGET 段、参数不动时，症状 3 的那句话仍有 7/10 次传 `shared`，参数也必须从 schema 里拿掉。
2. 拿掉的参数仍要被接受：若阻断策略的 `write_target` 只剩 `bound`，模型（或沿用的历史调用）传 `shared` 会得到校验失败而不是被降级；所以用 `SkipJsonSchema` 保持「接受但不提供」（`search_input.py` 对 `corpus` 同样处理），「阻断 schema 拒绝 `shared`」的变异体被 2 例捕获。
3. pydantic 类的 docstring 会进入原始 `model_json_schema()` 的 `description`（经 provider 的 wire 路径会被剥掉，其它读 schema 的地方不会）：`_BoundOnlySaveInput` 因此用注释而不是 docstring，`test_the_blocked_schema_differs_from_the_default_only_by_write_target` 钉住。
4. WRITE TARGET 段搬出核心常量后，读核心常量的守卫测试（指引、泄漏）不再覆盖它，改读组合后的默认描述；子串断言用带引号的 `"shared"`，不用 `share`（会命中 “User shares…”）。
5. 第一版跨提供方探针按「文本里第一次出现 `memory_save_tool`」切片，命中的是 search 描述里的提及，得出「默认策略的 wire 上没有 `write_target`」，与此前的核实矛盾；改成按 `name == "memory_save_tool"` 且带 schema 的那一项选取后，openai、anthropic、gemini、MiniMax（openai 兼容）四种 wire 上默认都有、阻断都没有。
6. 触及的测试文件里 3 处 mypy 既有问题（冗余 `cast`、两个未标注类型的 fixture 参数）一并修掉。
7. 「共享」不等于「写进 global」：汇报时曾按默认链把它说成写进 `global`，落点核实后才发现它随链变化（见下）。凡是说「写到哪」，先在目标链上跑一次落点核实，不凭默认链推广。
8. 真实模型的结论要有同模型对照臂：只跑候选面得到的 0/10 说不清是「选项被藏起来」还是「这个模型本来就不传」，补了对照才关闭。

### 落点实测 [实测 2026-11-07 晚]

做法：每个场景用 server 真实的 `resolve_context_binding`（`myrm-agent-server/app/core/memory/adapters/setup.py:262`）得到命名空间链，再按同文件 `:192-197` 的传参方式构造 harness `MemoryManager`（命名空间、各 id、记忆策略），调用真实的 `memory_save_tool`。向量、嵌入、关系库是桩，不落盘，没碰真实数据；脚本在会话临时目录、未入库。

| 场景 | 命名空间链（读取顺序） | `bound` 落点 | `shared` 落点 |
|---|---|---|---|
| 网页聊天，无项目 | global, agent:writer, conversation:c-1 | agent:writer | global |
| 网页聊天 + 绑定共享上下文 team-1 | 上一行再加 shared:team-1 | agent:writer | shared:team-1 |
| 项目 p1 内的网页聊天 | project:p1, global, conversation:c-1 | project:p1 | project:p1 |
| Agent 私有写入被收窄到会话 | global, agent:writer, conversation:c-1 | conversation:c-1 | global |
| 外部渠道，主人私聊 | global, agent:writer, channel:tg-1, conversation:c-1 | agent:writer | global |
| 外部渠道，群聊或访客（隔间） | conversation:c-1, ident:group-1 | ident:group-1 | conversation:c-1 |

- **定义**：`shared` ＝ 绕开这个 Agent 的私有写入范围，写到链上最后一个 `shared:*`，没有则取链的第一个（`_internal/scope.py:252` 的 `scope_for_write_target`）；`bound` ＝ 这个 Agent 当前的私有写入范围（`AgentMemoryPolicy.write_policy` 控制，`config.py:108`；主命名空间的挑选见 `scope.py:211` 的 `resolve_primary_namespace`）。第四行展示了它的实际作用：私有写入被收窄时，它是写到更广一层的唯一出口。
- 两种链里 `shared` 并不「更广」：项目会话里与 `bound` 相同；群聊隔间里反而更窄（落到会话层）。
- 阻断策略（外部渠道）下，上面 6 个场景里 `shared` 一律被压成与 `bound` 相同的落点（6/6）。
- preference / rule / instruction 调用 manager 时都不带 `write_target`（3/3）。
- 生产接线与这里的构造一致：`myrm-agent-server/app/core/memory/adapters/setup.py:192-197,237-242` 传入 `binding.namespaces`、各 id、`binding.memory_policy`；harness 的 `derive_namespaces`（`scope.py:107`）对非空的传入链只做校验就返回，只有非 INHERIT 的写入策略才改写写入范围（`scope.py:160` 起的 `build_scope`）。

### 同模型对照实验 [实测 2026-11-07]

两个臂用同一个脚本、同一系统提示、同一句话（症状 3 的那句，场景记作 S7）、温度 0.5、max_tokens 2048、单步，`memory_search_tool` 都预先回答「无相关记忆」，只有传入的工具集不同。模型：本地网关的 deepseek v4.1 flash，英文。

| 臂 | 工具集 | 请求 | 带 `write_target` | 传 `shared` | 存储类别 | prompt / completion token | 运行时间 |
|---|---|---|---|---|---|---|---|
| 对照（选项可见） | 默认策略 | 10 | 10/10 | 10/10 | knowledge 10 | 21,110 / 1,473 | 17:12 |
| 隐藏（选项隐藏） | 外部渠道策略 | 10 | 0/10 | 0/10 | knowledge 7，instruction 3 | 20,220 / 2,270 | 14:44 |

- Fisher 精确检验（双侧）：`write_target=shared` 10/10 对 0/10，p = 1.08e-05。
- 每次请求相差 89 个 prompt token（2,111 对 2,022，网关自己的计数）；wire JSON 用 `o200k_base` 数是 78。
- 没控制：两个臂相隔约 2.5 小时，网关别名背后的上游无法确认没变；每臂 n=10；只有一个模型、英文、单步。结论只到「这个模型在这个协议下」。
- **类别漂移（观察到，未证实）**：隐藏后 3/10 被改存成 `instruction`（常驻规则，优先级 ≥ 10），对照 0/10；Fisher 双侧 p = 0.21，不显著。对质量是好是坏没有评估。
- 隐藏臂另有 S1–S4（偏好带 key、规则带触发、指令不带触发、第三方归属）各 5/5 通过预设检查，共 0 次带 `write_target`、0 次 schema 校验失败；该批 30 次请求合计 prompt 60,535 / completion 4,786 token。

## MEMORY-20261107-02 · 项目会话里 `bound` 与 `shared` 落在同一命名空间，默认策略仍向模型提供两个写入目标

**状态**：OPEN（P3，未修）。**发现**：2026-11-07 晚，落点核实时。**引入**：未追溯（没有二分）；只要项目绑定与 `shared` 选项同时存在就成立。**修复**：无。

### 症状

- [实测] 项目 p1 内的网页聊天，命名空间链 `project:p1, global, conversation:c-1`：`bound` 落 `project:p1`，`shared` 落 `project:p1`，允许与阻断两种策略下都一样。默认策略仍向模型展示 `write_target` 与「bound：仅当前 Agent 角色可见 / shared：跨 Agent 共享」。
- [推断，按链的构造，没跑检索] 项目命名空间在同一项目里每个 Agent 的读取链里，所以 `bound` 在项目里并非「仅当前 Agent 可见」。

### 根因 [代码]

`derive_binding_namespaces`（`myrm-agent-server/app/core/memory/adapters/policy.py:108`）在有 `project_id` 时把 `project:<id>` 放在链首，没有记忆策略时不放 Agent 命名空间；`resolve_primary_namespace`（`scope.py:211`）把 `project:` 排在最优先，`scope_for_write_target` 的 `shared` 在没有 `shared:*` 时取链首，也就是项目命名空间。工具表面是否提供 `write_target` 只由 `allow_shared_write` 决定，而它只看渠道名（`tool_setup/memory.py:92-96`），不看链。

### 影响

不报错、不丢数据；模型被告知有两个目标而实际只有一个，可能向用户承诺「所有 Agent 都会记住」，实际只在该项目内可见。项目会话的生产占比没有数据（没有读生产数据）。

### 为什么没修

项目写入落项目命名空间是代码里写明的设计（`policy.py` 项目分支的注释写着「Primary namespace is always project_ns for writes」，`resolve_primary_namespace` 的文档把 `project:*` 排在首位），项目会话的占比与这个选项的实际使用也没有数据。可选改法有两种：在 server 里遇到项目绑定时也把 `allow_shared_write` 置为 `False`（同一类按场景打补丁的做法）；或按文末的根治方向，由真实落点决定是否提供。没有实施，需要单独决定。

## 同类复发统计与根治反思

**复发**：「模型可见的工具表面（schema、描述）和运行时真实行为不一致」在 memory 工具上 3 天内出现 3 次：11-05 的 search corpus（`70b0fef2ae`）、11-07 的 save `write_target`（`305d5cee34`）、同日晚发现的项目会话（OPEN）。

**为什么反复**：每次修复都是把一个工具参数（或描述段）接到 `MemorySearchPolicy` 的某个字段上，而这些字段由 server 按场景赋值（本条是渠道名）；真实落点却由别处算出的命名空间链决定。任何这套场景判断没预料到的链形态（项目、隔间、收窄的写入策略）都会再造一个同类问题。

**根治方向（未实施，需单独批准）**：是否提供 `write_target` 由真实落点决定——工具构建时取 manager 的写入范围，仅当 `shared` 的落点与 `bound` 不同、且 server 策略允许共享写入时才提供；保留压回逻辑作最后防线。一次覆盖外部渠道、项目会话、隔间、收窄的写入策略。代价：`agent_surface` 需要一个只读的落点能力（manager 方法或作用于 `(scope, namespaces)` 的纯函数），测试要按「落点实测」那张表逐行覆盖。

1. 一个选项只在「存在某种运行状态下选它会改变结果」时才提供；写不出这样的状态就不提供。
