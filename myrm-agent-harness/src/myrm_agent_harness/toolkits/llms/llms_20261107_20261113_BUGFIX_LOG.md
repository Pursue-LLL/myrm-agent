### 症状

以下 ①–⑥ 为改前（litellm）就存在的问题，除注明外均为 [实测，本机，脚本不入库]。

- ① 响应缓存默认开启：真实 `ChatLiteLLM` 加生产配置打本地 OpenAI 兼容 mock，非流式与流式的相同输入连发 2 次，上游都只收到 1 次，两次返回同一份回答（有效期 1 小时；真实使用里是否可见取决于提示词是否带时间戳等变量，未量化）；缓存键不含密钥与端点，设置页的探测与健康检查因此会把填错的密钥报成正常；主干随后在 `fa5497369f` 自己去掉了这层缓存。
- ② 凭证串用：`ChatLiteLLM._client_params` 把聊天提供商的 `api_base`、`api_key`、`organization` 写进 litellm 模块全局，之后没有显式凭证的 litellm 调用都会带上它；模拟 `cloud_embedding.py` 的调用形态，mock 收到 `Authorization: Bearer <聊天密钥>`；触发条件是嵌入配置里 `api_key` 与 `api_base` 各自独立可选，只配了自定义地址而没配密钥（真实配置里出现的频率未知）。
- ③ [代码，改前的 `runtime/diagnostics/doctor.py` 第 236 行] LLM 连通探测写成 `_, _, api_base, _ = litellm.get_llm_provider(model=model)`，而该函数返回的顺序是 `(model, custom_llm_provider, dynamic_api_key, api_base)`，被当作 `api_base` 的是第三项 `dynamic_api_key`；[实测，环境里设 `GROQ_API_KEY`] `groq/llama3-8b-8192` 的第三项是环境里的密钥，探测地址于是成了密钥字符串；`openai/…` 返回 `None`，退回默认的 OpenAI 地址（其他厂商是否同样探错没有逐个查）。
- ④ [实测] 云端重排按位置回填分数：服务商按相关度降序返回时，4 个文档里 3 个分数配错。
- ⑤ [代码，未逐个查证有没有这样的调用路径] 全局配置（缓存、`drop_params`、`modify_params`）只在首次访问 `llm_manager` 时作为导入副作用生效，绕过它直接构造 `ChatLiteLLM` 的路径拿不到。
- ⑥ 运行代价：流式每请求 CPU 45.0 ms（每 chunk 149 µs）、20 并发时 48.4 ms、峰值 275 MB；首次创建聊天模型 1.70 s CPU、240 MB；`import app.main` 6.25 s CPU、509 MB、8,238 个模块。以下 ⑦、⑧ 不是改前就有，而是替换本身留下的缺口，由对旧栈（litellm 1.97.0）的故障注入、应答形状探针与失败判定回放发现。
- ⑦ 重试：第一版传输层只对「连接被拒」重试一次，其余瞬时故障都不重试；对旧栈做「第一次 503，之后正常」的单次故障注入，22 个 provider id 里，走 OpenAI SDK 处理器的 11 个自动再请求一次并成功，10 个一次就失败，custom_gateway 发不出请求（0 次，没有查是脚本写法还是旧栈的限制）；原生 Anthropic、Gemini、Ollama 线对 503、429、408 一律 1 次就失败；对一个一直不回话的提供商（请求上限 1.5 秒），旧栈 OpenAI SDK 路径发 3 次（非流式 7.9 秒、流式 5.8 秒），Anthropic、Ollama 路径发 1 次（1.5 秒）。所以「删 litellm 后行为不变」在重试上原先不成立：对那 11 个提供商，瞬时故障在旧栈里被悄悄吸收，在第一版新栈里变成用户可见的失败。
- ⑧ 应答与失败判定：litellm 校验并规范化服务商的应答（用量、结束原因、角色、`choices`、200 里的错误体、流里的帧），第一版把 JSON 原样交给适配器，而适配器与下游的账本、日志、聚合器都按 OpenAI 的形状读它。把第一版（`989c762c28`）放到全路径用例上，134 例里 83 例失败：用量计数写成文本抛 `TypeError`，`usage: null` 抛 `AttributeError`，别家的结束词（`end_turn`、`STOP`、`SAFETY` 等）原样记账让截断与安全拒答被当成正常结束，流里 `"error": null` 的块让整条流中断，200 里的错误体读成「没有 choices」或空回答，Responses 线上 OpenAI 文档里平铺的 `error` 事件被静默吞掉（半截回答当成功）。之后回放旧栈录制的 289 例（121 个应答读法、132 个错误应答、36 条流内失败），又补出三处：a) 若干上下文溢出措辞不被识别，超窗的请求被当成普通的请求被拒、直接终止运行而不是压缩后重试；b) 原生 Anthropic、Gemini、Ollama 线把「200 且是 JSON 对象却没有答案」读成空回答（设置里「测试本地模型」报告正常，智能体拿到空回答），旧栈对任何没有应答外壳的 body 都抛异常；c) 服务端按被删 SDK 的类名分类，传输层抛出的失败在日报与对话压缩的兜底分支里被报成通用内部错误。

### 根因

模型请求的翻译、重试、缓存、目录与计费都放在一个体量很大的第三方库里，它的全局可变状态（缓存、凭证、参数改写）对调用方不可见；本仓库只用到它的一小部分（OpenAI 兼容、Anthropic Messages、Gemini、Ollama 四种线协议加价格与窗口目录），却承担它的导入成本、供应链面与隐式行为。症状 ⑦ 与 ⑧ 同源：旧栈里由第三方库悄悄做的重试、校验、规范化与异常分类，替换时没有逐项接手，而最初的验证只比了请求，应答、故障与失败判定下的行为没有比过；⑧ c) 的另一半在服务端：它的异常分类按被删 SDK 的类名匹配，没有跟着换成传输层自己的类型。

### 修复了什么

- ① 新增 `toolkits/llms/transport/`（30 个文件、5,669 行，只依赖 `httpx`，不加载任何厂商 SDK）：六条线协议——OpenAI Chat（含 19 个兼容厂商，Azure 另占一行）、OpenAI Responses（`toolkits/llms/adapters/wire/routing.py` 的 `resolve_wire` 按模型选用）、Anthropic Messages、Gemini `generateContent`、Ollama `/api/chat`、Bedrock Converse（只认 Bedrock API 密钥，不做 SigV4，不加载 boto3）；厂商差异写成 `PROFILES` 数据表（24 行），凭证只存在于每次调用的路由里，没有任何全局状态；`httpx` 客户端按事件循环与出口代理共用，遵循代理与企业 TLS。
- ② 目录与分词表：`toolkits/llms/catalog/` 与 `data/model_catalog.json`（价格、窗口、能力，4,514 条）由 `scripts/sync_model_catalog.py` 按键并集从上游公开 JSON 同步（上游不再列出的模型保留，上游保留的键不到快照一半时拒绝写入）；自定义单价走 `register_model`，在快照条目上叠加（只填单价时窗口与能力保留）；查找不分大小写，`model_info` 对供应商严格（计价与路由用），`model_facts` 供窗口、视觉、推理等模型自身的事实查询（网关复合名逐段去前缀，价格永远不走这条宽松路径）；tiktoken 的离线 BPE 表随包携带（`utils/_tiktoken_tables/`）。
- ③ 嵌入、重排、图像、一次性文本补全（`toolkits/llms/text_completion.py` 的 `acomplete_text`）、REST 搜索、`security.generate`、评测、`doctor`、TTS 摘要全部迁到传输层或目录；litellm 自定义 provider（`providers/minimax_image.py`、`providers/yunshu.py`）与 `wire/native_anthropic.py` 删除；`ChatLiteLLM` 改名 `TransportChatModel`，`create_litellm_model` 改名 `create_chat_model`，前端与生成脚本的 `litellm*` 命名同步改掉；顺带修的小缺陷各有测试（嵌入重试的判定条件、图像「绕过网关」重试吞掉一次重试额度、Anthropic 的 `user` 写入 `metadata.user_id`、`inline_refs` 留下 `$defs`、`get_model_context_limit` 对非字符串入参不设防）。
- ④ 依赖：`pyproject.toml` 与 `uv.lock` 里删除 litellm（harness 锁 237 → 221 个包：litellm 与它独占的 15 个；server 锁 276 → 270 个包：litellm 与独占的 5 个；`python-dotenv` 作为测试依赖显式声明回来；`openai` 只留在 dev 组，测试读真实 SDK 的异常形状，运行时依赖里没有它）；`tests/architecture/test_core_dependencies.py` 用 AST 扫描导入并检查 pyproject 与锁文件，litellm 不会回流。
- ⑤ 重试（`transport/retry.py`）：只在服务商还没有产出任何内容之前重试，最多 2 次；可重试的是状态 408、409、429 与所有 5xx（`x-should-retry` 为 `true` 或 `false` 时以它为准）、`ConnectTimeout`、`PoolTimeout`、`NetworkError`、`RemoteProtocolError`；等待从 0.5 秒起每次翻倍、封顶 8 秒、再乘 0.75 到 1 的抖动，服务商给的 `Retry-After`（秒数、小数或 HTTP 日期）与 `retry-after-ms` 在不超过 8 秒时照办。不重试的：`ReadTimeout`、`WriteTimeout`（服务商在整个请求上限内一直没出声，再问只会把等待放大 3 倍）；超过 8 秒的 `Retry-After`（长边界是配额窗口或故障，睡在调用里会瞒住密钥轮换、故障转移与用户，立即原样抛出）；已经开始的流（同步与异步都不重放）。连接被拒与连接超时（请求没有到达服务商）在 `retries=0` 的调用上也重试一次。各条聊天线都带 `DEFAULT_RETRIES`；嵌入、重排、图像、搜索在传输层 `retries=0`（嵌入的重试在 `CloudEmbedding`：可重试集合同上，`Retry-After` 在不超过 60 秒时作等待下限；图像在 `toolkits/llms/image/generator.py`）。
- ⑥ 应答整形与失败的类型（`transport/chat_shape.py`、`frames.py`、`errors.py`）：门面（同步与异步、非流式与流式）把每条聊天线的应答与流块过一遍——用量计数转成非负整数（文本、小数、null、负数都能读，缺总数时补成前两项之和），结束词映射到 OpenAI 的五个（litellm 1.97.0 的 36 个词逐词相同，另加 `model_context_window_exceeded`），带工具调用却写 `stop` 的非流式应答记为 `tool_calls`，缺 `role`、分段数组内容、`choices: null`、`delta: null` 按规则读；不以 `{` 开头的流帧（keep-alive 文本、`[PING]`）跳过，以 `{` 开头却解析不了的帧抛 `LLMResponseError`。传输层抛出的每个模型调用失败都派生自 `LLMCallError`（带 `llm_provider` 与 `status_code`）：`LLMHTTPError`（非 2xx，带状态）、`LLMAnswerError`（流内 error 事件与 200 里的错误体；状态取事件自带的，其次取错误类别对应的，流内都没有时 500，200 里的错误体都没有名字时保持未知 `None`，避免重试服务商可能已拒绝的请求）、`LLMResponseError`（2xx 却读不出答案，状态 502；不是 `ValueError`：路由把 `ValueError` 答成「输入无效」，而服务商读不出的应答不是调用方的输入）。服务端的 `app/core/utils/errors/` 按 `LLMCallError` 与 `httpx` 超时分类（`classify_model_failure`，经 harness 的失败分类器映射到 AI 错误码，服务商原话只进日志），日报与对话压缩的兜底分支因此报 AI 错误而不是通用内部错误。
- ⑦ 失败分类与溢出识别（`toolkits/llms/errors/classifier.py`、`classifier_patterns.py`、`output_limit.py`）：408 归 `TIMEOUT`，流内 error 事件按状态分类；补上旧栈错误映射认得而分类器漏掉的上下文溢出措辞（Gemini 的 token 计数句、Cerebras 的 current/limit 长度、TGI 的 inputs + max_new_tokens、`longer than the model's context length`、`maximum input length is N tokens`、`maximum context limit`、Cohere 的 `too many tokens`；这些措辞不带错误码）；认得 Vertex / Gemini 的 `maxOutputTokens` 越界句式（上限取 M−1，只认这一个字段，温度与 topK 越界用同样的句式，有负例）与 Bedrock 的措辞；诊断卡（`agent/errors/diagnostics/engine.py`）先看分类器、再看关键词族（`_diagnose_outranking`：WAF 的 403 不再读成密钥被拒，订阅档位的 429 不再读成限流），展示给用户的服务商原话（`provider_words.py`）认传输层自己的 `<供应商> API error NNN:`、`stream error:`、`answer error:` 前缀与新版 OpenAI SDK 只剩 `Error code: NNN` 的文本，不再把 `{'code': 1027, 'msg': …}` 这类数据当话展示（关键词族读什么文字见 ⑳）；未知服务商（`UnsupportedProviderError`）归为「请求被拒」，`httpx` 传输错误归为连接类。

- ⑩ `mypy` 不在 CI 与 pre-commit 门禁里（只有 `pyproject.toml` 的配置）：传输层在严格配置下没有错误，`toolkits/llms` 里 37 个既有错误分布在 9 个文件，每个文件的错误数与改前相同，没有动；`tests/toolkits/llms/test_error_classifier.py` 在改动之前就有 850 行（现 866 行），没有拆分。真实模型端到端用例（`tests/e2e/test_real_artifacts_e2e.py`、`tests/api/agent/test_general_agent_stream_e2e.py`、`tests/api/agent/utils.py`）的「环境问题则跳过」关键词里还留着旧库的异常类名（`APIConnectionError`、`RateLimitError` 等），新栈的失败文本由 `_TRANSPORT_ENV_SIGNALS` 的 `API error NNN` 覆盖；没有清理，也没有逐个核对这些词在新栈上还能匹配到什么。
- ⑪ 整套测试里仍有与本条无关、在主干上同样失败的用例（缺可选依赖 `discord`、`lark-oapi`，主干拆分模块后过时的断言、补丁目标与架构索引，依赖目录布局，用时断言，真实模型用例遇到额度用尽）：它们没有处理，也不该由这条替换去处理，改它们会与主干作者的修复相撞；这一轮整套结果与逐项归属见回归；主干几乎每天都有新提交，推送前要再合并一次并重跑与改动重叠的部分。
- ⑫ 整套服务端测试里仍有三个活测试会改写本机共享开发后端的配置（踩坑 ⑪），在开发机上跑整套之前要先把那三个环境变量指到关闭的端口。
- ⑬ WebUI 里操作时发现 4 处改前就存在、与本条无关、没有处理：a) 嵌入与重排设置的「应用」请求 `/api/v1/retrieval/embedding`（`/reranker`），server 没有这条路由，界面报「Requested resource not found」；b) 搜索服务设置里「搜索类型」下拉全部禁用：后端 `SearchProviderResponse` 序列化出 snake_case（`backend_ready`、`name_zh`），前端读 camelCase（`backendReady`、`nameZh`）；c) 新手引导的 AI 引擎向导在 1080p 屏幕上顶部被裁；d) Next 开发模式下有 hydration 报错浮层。
- ⑭ 本分支仍是本地分支，没有推送，也没有合并到 `main`；外层私有仓库里的文档、官网文案与维护脚本仍提到 litellm，未改动（跟进补丁只是文件，没有应用）。

### 踩坑

- ① 最初的验证只比了请求（黄金基线），应答、故障与失败判定下的行为没有比过：重试缺口与应答形状缺口（症状 ⑦、⑧）是用故障服务器与应答变体探针才发现，上下文溢出措辞、「200 却没有答案」与服务端分类缺口是回放旧栈录制的 289 例才发现；「功能都正常」的端到端验证都没有照到它们。
- ② 夹具来自自己的假设时，测试只会证明自己的假设：Responses 夹具把错误事件假设成嵌在 `error` 里，漏掉了 OpenAI 文档里平铺的 `error` 事件，第一版因此对它静默收尾、把半截回答当成功；应答侧第一轮探针只比了内容与异常、没有读记账器里的结束原因与用量，所以 `end_turn`、`SAFETY` 被记进账都显示「两栈一致」。
- ③ 对旧栈的基线必须取生产用的库版本：服务端锁 litellm 1.97.0（产品实际运行的），harness 锁 1.106.0，行为不同。这个错误犯了不止一次：地址基线最初在 harness 的环境里录、标成 1.97.0，用 `importlib.metadata` 与 `uv.lock` 核出来后重录；失败判定与应答读法的 289 例最初录自 1.106.0，用同一语料在 1.97.0 上重录后，132 个错误应答里 4 个读法不同（3 个 Ollama 错误旧栈一律读成连接失败，1 个 Moonshot 策略拒绝读成 `FORMAT_ERROR`），36 条流与 121 个应答相同，基线已改按 1.97.0 登记；探针还要带生产设置（`drop_params`、`modify_params`、关遥测、先访问 `llm_manager`），没带时得出过「旧栈什么也没发」的假结论。
- ④ 目录整体换成最新上游，旧目录的 364 条没了，原先的快照下限断言 `> 1000` 照样通过；现在下限 4,500，并钉住 5 个上游已不列出、供应商仍在服务的模型（`claude-opus-4-1`、`claude-3-haiku-20240307`、`command-r-plus`、`chatgpt-4o-latest`、`gpt-4-turbo-preview`）。
- ⑤ 验证工具自己也要先验证：变异检验脚本在 zsh 里把未加引号的变量当成一个超长路径，没有跑任何用例却全部报「被抓住」；后台被杀时把源码留在被改过的状态，随后的判定全部无效；清单驱动的复跑脚本在 `cd` 之后才用相对路径读清单，0 秒退出码 0、一个用例也没跑。之后变异检验只用单实例、直接以后台方式启动、结束后校验每个文件的改前改后出现次数，运行是否真的发生以通过与失败的用例数判断，不以退出码判断。
- ⑥ 整套并行跑出的「只在新栈失败」不能直接当回归：同一个 xdist 工作进程上一批用例报 `no such table`（共享库状态被前面的用例清掉），两栈各单独运行全部通过；判定规则必须是「只在一栈失败的 id 单独复跑」，且两侧环境、命令一致（CI 式环境与装满可选依赖的环境对比，曾得到 24 个假回归）；按「改动影响面」选测试会漏掉 harness 源码的改动，而这次替换最大的改动恰恰在 harness 的传输层。
- ⑦ `Retry-After` 的第二版尊重任意长的值，带 `Retry-After: 42` 的用例真的睡了 84 秒，暴露的是设计问题（长边界是配额窗口），不是测试问题，所以改成超过 8 秒立即抛出，没有给测试打补丁；第二版还对读超时重试，挂住的调用从旧栈的 1 次、1.5 秒变成 3 次、5.8 秒，是自己引入的回退，重测才发现。
- ⑧ 黄金对照与类级对照不经过的层会悄悄变：`CloudReranker.rerank` 曾被改成「按分数排序并截到 `top_k`」，旧代码原样返回服务商的应答，是主干新加的测试才让它红，随后还原并补了类级两栈对照（286 个场景）。
- ⑨ 用 `import app.main` 守住「默认路径不加载 litellm」时，传输层包的 `__init__` 急切导入 `client`，守卫先红；包改成按名懒加载（PEP 562），守卫改为 `litellm`、`openai`、`anthropic`、`boto3`、`google.genai`、`tiktoken`、`tokenizers` 都不在 `sys.modules`。
- ⑩ 给黄金基线补录新用例时，第一次没设 `LITELLM_LOCAL_MODEL_COST_MAP=True`（生产服务端在导入 litellm 前设置它）：价格表是空的，录出的 xAI 走 chat completions 而不是 Responses、Moonshot 与 MiniMax 的字段也不同，差点把这些假差异登记进白名单；录制脚本现在断言该环境变量已设且价格表非空。
- ⑪ 整套服务端测试里有几个活测试会读写本机的共享开发后端（默认 `127.0.0.1:28080`），而且只带 `integration` 标记，默认的 `-m 'not e2e and not chrome_e2e and not performance'` 筛不掉它们，后端在线就真的去连：`test_search_priority_chain_persists_via_omni_config_api` 用占位条目 PUT 再写回 `searchServices`，`test_live_mcp_config_put_get_roundtrip` 用只含探测条目的列表整体替换 `mcpServers`。发现之后，复跑脚本都把 `E2E_API_BASE`、`MYRM_SHARED_BACKEND_PORT`、`MYRM_SHARED_FRONTEND_PORT` 指到一个关闭的回环端口；本分支没有改这几个用例。
- ⑫ 主干提交很频繁，本分支合并过多次，条目编号与 `BUGFIX_LOG.md` 开头、`file_line_baseline.txt`、`_ARCH.md` 反复冲突；合并后要重跑与改动重叠的部分，别沿用旧结果；合并时没有文本冲突的接缝也会出错（主干新增的 TTS 摘要仍调 litellm、被主干删掉的探测 helper 的文件头仍写着 `litellm::model_cost`、主干为拆分后的包重新生成的文件头仍列着旧库的导入）；主干把一个文件拆成包而本分支改过它时，是「修改与删除」冲突，要把改动逐段搬进新的模块，不能只取一边。
- ⑬ 对「主干纯净导出树」的服务端复跑，主干 server 虚拟环境里的 harness 是 `.pth` 编辑安装，它在解释器启动时把主检出目录的 harness 插到 `sys.path` 最前，`PYTHONPATH` 压不过它：复跑的其实是「导出的 server 加正在被别人改的主检出 harness」，两者在 `src` 下有 111 处差异（含模块拆分与新文件）。整套归属之前对主干做的服务端切片复跑都在这个环境里，结果不作为依据；之后在进程里先把导出树的 harness 提到最前再启动 pytest，并打印 `myrm_agent_harness.__file__` 核对。harness 工程自己的虚拟环境没有这个问题（`.pth` 只追加路径，`PYTHONPATH` 生效，已核对）。
- ⑭ 按名称检索 litellm 类名找不到的耦合：服务端有三处分类器不引用类名常量，而是用 `type(exc).__name__.lower()` 加子串判断（`shared_context_health._classify_probe_failure`、`diagnostics._classify_local_model_error`、`turn_capability_terminal.classify_turn_capability_failure_reason`），审计只搜了带引号的类名，漏掉了它们；前两处是在两栈上真实触发故障（拒绝连接、多种措辞的 401）才发现，第三处是把全仓读异常类名与文字的地方逐个核对时才发现。之后的做法：审计分类器靠真实故障穿过两栈，不靠搜名字；三处现在用服务商状态与传输层的 `httpx` 错误类型分类，并用真实的故障应答与关闭的端口写成测试（各自的变异检验全部被抓住）。全仓 `__name__.lower()` 加子串的判断共 8 处，3 处与模型调用有关（就是上面三处），5 处无关（`storage_resilience`、Telegram 的 `inbound_poll`、`dropped_manifest`、`advisor_risk_trigger_router`、统计的用量校验）；按类名集合比较的两处（后台任务 `worker._PERMANENT_ERROR_TYPES`、视频 `_NON_RETRYABLE_NAMES`）收到的是图像生成器与视频提供商自己的异常，不是传输层的；按文字读异常的分类器（熔断、流恢复、摘要处理器、鉴权检测、请求体积判断）读的是状态数字与提供商原话，新栈的异常文字 `<提供商> API error <状态>: <应答体>` 保留了这两样，对照里与旧栈一致或只有已解释的差异（回归 [13]）；用户看到的错误卡不在这 11 个里，它读同一段文字时把状态数字与 JSON 字段名当成了服务商的话（见 ⑮）。
- ⑮ 11 个分类器的两栈对照（回归 [13]）没有覆盖用户最终看到的错误卡（`LLMErrorDiagnostic`）与服务端的 `handle_llm_exception`：它们读同一段异常文字，读法却不同。分类器读状态与原话，诊断引擎的状态数字正则与关键词族把传输层加的框架（`openai API error 429:`）与 JSON 字段（`"code": 404`）当成服务商的话；这是测量衰减：衡量的是「某个分类器的结论有没有变」，不是「用户看到的那张卡有没有变」。把诊断引擎的输入输出整条放到两栈上逐例对照才发现：229 例里，修前（提交 `a5086ad39e`）卡的类型与旧栈相同的 197 例、不同的 32 例，其中 12 例是读错的卡（5 个 404 被读成「模型不存在」、4 个 504 被读成「过载」、智谱欠费的 429 被读成「限流」、403 的限流话被读成「密钥被拒」、kind 字段里的 `timeout_error` 被读成「超时」）；修后 206 例相同、23 例不同，全部有解释（行为变化 ⑯），其中 3 例是这次修复带来的：Gemini 的 504、Anthropic 在 500 下写 `timeout_error`、Gemini 的 404 原话不含模型字样。对照脚本自己也出过错：它把服务端业务码的差异记成「只差引用文字」（对没有 `type` 与 `steps` 字段的字典，这个判断恒成立），按 `code` 与 `http` 逐字段重算后，业务码在 22 例上真的不同，全部落在已登记的分类差异里。之后的做法：对照的单位是用户或下游真正读到的最终结果（卡的类型与步骤、业务码与 HTTP 状态），不是中间的分类器；修复后又用 18 个「原因只写在 kind、code 字段里」的应答补扫一轮，查出 4 个差异，已登记进黄金契约。
- ⑯ 归属比对要保证两侧环境逐项相同，并先排除测试基础设施自己的干扰：主干导出树里没有 `.env.test`（服务端测试从 `_SERVER_ROOT/.env.test` 读测试密钥，导出树不带这个文件），搜索链的用例（`test_no_chain_hop_when_primary_succeeds`）两栈因此给出不同的原因，补上同一份文件后两栈一致；整套并行跑里 `tests/remote_access` 的 4 个身份与配对用例失败来自执行顺序：`tests/middleware/test_ws_auth.py` 把 `get_deployment_capabilities()`（`lru_cache(maxsize=1)`）留在沙箱模式，之后的用例读到 `'sandbox'`，用同一对文件在纯净主干上逐字复现，单进程按收集顺序跑整块两栈全部通过（主干 674 个、新栈 678 个，多出的 4 个是本分支的 `tests/server/test_shutdown_model_transport.py`）；`test_intelligent_agent_subagent_notification_no_injection` 撞到 150 秒上限之后，`TestClient` 退出时一直等遗留的 portal 任务（`tests/api/agent/conftest.py`），整批卡住 28 分钟，两栈一样，上限放宽到 600 秒时两栈都通过。三处都是主干测试基础设施的问题，本分支没有改相关文件；之后的做法：归属复跑固定两侧的 `.env.test`、聊天模型端点与超时，先单进程按收集顺序复现，再判定是栈的差异还是执行顺序的差异。

- ⑧ Bedrock 与旧栈的差异：传输层对 429、5xx、408 重试 2 次，旧栈只发 1 个请求；缺 `usage` 的非流式应答记零用量（旧栈抛异常）；流式的无参数工具调用保留为 `{}`；工具调用保留 Bedrock 给的 `toolUseId`；输出上限被拒时按服务商自报的上限重发一次（旧栈对已知模型预先夹紧 `max_tokens`，新栈靠这次恢复）；随包目录与测试固定目录在 Nova Pro 上不同，Mistral 在设了推理强度时旧栈不强制结构化输出工具、新栈照常强制（`golden_bedrock_allowed.py` 登记）。
- ⑨ 非聊天路径：Brave、Google PSE、SearXNG 的密钥被拒（401）改前被吞成空结果，现在抛出，其余搜索厂商改前把一切失败包成 500、现在保留服务商的真实状态码；嵌入向量按应答里的 `index` 排序，向量数与输入数不符抛 `ValueError`；重排的应答没有结果列表、或 `index` 为负、越界、缺失时抛 `ValueError`（旧栈有的返回空列表，有的把 `-1` 当最后一个文档）；Ollama 嵌入走 OpenAI 形状的 `/v1/embeddings`；Cohere 重排给了自定义地址时改前拼出 `…/v1/v2/rerank`，Together 重排改前无视自定义地址，现在都用配置的地址；Gemini 图像不再发默认的 `imageSize: 1K`，MiniMax 图像现在发送 `n`（改前该值在 litellm 里丢了），Azure 嵌入的 API 版本由 `2025-02-01-preview` 改为稳定版 `2024-10-21`；设置里的 `flux/schnell`、`flux/pro` 改前每次都以「LLM Provider NOT provided」失败，现在映射到 Together 的 FLUX；`CloudReranker.rerank` 仍照服务商的应答原样返回（顺序与条数不动）。
- ⑩ 凭证与端点：嵌入、重排、图像不再从环境变量取凭证（旧栈会把环境里的聊天密钥发给用户为图像另配的端点；产品里嵌入与重排的工厂本来就要求配置带密钥，只有「图像模型没填密钥、环境里却有该渠道密钥」的部署受影响）；聊天仍和旧栈一样，没给密钥时读渠道的密钥变量；多认 6 个端点变量（Azure 嵌入与图像的 `AZURE_OPENAI_ENDPOINT`、Cohere 嵌入的 `COHERE_API_BASE`、Voyage 嵌入的 `VOYAGE_API_BASE`、Together 重排的 `TOGETHER_AI_API_BASE`、OpenAI 图像的 `OPENAI_API_BASE`）；litellm 独有的环境变量不再读（`ANTHROPIC_AUTH_TOKEN`、`TOGETHER_AI_TOKEN`、`SSL_VERIFY`、`SSL_SECURITY_LEVEL`、`SSL_ECDH_CURVE`；企业网络走 `MYRM_TLS_STRICT` 与 `SSL_CERT_FILE`）；基址写法各异时（已带操作后缀、尾斜杠、`/v1` 结尾）落到用户写的地址，旧栈会拼出 `/v1/v1/messages`、`//v1/messages` 一类路径。
- ⑪ 目录：按供应商严格查找，网关转发的 id 在目录里没有对应条目时返回「未找到」，不再被宽松匹配出一份看似完整的能力信息（实测 `antigravity/claude-opus-4-6-thinking` 改前得到窗口 20 万、单价 0.0）；模型切换预检不再把目录里的 `max_tokens` 当上下文窗口回退（旧数据 2,981 条里只有 6 条没有 `max_input_tokens` 而有 `max_tokens`，新目录 4,514 条里 1 条）。
- ⑫ 模型配置里的 `top_p`、`top_k` 现在到达 Gemini、Ollama、Responses 与 Anthropic（旧栈只对 OpenAI 形状的请求体生效）；Anthropic 请求带温度时不发 `top_p`，所以实际多发的只有 `top_k`；Gemini 2.5 Pro 关闭思考发 `thinkingBudget: 128`（旧栈 0），`xhigh` 档位改前被丢掉、现在 Gemini 3 起发 `thinkingLevel: high`、2.5 发预算 8192；Gemini 3 之前「函数声明加 JSON 输出」丢掉 JSON 约束；2.5 Flash-Lite 与 3 Flash 的输出上限随更新的目录由 65535 变成 65536。
- ⑬ 生命周期：运行中切换企业 TLS 开关，下一次模型请求就按新设置新建客户端（旧栈只在打开时丢弃 litellm 缓存的 SSL 上下文，关闭时不重建任何客户端，`tls_config.py` 的文档写明完全生效要重启）；服务端关闭时多一步：最多等 2 秒关闭传输层的共享客户端。
- ⑭ 服务端按故障措辞分类的三处：设置里「测试本地模型」对拒绝连接的 Ollama，旧栈显示「SSL/TLS error — check your server's certificate」（litellm 的异常文本带 `ssl:<ssl.`），对拒绝连接的 OpenAI 兼容服务与不存在的模型（404）都显示「Connection test failed」；新栈依次是「Could not connect — is the model server running?」、同一句、「Model not found — check the model name」，macOS 与 Linux 解析器报告主机名不存在的措辞（`nodename nor servname`、`Name or service not known`）归为 DNS 失败（以上在两栈上用真实故障逐条实测）。共享上下文的嵌入探测改按服务商的状态判定（401 → `invalid_api_key`、402 → `insufficient_quota`、408 → `timeout`），措辞只用于状态说不清的情形（429 是限流还是额度、连接中断）；旧栈靠 litellm 的类名 `AuthenticationError` 识别拒绝，新栈的异常文本若不含固定措辞（例如「invalid subscription key」「invalid api token」），401 会被读成可重试的通用失败。回合遥测的失败原因（`app/services/agent/stream_session/turn_capability_terminal.py`）原先读异常类名与消息里的 http、server、status 字样；新栈的 `LLMHTTPError` 名字里有 http，每个服务商状态都会被记成 server_error（在本机故障服务器上实测，400、401、403、404、429、500、502、503 全是）。现在按服务商的状态与传输层的 `httpx` 错误类型分类：5xx 记 server_error，408、504 与断开的连接记 network_error，其余状态记 unknown_error；与旧栈对照，400、401、403、404、429、500 与拒绝连接一致，502 与 503 旧栈记 unknown_error（litellm 的类名 `BadGatewayError`、`ServiceUnavailableError` 里没有 server 字样），新栈记 server_error。全部 11 个按类名、文字或状态分类的分类器在两栈上的对照（154 格里 19 格不同，逐格归类）见回归 [13]。
- ⑮ 回合出错事件与统计里的 `error_type` 由 litellm 的类名（`RateLimitError`、`AuthenticationError`、`InternalServerError`、`Timeout`、`APIError` 等）变为 `LLMHTTPError`、`LLMAnswerError`、`LLMResponseError` 与 `httpx` 的错误类，状态码在异常的 `status_code` 上；前端只在 `AgentBusyError`、`provider_not_configured`、`interrupted` 三个值上分支，其余只展示。
- ⑯ 用户看到的错误卡与服务端业务码（脚本不入库；229 个失败：黄金基线里的错误体与流、竞品的错误体、只有状态的应答、原因只写在 kind 与 code 字段里的应答；旧栈为主干 `5a9990bb39` 加 litellm 1.97.0，新栈为本分支，卡取 `LLMErrorDiagnostic.diagnose` 的英文、中文与带自定义本地端点三种）：204 例两栈给出逐字相同的卡（类型、文字与步骤），25 例不同（卡的类型不同 23 例，类型相同、只有文字不同 2 例）。其中 20 例登记在黄金失败契约里：6 个空流改为抛 `EmptyStreamError`；Anthropic 流内的 `authentication_error` 由「过载」变「密钥」；OpenAI 流内的 `server_error` 由「超时」变「过载」；Ollama 的 400、500 由「超时」变按状态给卡；Moonshot 的策略拒绝由「请求格式」变「安全拦截」；503 容量不足由「限流」变「过载」；Gemini 的 504 由「过载」变「超时」；Anthropic 空体的 404 由「未知」变「模型」；Anthropic 在 500 下写 `timeout_error` 由「超时」变「过载」（`timeout_error` 随 504 到来时仍是超时卡）；Gemini 的 404 原话不含模型字样时由「模型」变「未知」（卡里引用服务商的原话，不再猜）；OpenAI 形状的 400 在 code 写 `unauthorized`、type 写 `billing_error` 时由「请求格式」变「密钥」「账单」。另有 5 例不在契约里：3 个空体的 Ollama 应答（旧栈一律读成连接失败，新栈按状态给卡，与上面 Ollama 的两条同理）；`422_validation` 与 `s400_empty_text`（卡的类型相同，文字不同：旧栈引用 litellm 的类名 `BadRequestError` 与文字 `Error code: 400`，新栈在服务商没有原话时给通用的「请求无法处理」卡与 `LLMHTTPError`）。同一批失败经服务端 `handle_llm_exception` 得到的业务码与 HTTP 状态，207 例相同、22 例不同，都是上面分类差异在服务端映射上的体现：6 个 Ollama 应答与 2 个 `server_error` 流事件旧栈给 `AI_TIMEOUT_ERROR`（504），新栈给 `AI_MODEL_ERROR`（502）或 `AI_RATE_LIMIT_ERROR`（429）；Anthropic 流内的 `authentication_error` 由 `AI_MODEL_ERROR` 变 `AI_AUTH_ERROR`；503 容量不足由 `AI_RATE_LIMIT_ERROR` 变 `AI_MODEL_ERROR`；Anthropic 的 504 由 `AI_TIMEOUT_ERROR` 变 `AI_MODEL_ERROR`（诊断卡仍是超时）；400 下的 `billing_error`、`unauthorized` 由 `AI_MODEL_ERROR` 变 `AI_RATE_LIMIT_ERROR`、`AI_AUTH_ERROR`；6 个空流由「没有异常」变 `AI_MODEL_ERROR`；Bedrock 式的上下文溢出与 Moonshot 的策略拒绝只变原因文字。
