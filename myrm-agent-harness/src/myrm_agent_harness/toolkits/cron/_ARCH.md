# cron/

## Overview
Cron toolkit entry point. Aggregates scheduling engine, CRUD manager, protocols, built-in
stores, triggers, delivery, runners, and situation report aggregator. **Single SSOT for
user-facing automation** (time-based schedules plus **five wired** event triggers:
event / system_event / webhook / poll / stream via `triggers.py`; `manual` is the trigger
source of a manual run (`CronManager.run_now`), not a `TriggerConfig` rule. Product wiring in
`myrm-agent-server/app/core/cron/`). Supports `skip_if_active`
concurrency control, `PreFlightCondition` script injection (probe interceptor), `context_from`
cross-task data piping (inject referenced jobs' latest successful output), incremental monitoring
(`MonitorConfig` — set/hash change detection via `infra.incremental`), and
`SituationReportBuilder` for enriching heartbeat prompts with dynamic context from registered data sources.

The heartbeat is found by its exact name through a name-filtered listing that includes system jobs (the default listing hides them, and a page of the newest jobs can leave the oldest one out) and is created as a system job (`system=True`) (`tests/toolkits/cron/test_cron_system_jobs.py`). | ✅ |
| job_listing.py | Core | One-line job summary for the `cron_manage` list action: state, schedule (recurring jobs only), next run, and the last run's time and status; when that run failed (`error` / `circuit_break`) the reason follows, redacted with `redact_sensitive_text` over a bounded prefix, then cut to 120 characters on a single line. A skipped run never shows the older error. The line is tool-result text only: it never enters the `cron_manage` name, description or schema, which form the prompt-cache prefix. | ✅ |
| manager.py | Core | Cron CRUD orchestration layer. Validates job configurations, persists changes via CronStore and notifies CronScheduler; reads (`CronQueryMixin`), updates (`CronUpdateMixin`) and field validation (`CronValidationMixin`) are mixed in. `create_job` accepts every user-set field, including `skip_if_active` and `acceptance_criteria`, and books the first slot with `_book_slot`; `system` marks a job the application creates itself (the heartbeat), which takes a reserved name (`__` prefix) while no other job does: a user job under a reserved name and a system job under a visible one are both refused (`CronValidationMixin._validate_name`), and `duplicate_job` refuses a system job, whose copy would be a user job under a reserved name (`tests/toolkits/cron/test_cron_system_jobs.py`). `resume_job` hands a job that is not enabled to `update_job` as a status patch to active (the one activation path) and returns an enabled job as it is, without a write or a notification. `duplicate_job` copies every `CronJob` field with `dataclasses.replace` except the identity, the webhook credentials and the run state (the failure count and last error, the pause reason included): a new configuration field is copied automatically, a new run-state field must be added to its reset list (`tests/toolkits/cron/test_cron_job_config_fields.py` makes every field either creatable or classified, and pins the exceptions). `run_now` starts a manual trial run of an active job that is not already running and answers a `RunNowOutcome`; the run books nothing and counts no fire (`tests/toolkits/cron/test_cron_manual_run.py`). | ✅ |
| manager_port.py | Core | `CronManagerPort`: structural contract of the eight job operations the `cron_manage` tool and the heartbeat call (`create_job`, `update_job`, `list_jobs`, `get_job`, `delete_job`, `pause_job`, `resume_job`, `run_now`), listing only the options they pass (`create_job` lists `system` and `list_jobs` lists `include_system`, which the heartbeat passes). `CronManager` satisfies it, and so does an application wrapper that holds a manager instead of inheriting from one, so such a wrapper goes into `create_cron_tools` and the heartbeat functions without a cast. A rejected mutation raises `ValueError` with the reason. | ✅ |
| manager_queries.py | Core | `CronQueryMixin` mixed into `CronManager`: `list_jobs` / `count_jobs` (name, chat and project filters; the user's jobs unless `include_system` asks for the application's own, which the store lists by default), `get_job`, `list_runs` / `count_runs` and the incremental-monitor state reads `get_monitor_state` / `batch_get_monitor_states`. Run records outlive a deleted job (a one-shot job is deleted after it ran) but are not served by its id: a run query for the id of a missing job returns nothing. | ✅ |
| manager_update.py | Core | `CronUpdateMixin` mixed into `CronManager`: `update_job` applies a `CronJobPatch` to every user-set field, including `skip_if_active` and `acceptance_criteria`; no patch field carries run state, which a run writes as it starts and closes (the fire count, last run, failure count, last error and the rest), so a caller cannot set any of it (`tests/toolkits/cron/test_cron_job_config_fields.py`); a rename goes through `_validate_rename` first. It validates the content rule on the record the patch would produce before it changes the stored job, then the schedule and `context_from`, and applies every field before the slot is decided. A status patch to active on a job that is not enabled is the one activation path (`_activate`, also behind `resume_job`): the resume preconditions are checked on the job as the patch leaves it, the failure story restarts (failure count, last error and the scheduler's pause reason) and the next slot is booked from now (`_book_slot`). Any other status patch is a person's own decision and drops the pause reason (`tests/toolkits/cron/test_cron_activation.py`). An enabled job whose schedule, active window or cooldown changes books its slot again; a paused job keeps none, so a paused job's edit is judged at its resume. The job is then saved and the scheduler re-armed (`notify_change`). A changed command, prompt or monitor type on an enabled monitor resets its baseline (`_reset_baseline_on_change`); a failed reset is logged and does not fail the update. | ✅ |
| manager_validation.py | Core | Cron job validation and normalization helpers. `_validate_job_content` is the one required-content rule for create and update: a shell job needs a command, a router job a prompt or a pre-condition script (it passes its input straight through), every other type a prompt. `_validate_update_content` applies it to the record an update would produce, only when the patch touches prompt, command or the pre-condition script (`tests/toolkits/cron/test_cron_job_content_rule.py`). `_validate_schedule` rejects an invalid cron expression, an unknown timezone and a one-shot whose time has passed; `_validate_resume_preconditions` rejects a completed, expired, exhausted or passed-one-shot job (`tests/toolkits/cron/test_cron_activation.py`). `_book_slot` is the one booking a user's input makes (create, edit, resume): `next_eligible_run`, and a refusal when a recurring schedule has no run inside its job's active window (the slot scan ended on a slot outside it, at least a day ahead; a one-shot is exempt, and a schedule that fires every few seconds is not refused because its scan runs out within hours) (`tests/toolkits/cron/test_cron_unreachable_window.py`). `_validate_name` keeps the reserved names for system jobs in both directions (a reserved name needs `system=True`, and `system=True` needs a reserved name, so the flag cannot take a visible job past the plan quota, which counts only the user's jobs) and `_validate_rename` refuses a rename into or out of them (`tests/toolkits/cron/test_cron_system_jobs.py`). | ✅ |
| protocols.py | Core | Protocols for the cron toolkit. `PreFlightCondition.evaluate` returns `(False, …)` to skip a run and raises `PreFlightConditionError` when it cannot decide (script crashed, timed out, could not start), which fails the run. `CronNoticeCallback` is the async `(CronNotice) -> None` hook through which the engine reports a run's outcome and an automatic pause; the application layer owns severity, wording and language. `CronStore` carries the in-flight run markers beside the job and run records: `mark_running` writes the job's marker (or overwrites it with the current time), `clear_running` removes it and `list_running` lists the markers oldest first. A marker belongs to the run, not to the job row, and it stays when the process dies under its run, which is how the next start learns of that run. A `ConcurrencyLock` must not pass to another process while its holder is alive, because the start reads every marker as the trace of a dead process. The `status` filter of `CronStore.list_runs` / `count_runs` means what `run_status_filter.matching_run_statuses` says: a filter on `error` selects circuit breaks too. `CronStore.list_jobs` / `count_jobs` list every job by default and leave out the reserved names (`is_system_job_name`) when `include_system=False`: the scheduler, startup recovery and the name-conflict check read the default. | ✅ |
| run_status_filter.py | Core | The one definition of a failed run: `FAILED_RUN_STATUSES` (`error` and `circuit_break`) and `matching_run_statuses`, which maps a run-history status filter to the stored statuses it selects: `error` selects every failed run, a circuit break included, any other status selects only itself. `InMemoryCronStore` and the SQL store apply it in `list_runs` / `count_runs`, so a failure count and the failed run list agree; `job_listing.py` reads the same set to show a failed run's reason (`tests/toolkits/cron/test_cron_run_status_filter.py`). | 纯 |
| runners.py | Core | Built-in job runners (ShellJobRunner, RouterJobRunner, NotificationRunner). `ShellJobRunner` runs the command under the job's own `timeout_seconds` (a timeout is a failure, exit code 124, reason names the limit); exit code 0 is success, exit code 1 is success only for a job with monitoring enabled (the change monitor's "new content" signal) and every other non-zero code fails with stderr, or `exit code N` when stderr is empty (`tests/toolkits/cron/test_cron_runners.py`). | ✅ |
| serialization.py | Core | JSON-safe converters between the frozen cron value objects (`ActiveHours`, `DeliveryConfig`, `FailureAlertConfig` / `False`, `Schedule`) and the dicts that persist them (`dict_to_*` / `*_to_dict`). `types.py` holds only the data definitions; their conversion lives here. | 纯 |
| situation.py | Core | Situation Report — pluggable context aggregator for heartbeat ticks. SituationSection Protocol + SituationReportBuilder (concurrent build, token budget, fault-tolerant) + SituationContext. | ✅ |
| stores.py | Core | Built-in in-memory CronStore for development and testing; it keeps the in-flight run markers in a dict, filters run history by status as `matching_run_statuses` defines (a filter on `error` includes circuit breaks) and answers the same contract as the SQL store, `include_system=False` leaving out the reserved names included (`myrm-agent-server/tests/core/cron/adapters/test_cron_store_contract.py` runs one set of cases against both). | ✅ |
| triggers.py | Core | Trigger type definitions and security helpers. | ✅ |
| types.py | Config | Cron job domain types. `JobType.REMINDER` for zero-LLM prompt delivery. JobResult supports `skipped` + `skip_reason`, `retry_at` (re-arm the job at an instant without counting a failure) and `retry_safe` (False when a repeat could redo what the run already did, would spend the same time budget again or would meet the same cause of failure: the executor then leaves a failed job for its next regular slot instead of a backoff retry). **`CronJob.required_capabilities` + `CronJob.tools_allowed` + `CronJob.skill_ids`**; `CronJobPatch` supports `clear_tools_allowed` / `clear_skill_ids`. Agent jobs may bind **`workflow_template_id` + `workflow_template_args`** for pinned DW reruns (server runner passes through). `CronNotice` / `CronNoticeKind` are the facts the engine reports about a job: a run's outcome (`RUN_SUCCEEDED`, `RUN_FAILED`), a run a crash cut short (`RUN_INTERRUPTED`, which carries no text) or an automatic pause (`JOB_EXPIRED`, `JOB_MAX_FIRES_REACHED`, `JOB_PAUSED_BY_FAILURE`); a notice carries no severity or wording (`job_name` is the job's stored name and `text` the bare output-or-error snippet of a run; the application decides how both are shown). `PauseReason` (`CIRCUIT_BREAK`, `RUN_FAILURES`, `SCHEDULE_ERROR`) is why the scheduler paused a job by itself after a failure, kept on the job as `CronJob.paused_reason` (None while the job is not paused, after a resume, after a person's own status patch and on a duplicate; a pause for expiry or the fire limit has none, those jobs say why through their own fields). `RunNowOutcome` is the answer to a manual run request (started, already running, not found, not active). `SYSTEM_JOB_NAME_PREFIX` and `is_system_job_name(name)` are the one place that says which job names (the `__` prefix) are reserved for jobs the application creates itself, as the heartbeat's is; the layers above ask it instead of repeating the prefix. | ✅ |
