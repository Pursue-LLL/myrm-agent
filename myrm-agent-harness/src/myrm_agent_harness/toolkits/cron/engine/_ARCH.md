## Scheduling contract

A job's slot is booked before its run starts, and a run's state lives in its own in-flight marker, so no crash can leave an enabled job without a next run time. Permanent tests hold these invariants: the slot oracle (`test_next_eligible_run_oracle.py`), the invariants soak (`test_cron_invariants_soak.py`, harness and server), the kill matrix (server `test_cron_kill_matrix.py`), the marker and graceful-stop tests, the removed-symbols gate and the `cron_manage` description contract.

| # | Invariant |
|---|-----------|
| I1 | An enabled job always has a next run time; an empty `next_run_at` exists only on a paused or completed job. |
| I2 | Every booked slot ends in one run record (success, failure, skip, circuit break) or is merged: slots past their grace are merged into one rebooking at start. The exceptions write a log line only: no runner registered for the job type, and `skip_if_active`. |
| I3 | A job has at most one scheduled run in flight. A manual run is refused while a run is in flight and while the job's due slot is being booked (`_admitting`). |
| I4 | While the process lives, the in-flight markers are exactly the jobs that have a run in flight; markers a dead process left are reconciled by the next start. |
| I5 | A schedule that can fire faster than once a minute is booked at least 60 seconds ahead. |
| I6 | A manual run writes only its run record and `last_run_at`, `last_status`, `last_error`, `last_output_hash`; it never changes the schedule, the status, the failure budget or `fire_count`. An expired or exhausted job is still paused, by the guard a scheduled run meets. |

Rules for changing the engine:

1. Writers of `next_run_at`: a feature that books a slot derives it with `next_eligible_run` (directly, through `next_slot_or_retry`, or, for a booking a user's input makes, through `CronValidationMixin._book_slot`, which also refuses a window the schedule never reaches). A backoff retry, a schedule-error retry and a `retry_at` deferral name their own instant, a pause clears the field, and `CronManager.trigger_now` (the IMA source sync) sets it to now.
2. Guards: a scheduled run that a dispatch guard refuses (today the cooldown and the active hours) writes a SKIPPED record and books the next slot (`record_guard_skip`), and a new guard does the same. A bare return would end the slot with no run record (I2).
3. Cancellation: a new path that cancels a run at the user's request writes the run's terminal record itself and clears the marker. Only `stop()` and an event loop that ends keep the marker, and the next start reconciles it.
4. Missed slots: replaying or dropping a slot the downtime missed happens in two places only, `StartupRecovery._replay_missed_slots` (startup replay) and `reschedule_skipped` (a slot past its grace).
5. Activation: a paused job becomes enabled only through `_validate_resume_preconditions` (`resume_job`, or an update that patches the status to active).

Limits that are accepted, each a deliberate trade:

- A crash between the booking write and the marker write loses that one slot's run, with no record; the next slot is booked, and a one-shot job (never booked) is not affected. A crash between the closing write and the marker clear is reported at the next start as an interrupted run and counts one failure. A run that ends just as the next run of the same job has written its marker clears that marker too, so the next run, if killed, leaves no record.
- An interrupted one-shot job is delivered again within its grace: at least once, so a run that delivered and was killed before it closed delivers twice. A killed run counts one failure, so a job whose every run kills the process is paused after `max_retries`.
- `stop()` gives cancelled runs half a second to unwind; a message already sent or a file already written is not rolled back.
- A recurring cron job whose run a crash interrupted is not run again for that slot: the booking write that preceded the run stamped `updated_at` past it (`CronStore.advance_next_run` stamps it on every successful booking, in the SQL store and in the in-memory one). The crash report does not move `updated_at`, so the replay anchor, `max(last_run_at, updated_at)`, stays put and a slot that came due while the process was down is replayed once, as for a job nothing happened to.
- A run that outlasts its interval makes the timer re-arm against the slot that is already due and wake about every two seconds (`_MIN_REFIRE_GAP_S`), one `list_jobs(due_before)` query each, until the run closes. A one-shot job whose type has no runner stays due and logs `No runner registered` on each of those wakes.
- A trial's `last_run_at` is the anchor of the next slot's cooldown. A trial shares `last_output_hash` with scheduled runs, so under `deduplicate` an output equal to the last one is not delivered again.
