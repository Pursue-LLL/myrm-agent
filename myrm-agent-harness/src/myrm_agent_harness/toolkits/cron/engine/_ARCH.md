# engine/

## Overview
Cron scheduling engine internals.

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| __init__.py | Package | Cron scheduling engine internals. | — |
| connector_health.py | Core | Structured connector health degradation and failure classification for cron automations. | 纯 |
| executor.py | Core | Single-job execution lifecycle. Delivery gate: incremental skip, `is_silent_output`, output-hash dedup；A repeated `monitor_contract_error` is not delivered again on the primary channel (`monitor_contract_error_dedup`); the monitoring itself lives in `IncrementalMonitoringMixin` (`incremental_monitoring.py`).The closing write (`_update_after_run`) adopts the stored job first (`job_freshness.py`), then applies what the run decided (auto-pause, backoff, completion). A failed run with `JobResult.retry_safe=False` (the runner reports that a repeat could redo what the run already did or would meet the same cause of failure, or the executor's own timeout fired, or the pre-flight probe failed) is not re-fired on the backoff schedule: a recurring job waits for its next regular slot, a one-shot job is paused instead of retried; the failure still counts toward auto-pause. A pre-flight condition that raises `PreFlightConditionError` (its script crashed, timed out or could not start) ends the run as a failed one with `retry_safe=False`, through the same closing path (`_finish_run`: monitoring, delivery, run record, run notice, closing write) as any failed run, so it alerts and auto-pauses like one; a condition that returns `(False, …)` is a skip. Skips and `JobResult.retry_at` deferrals are recorded by `SkippedRunMixin` (`skipped_runs.py`). A delivered run's outcome is reported through `RunNoticeMixin` (`run_notices.py`). | ✅ |
| failure_alerts.py | Core | `FailureAlertMixin` mixed into `JobExecutor`: `_maybe_send_failure_alert` resolves the per-job or global alert config, throttles by `after` consecutive failures and cooldown, and delivers an alert (job name, consecutive failure count, the last error) whose last sentence describes the job's updated state (auto-paused, will retry with backoff, or not re-run ahead of schedule with its next regular run). A failure that will not be repeated early (`retry_safe=False`) is alerted without waiting for `after` failures; the cooldown still applies. The text is plain and points to no product screen. | ✅ |
| fingerprint.py | Core | Canonical workflow fingerprint hashing for automation manual success prerequisite gating. | 纯 |
| helpers.py | Core | Pure engine helpers: stagger resolution, active-hours / stale-run / misfire / error-backoff checks, the pre-execution guards (`pre_execution_check`: expiry, fire limit, cooldown) with the `CronNotice` an automatic pause raises (`auto_pause_notice`), failure-alert resolution and error classification, and telemetry extraction. | ✅ |
| incremental_monitoring.py | Core | `IncrementalMonitoringMixin` mixed into `JobExecutor`: `_apply_incremental_monitoring` diffs a successful run's output against the job's stored baseline (exit code 0 = nothing new, 1 = new content carried in `incremental_delta`; a baseline past its TTL is reset and flagged in the run metadata). A monitor that fails leaves the full output untouched, except an invalid JSON-like output (`monitor_contract_error`), which turns the run into a failed one so the unified failure path alerts. `_next_monitor_failure_count` persists the consecutive monitor failure count and falls back to an in-memory count when the store refuses it. | ✅ |
| integrity.py | Core | Merkle chain integrity for cron run records. | ✅ |
| job_freshness.py | Core | `adopt_latest(store, job)`: the stored job is the truth. Copies every `CronJob` field except the run-owned `RUN_OWNED_FIELDS` (`fire_count`, `last_output_hash`) from the store onto an in-hand snapshot; `False` when the job was deleted. Called after the stagger and slot waits (`scheduler.py`) and before each closing write (`executor.py`, `skipped_runs.py`), so a pause, edit or delete made while a run waited or ran is neither undone nor resurrected. A new run-owned `CronJob` field must be added to `RUN_OWNED_FIELDS` (a test pins the set to real fields). | ✅ |
| name_generator.py | Core | Intelligently truncates long prompts/commands while preserving readability. | ✅ |
| parser.py | Core | Cron expression parsing and next-run calculation. | ✅ |
| recovery.py | Core | Three-phase startup recovery strategy. | ✅ |
| run_notices.py | Core | `RunNoticeMixin` (mixed into `JobExecutor`): `emit_notice` hands a `CronNotice` to the application layer's callback, and `_notify_run_outcome` reports a delivered run's outcome (the job's name and the first 100 characters of its output or error; a run whose delivery was skipped stays quiet). The engine states the fact only; severity, wording and language belong to the callback. A callback that raises is logged and never fails a run or a scheduler tick. | ✅ |
| skipped_runs.py | Core | `SkippedRunMixin` mixed into `JobExecutor`: `_record_skipped()` writes a SKIPPED run and advances the schedule (one-shot jobs complete or are deleted); `_record_deferred()` handles `JobResult.retry_at` — SKIPPED run, no failure counted, job re-armed at the instant, one-shot jobs stay alive. Neither spends `max_fires`: the scheduler counts a fire when the run starts, and both hand it back (never below 0), so the limit counts runs that executed. Both adopt the stored job first: a deleted job gets no run record and is not brought back, a paused job stays paused. | ✅ |
| scheduler.py | Core | Cron scheduling engine. Computes exact sleep durations to the next due job and dispatches due jobs into async tasks bounded by a semaphore of `CronConfig.max_concurrent` slots. After the stagger and slot waits a run starts only if the stored job still exists and is ACTIVE (`adopt_latest`), and then runs the stored definition. A job the pre-execution check pauses (expired, fire limit reached) is saved and reported as a `CronNotice`. | ✅ |
