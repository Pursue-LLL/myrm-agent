# engine/

## Overview
Cron scheduling engine internals.

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| __init__.py | Package | Cron scheduling engine internals. | — |
| connector_health.py | Core | Structured connector health degradation and failure classification for cron automations. | 纯 |
| executor.py | Core | Single-job execution lifecycle. Delivery gate: incremental skip, `is_silent_output`, output-hash dedup；A repeated `monitor_contract_error` is not delivered again on the primary channel (`monitor_contract_error_dedup`); the monitoring itself lives in `IncrementalMonitoringMixin` (`incremental_monitoring.py`).The closing write that follows the run record is `RunCloserMixin` (`run_closer.py`). A pre-flight condition that raises `PreFlightConditionError` (its script crashed, timed out or could not start) ends the run as a failed one with `retry_safe=False`, through the same closing path (`_finish_run`: monitoring, delivery, run record, run notice, closing write) as any failed run, so it alerts and auto-pauses like one; a condition that returns `(False, …)` is a skip. Skips and `JobResult.retry_at` deferrals are recorded by `SkippedRunMixin` (`skipped_runs.py`). A delivered run's outcome is reported through `RunNoticeMixin` (`run_notices.py`). | ✅ |
| failure_alerts.py | Core | `FailureAlertMixin` mixed into `JobExecutor`: `_maybe_send_failure_alert` resolves the per-job or global alert config, throttles by `after` consecutive failures and cooldown, and delivers an alert (job name, consecutive failure count, the last error) whose last sentence describes the job's updated state (auto-paused, will retry with backoff, or not re-run ahead of schedule with its next regular run). A failure that will not be repeated early (`retry_safe=False`) is alerted without waiting for `after` failures; the cooldown still applies. The text is plain and points to no product screen. | ✅ |
| fingerprint.py | Core | Canonical workflow fingerprint hashing for automation manual success prerequisite gating. | 纯 |
| helpers.py | Core | Pure engine helpers (no I/O besides log lines): stagger resolution, active-hours / misfire / error-backoff checks, the pre-execution guards (`pre_execution_check`: expiry, fire limit, cooldown) with the `CronNotice` an automatic pause raises (`auto_pause_notice`), failure-alert resolution and error classification, and telemetry extraction. `next_eligible_run` is the one function that derives a job's next regular slot (create, resume, schedule edit, run closing, skipped runs, recovery): the first slot after the job's cooldown that lies in its active window (at most 2000 candidates are examined, so a window no slot reaches ends in a slot outside it rather than a loop), with a 60-second floor for a schedule that can fire faster than once a minute (an interval or a cron with a seconds field); a one-shot names its own instant. `next_slot_or_retry` is the slot the scheduler books for a recurring job: `next_eligible_run`, or a minute ahead (with a warning) when the schedule cannot be computed. A backoff retry and a `retry_at` deferral set their own instants. `tests/toolkits/cron/test_next_eligible_run_oracle.py` compares `next_eligible_run` with an independent slot enumeration. | ✅ |
| incremental_monitoring.py | Core | `IncrementalMonitoringMixin` mixed into `JobExecutor`: `_apply_incremental_monitoring` diffs a successful run's output against the job's stored baseline (exit code 0 = nothing new, 1 = new content carried in `incremental_delta`; a baseline past its TTL is reset and flagged in the run metadata). A monitor that fails leaves the full output untouched, except an invalid JSON-like output (`monitor_contract_error`), which turns the run into a failed one so the unified failure path alerts. `_next_monitor_failure_count` persists the consecutive monitor failure count and falls back to an in-memory count when the store refuses it. | ✅ |
| integrity.py | Core | Merkle chain integrity for cron run records. | ✅ |
| job_freshness.py | Core | `adopt_latest(store, job)`: the stored job is the truth. Copies every `CronJob` field except the run-owned `RUN_OWNED_FIELDS` (`fire_count`, `last_output_hash`) from the store onto an in-hand snapshot; `False` when the job was deleted. Called after the stagger and slot waits (`scheduler_dispatch.py`) and before each closing write (`run_closer.py`, `skipped_runs.py`), so a pause, edit or delete made while a run waited or ran is neither undone nor resurrected. A new run-owned `CronJob` field must be added to `RUN_OWNED_FIELDS` (a test pins the set to real fields). | ✅ |
| name_generator.py | Core | Intelligently truncates long prompts/commands while preserving readability. | ✅ |
| parser.py | Core | Cron expression parsing and next-run calculation. | ✅ |
| recovery.py | Core | Two-phase startup recovery. A recurring job's next slot is booked before its run starts, so an unclean shutdown leaves every enabled job with a next run time; recovery only decides what happens to the slots that came due while the process was down. Phase 1 replays the cron slots missed during the downtime, phase 2 runs the due jobs still within their misfire grace (a job in error backoff waits for the tick). Both hand the job to the scheduler's admission (`admit_fn`), which books the next slot and launches the run. A due job past its grace is not run: `reschedule_skipped` books its next slot and marks it SKIPPED (a one-shot job completes). | ✅ |
| run_closer.py | Core | `RunCloserMixin` mixed into `JobExecutor`: the closing write once a run is recorded. `_update_after_run` adopts the stored job first (`job_freshness.py`), then applies what the run decided: auto-pause on a circuit break or when consecutive failures exceed `max_retries`, the next regular slot after a success or a failure that must not be repeated early, otherwise a backoff retry. A failed run with `JobResult.retry_safe=False` (the runner reports that a repeat could redo what the run already did or would meet the same cause of failure, or the executor's own timeout fired, or the pre-flight probe failed) is not re-fired on the backoff schedule: a recurring job waits for its next regular slot, a one-shot job is paused instead of retried; the failure still counts toward auto-pause. `_handle_once_completion` completes a one-shot job and deletes it only when `delete_after_run` is set, the run succeeded and its delivery did not fail (a failed delivery keeps the job and its run record, the only copy of the result; `tests/toolkits/cron/test_cron_once_completion.py`); a retry-safe transient failure within `max_retries` is retried with backoff, any other failure pauses it; `_handle_schedule_compute_error` re-arms a job whose schedule cannot be computed 60 seconds later and auto-pauses it at the third consecutive error. | ✅ |
| run_notices.py | Core | `RunNoticeMixin` (mixed into `JobExecutor`): `emit_notice` hands a `CronNotice` to the application layer's callback, and `_notify_run_outcome` reports a delivered run's outcome (the job's name and the first 100 characters of its output or error; a run whose delivery was skipped stays quiet). The engine states the fact only; severity, wording and language belong to the callback. A callback that raises is logged and never fails a run or a scheduler tick. | ✅ |
| skipped_runs.py | Core | `SkippedRunMixin` mixed into `JobExecutor`: `_record_skipped()` writes a SKIPPED run and advances the schedule (one-shot jobs complete or are deleted); `record_guard_skip()` is the entry for a dispatch guard's refusal: a SKIPPED run that never began, so the job's last run time (the cooldown anchor) stays where it was while the next slot is booked; `_record_deferred()` handles `JobResult.retry_at` — SKIPPED run, no failure counted, job re-armed at the instant, one-shot jobs stay alive. Neither spends `max_fires`: the scheduler counts a fire when the run starts, and both hand it back (never below 0), so the limit counts runs that executed. Both adopt the stored job first: a deleted job gets no run record and is not brought back, a paused job stays paused. | ✅ |
| scheduler.py | Core | Cron scheduling engine. Computes exact sleep durations to the next due job. Each tick lists the due jobs and handles every one on its own (`_handle_due`): a job still in flight waits, one past its misfire grace is rebooked and marked SKIPPED, any other is admitted; a failure on one job is logged and never holds back the rest. Runs are async tasks bounded by a semaphore of `CronConfig.max_concurrent` slots, and `_in_flight` counts each job's runs between launch and close. Admission, launch, trigger dispatch and the guarded execution path every run takes are `SchedulerDispatchMixin` (`scheduler_dispatch.py`). | ✅ |
| scheduler_dispatch.py | Core | `SchedulerDispatchMixin` mixed into `CronScheduler`: `dispatch_event`, `dispatch_system_event` and `dispatch_webhook` ask the injected `TriggerProvider` for the matching jobs (none injected: nothing triggers) and launch each (`_launch`). `_admit` books a due recurring job's next slot with one conditional write (`CronStore.advance_next_run`) and only then launches the run: a job that was paused, deleted, edited or already dispatched meanwhile is not run, and a crash cannot leave the job without a next run time. A one-shot job is not booked: it stays due until it completes. `_launch` registers the run in flight before its task exists and `_run` clears it when the run closes. `_dispatch` is the guarded execution path every run takes: pre-execution check, active hours, `skip_if_active`, stagger, runner lookup, concurrency slot; a one-shot job is held back by neither the cooldown nor the active hours. A scheduled slot that a guard refuses is recorded as SKIPPED with the next slot booked (`record_guard_skip`); a run a trigger started leaves no record. After the stagger and slot waits a run starts only if the stored job still exists and is ACTIVE (`adopt_latest`), and then runs the stored definition. A job the pre-execution check pauses (expired, fire limit reached) is saved with no next run time and reported as a `CronNotice`. | ✅ |
