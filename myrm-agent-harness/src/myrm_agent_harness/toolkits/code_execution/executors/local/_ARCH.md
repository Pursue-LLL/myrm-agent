# local/

## Overview
Local code executor module. Executes Python code and Bash commands on the
host machine using subprocesses, persistent sessions, and OS-level sandboxing.

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| __init__.py | Package | Re-exports `LocalExecutor`. | — |
| executor.py | Core | Orchestrator: Python execution, persistent-shell lifecycle (it keeps the shell registry and, weakly held, the per-identity start locks), workspace binding and the composed services; its bash path is `LocalBashMixin`. A bash command may name the granted directories only while an OS sandbox enforces them (`_command_whitelist`). | ✅ |
| _bash_exec.py | Core | `LocalBashMixin`, the bash path of `LocalExecutor`: `execute_bash` validates, audits and logs the command the agent issued (`context.original_code`; no log line quotes the header the prepared script starts with), runs the prepared script in the persistent shell (the issued text with `/workspace` swapped for the bound workspace, quoted for a bash session when its name needs it, and pip commands pointed at the venv), and hands the context's `cancel_token` and the command's `CommandEnv` (with the working directory when `context.enter_work_dir` is set) to it. The shell itself starts with a sanitized environment that holds no credentials. | ✅ |
| _bash_sessions.py | Helper | Which persistent shell serves a command: `shell_grants` (the granted directories the shell's sandbox may open: none without an enforcing OS sandbox), `get_or_create_bash_session` (the key carries a signature of the grants, so a changed set starts a new shell and closes the old one; the callers of one run identity pass through a per-identity start lock, so commands that arrive together — the parallel sub-agents of a run — start one shell, and a shell that is in use is not probed, so a caller neither queues at the lock behind its command nor restarts its shell), `close_bash_sessions`, `grant_command_paths` (what the command validator is relaxed for). | ✅ |
| _command_env.py | Helper | What one bash command may read: `scrubbed_user_env` (skill/global settings minus host-secret names), `skill_secret_env` (the secret-named settings of the running skill, `ExecutionContext.skill_env`: delivered only around the commands that `plain_skill_call` accepts as calls of that skill's own `.claude/skills/<name>/` files, under the same name rule as a one-time credential, so loader/runtime hook names and shell-shaping names are refused), `collect_command_credentials` (user OAuth credentials filtered by `allowed_credential_issuers`, plus single-use ephemeral credentials consumed against the command's digest), `build_command_env` (skill secrets and credentials form `scoped`; a credential wins over a skill setting of the same name; `cwd` carries the command's starting directory). | ✅ |
| _file_ops.py | Core | Native file I/O (read/write/delete/list; `file_size` is a `stat` that refuses non-regular files; `.gz` reads are size-bounded) via pathlib. Text is read and written as UTF-8 bytes, so a file's CR/LF line endings reach the caller and come back unchanged on every platform. Every mutation passes `_guard_write`, which refuses a write into a directory granted read-only (`refuse_write_into_readonly_grant`) and, through the shared `core.security.path` rules, credential paths, persona instruction files, read-only evidence directories and the active Goal's protected paths — so a sandbox write is refused exactly when the file tools or the shell pre-flight would refuse it. Reads of those paths stay open. Every mutation (the four write variants and delete) goes through one `_prepare_mutation`: resolve, `_guard_write`, then `trigger_destructive_action_hook` with the target and the `session_id` for turn/chat binding, so a refused write is never reported. | ✅ |
| _python_subprocess.py | Helper | Python script subprocess: sandbox wrapping, readonly_workspace context passthrough, env, stdin of `/dev/null` (an `input()` gets `EOFError` at once instead of waiting on the host's stdin), timeout, output parsing; a stopped request (`context.cancel_token`) shares the timeout's exit and kills the script: SIGTERM to its process group, then SIGKILL of what is left after 2 s (`kill_spawned_group`, so a command the script started and left running dies with it even after the script itself has exited). The pipes are read through `communicate_bounded`: stdout up to 12 × the wrapper's `max_output_bytes` + 64 KiB (the wrapper bounds only the stdout characters it captures and prints its result with `json.dumps`, up to 12 bytes per character), stderr up to `max_output_bytes` + 64 KiB (raw text the wrapper never carries its result on), so a script that floods either pipe or a file descriptor cannot grow the host's memory; when a pipe was cut, a line saying so is appended to the result's stderr. A failure of the executor itself (not of the script) returns an error result and is logged with its stack by `logger.exception`, never printed to stderr, where the host's log handler could not mask it. | ✅ |
| _background_spawn.py | Helper | Background process spawning with sandbox, env isolation, process groups; **PTY-first on POSIX (non-sandbox) with PIPE fallback** via `_background_pty_spawn.py`. A job's environment is the host's filtered one plus non-interactive defaults (`CI`, `NO_COLOR`, `TERM=dumb`, …) with `PAGER` and `GIT_PAGER` pinned to `cat`, so a job on a PTY never waits at a pager; the caller's `env` overrides every one of them. Unless `harness_owned` (MCP servers), a job runs under the agent's capability scope (read-only workspace) and records execution evidence. A sandboxed job may use the standing granted directories (`standing_access_roots`). The log line of a spawn quotes the command the agent issued (`context.original_code`), not the shell text built from it. | ✅ |
| _background_pty_spawn.py | Helper | POSIX PTY master/slave spawn adapter (merged stdout/stderr); skipped when an OS sandbox wraps the command or on Windows. The master read side maps the Linux EIO hang-up to a clean EOF so output still buffered at child exit is never dropped. The parent closes its slave descriptor after the master reader is attached, on a thread of its own (not the shared default executor), so the output of a job that finished before the spawn returned is not discarded (macOS) and a busy executor cannot hold a spawn up. A spawn that fails or is cancelled once the child runs stops the child's whole process group, since no wrapper owns the job yet. | ✅ |
