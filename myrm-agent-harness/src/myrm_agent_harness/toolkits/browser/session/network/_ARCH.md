# browser/session/network/

## Overview
The two recorders behind the `network_log` / `network_detail` / `network_replay` actions of `browser_manage_tool`. `NetworkIntelligence` listens through CDP and numbers the XHR/Fetch requests of the active page; `NetworkLogger` listens through the driver's own events and covers what CDP cannot (engines without CDP, the other resources that answered 4xx/5xx). The session-level APIs that compose their answers live one level up in `browser_session_network_mixin.py`.

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| `__init__.py` | Package | Public facade: `NetworkIntelligence`, `CdpRequestRecord`, `EMPTY_RESPONSE`, `NetworkLogger`, `RequestInfo`, `safe_preview` and the preview limits. | ✅ |
| `intelligence.py` | Core | CDP-based network intelligence: how each API request ended, and on-demand response bodies. Raw POST body window stored; get_summary masks URL and POST body before cutting them to their previews (`safe_preview`); response body redacted before truncation (boundary-crossing credentials stay masked). The CDP detach is time-bounded (`detach_cdp_bounded`) because the bound page may be wedged. The number `network_log` shows is the request's own `seq` (handed out once, in arrival order; never reused, even after `clear`; only XHR/Fetch requests are tracked, because nothing opens a document's body and tracking documents would fill the 100-record window with entries no number can name), not a position in the 100-record window, so `network_detail` / `network_replay` can never act on a different request than the one listed: a number that has left the window is refused with the range that is valid now. A request says how it ended, so `[pending]` means in flight only: a redirect hop takes the status of the redirect response (Chrome reuses the requestId across hops and reports that response with the next hop), and a request the browser gave up on carries its `Network.loadingFailed` error (`[failed: net::ERR_…]`, CORS failures add the CORS reason; a failure outranks an earlier status, so a body cut off mid-transfer reads as failed). Chrome also sends `loadingFailed` with `canceled` for a response the page itself dropped after it arrived (a 204 or empty body nobody read, a stream the page aborted): that keeps the server's status, because the answer did arrive. A request a navigation cuts off before its headers stays `[pending]` (Chrome reports nothing for it). `network_detail` answers a hop with the request that carries on, a failure with the browser's error, and a 204 / 205 / 304 with `No response body (status N)`, all without asking Chrome; an empty body reads `Empty response`, and a body Chrome kept none of says so instead of quoting the driver's error. | ✅ |
| `logger.py` | Core | Network request logging for the browser toolkit. Provides self-diagnosis capability for browser sessions. `get_summary` lists XHR/Fetch requests only (the numbered list of an engine without CDP); `get_other_failed_summary` lists the other resources that answered 4xx/5xx, one unnumbered line each (the latest 20, the rest counted). `safe_preview` masks credentials first and cuts afterwards (a cut ends with `…`), so a credential the cut would split leaves no fragment: URL up to `URL_PREVIEW_CHARS`, POST body up to `POST_PREVIEW_CHARS`. A POST body the driver cannot decode as text reads `<binary body>` and keeps its record. | ✅ |
