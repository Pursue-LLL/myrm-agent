# completion_guard/

## Overview

The finish gate: it holds an answer back until the run has earned it, and routes the run back to the model with
an instruction that exists only in the next model request. `guard.py` decides, `hold_back.py` delivers,
`directive.py` words the instruction, `directive_middleware.py` appends it to the request; the checks the
decision draws on (checklist, external evidence, freshness, capabilities, re-run, mixed message) sit beside them.
Nothing the guard says to the model is stored in the conversation or the checkpoint, so the prompt-cache prefix
stays intact.

Detailed design: [MIDDLEWARE_SYSTEM.md](../../MIDDLEWARE_SYSTEM.md)

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| `__init__.py` | Package | Public surface: `CompletionGuard`, `reset_completion_guard`, `build_checklist`, `classify_verification`, `is_mutating_tool`, `attach_disclosure_to_event`. The other modules are imported by path. | — |
| `guard.py` | Core | `CompletionGuard.aafter_model`: the finish gate. Orchestrates checklist, external evidence, deliverable write, execution-claim, query-grounding and PPT checks, plus an independent sandbox re-run (`rerun.py`) for code tasks. Each demand is made only of a run that could meet it (`CompletionCapabilities`): the unwritten-deliverable demand (its rejections and the forced-finish staging) only of a run that can save a file, the unfinished-todo check only of a run that keeps a todo list, and the external-evidence demand only of a run holding a tool that can produce evidence; a run that holds none is asked once to say plainly it could not check (`evidence_unreachable`, tracked per turn) and then passes. A false "saved" claim is blocked for every run. Publishes the per-turn disclosure payload (evidence tier + staged artifacts) read by the post-run `message_end` event, with a per-run rejection budget keyed by the bound message id so concurrent runs cannot reset or exhaust each other. | ✅ |
| `hold_back.py` | Internal | `hold_back()`: what a held-back draft becomes and where the instruction follows. Routes the run to the model (`jump_to="model"`), leaves the instruction pending in the run state, records the decision and tells the UI the draft is superseded. A draft that says something stays and the instruction follows it (a finish-tool call it carries is dropped, as it never runs); a finish-tool draft that says nothing is removed from the conversation (`RemoveMessage`) and the instruction follows the message before it, so neither an unanswered call nor an empty assistant message stays in the thread; a message without an id cannot be addressed and the answer is let through. | ✅ |
| `mixed_message.py` | Internal | `strip_readonly_calls_beside_answer()`: the Mixed Message Guard. A finished answer that still carries read-only tool calls ends the turn at once; effectful calls (`is_mutating_tool`, registry fail-closed) and interaction/UI carriers are kept, and only guaranteed side-effect-free non-interactive read-only tools are stripped. | ✅ |
| `capabilities.py` | Internal | `CompletionCapabilities` (`keeps_todo_list`, `can_save_files`, `can_gather_evidence`) and `capabilities_of(registry)`: what the run can do, read from its tool registry and the policy of the call each time it is asked, so the guard demands only what the run could meet. Defaults hold a run to every demand. | ✅ |
| `directive.py` | Internal | `BlockReasons` (what the guard found, one field per check) and `render_completion_directive()`: the model-facing instruction for each reason (for an unreachable evidence demand: say plainly the run could not check, no instruction to gather evidence; a forced finish: the final reply must state what is still unresolved) and, with no reason set, the task-aware verification checklist from this run's records. | ✅ |
| `directive_middleware.py` | Internal | `CompletionDirectiveMiddleware.awrap_model_call`: appends the pending directive to the model request as the last message, only while the message it follows (the held-back draft, or the message before a removed finish-tool draft) is still the last message of the request; the conversation and the checkpoint never hold it. Placed right after the user middlewares in `build_middlewares`. | ✅ |
| `events.py` | Internal | The guard's two outward signals: `log_guard_decision()` writes a `completion_guard` event (held back or forced finish, reason names, rejection count, number of staged drafts — names and counts only) to the session event log, and `announce_superseded_draft()` sends the `answer_recheck` restart status so the UI drops the draft it was streaming. | ✅ |
| `freshness.py` | Internal | The trigger of the external-evidence gate: whether the request needs fresh outside data, from word lists (a strong cue alone; time words only beside a changing topic or a lookup ask; always-volatile facts), with exemptions for the user's own project or material and text-only transforms, plus a branch for a short question about today or right now that asks for a fact rather than advice (messages over 200 characters are pasted material and never take it). Word lists cover English, Simplified and Traditional Chinese. Pinned by a hand-labeled prompt set. | ✅ |
| `external_evidence.py` | Internal | External evidence gate: whether this run's records hold successful web/browser/MCP evidence (PTC bash via ``skills.mcp_*`` and Direct FC via ``mcp__{server}__{tool}``) for a request `freshness` says needs it, and `can_produce_external_evidence` — whether a set of mounted tools could ever produce that evidence (a shell counts: it may import an MCP server). | ✅ |
| `checklist.py` | Internal | Checklist builder (including the unfinished-todo check, run only by an agent that holds `todo_write`, on the running chat's own list; the list blocks finishing only once `file_write_tool` or `file_edit_tool` has run in the run, otherwise it is a WARNING line that never blocks and is read by the model only in the checklist the guard sends when it holds an answer back for a failed verification) and temporal ordering analysis (code written after the last passing verification). | ✅ |
| `verification.py` | Internal | `classify_verification()`: which bash command counts as a test, lint, type-check or build run, matched on command boundaries. | ✅ |
| `rerun.py` | Internal | `rerun_verification_in_sandbox()`: runs the last verification command again in the sandbox (fail-closed, 120 s timeout) when code was written after it last passed; no model call. | ✅ |
| `state.py` | Internal | Per-run guard state (rejection budget, forced-finish latch, whether the "could not check" disclosure was already requested, the directive pending for the next model request) and the per-turn disclosure registry (evidence tier, staged drafts), keyed by the bound message id with an LRU cap; `isolated_run_state` keeps a nested run (a child agent) from resetting or evicting its caller's turn and leaves none of its own behind; `attach_disclosure_to_event()` feeds the `message_end` event once per turn. | ✅ |
| `safety.py` | Internal | Effectful tool detection SSOT (`is_mutating_tool`) with static mutation/interaction-UI alias sets and registry fail-closed fallback, and `FINISH_TOOL_NAMES`, the tool a model calls to hand in its answer (the guard reads a call to it as a completion attempt); `is_mutating_tool` is consumed by the Mixed Message Guard and server Cron post-run verification. | ✅ |
