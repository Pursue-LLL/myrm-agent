# completion/

## Overview

Completion guard subsystem — finish gate, code verification, external evidence,
deliverable write claims, execution-claim grounding, per-turn evidence
disclosure, and mixed-message early termination. A held-back answer is routed
back to the model with the instruction delivered in the next model request
only (`completion_directive_middleware.py`); no tool call stands in for it and
nothing is stored in the conversation.

Detailed design: [MIDDLEWARE_SYSTEM.md](../MIDDLEWARE_SYSTEM.md)

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| `__init__.py` | Package | Public exports for CompletionGuard and helpers. | — |
| `completion_guard.py` | Core | Finish gate + Mixed Message Guard + independent sandbox re-run (`completion_guard_rerun.py`) for code tasks. Orchestrates checklist, external evidence, deliverable write, execution-claim and PPT checks. Each demand is made only of a run that could meet it (`CompletionCapabilities`): the unwritten-deliverable demand (its rejections and the forced-finish staging) only of a run that can save a file, the unfinished-todo check only of a run that keeps a todo list, and the external-evidence demand only of a run holding a tool that can produce evidence; a run that holds none is asked once to say plainly it could not check (`evidence_unreachable`, tracked per turn) and then passes. A false "saved" claim is blocked for every run. Holding an answer back routes the run to the model (`jump_to="model"`), leaves the instruction pending in the run state, records the decision (`completion_guard_events.py`) and tells the UI the draft is superseded; a draft that says something stays and the instruction follows it (a finish-tool call it carries is dropped, as it never runs), while a finish-tool draft that says nothing is removed from the conversation (`RemoveMessage`) and the instruction follows the message before it, so neither an unanswered call nor an empty assistant message stays in the thread; a message without an id cannot be addressed and the answer is let through. Publishes the per-turn disclosure payload (evidence tier + staged artifacts) read by the post-run `message_end` event, with a per-run rejection budget keyed by the bound message id so concurrent runs cannot reset or exhaust each other. Mixed Message preserves effectful calls (`is_mutating_tool`, registry fail-closed) and interaction/UI carriers; only guaranteed side-effect-free non-interactive read-only tools are stripped. | ✅ |
| `completion_capabilities.py` | Internal | `CompletionCapabilities` (`keeps_todo_list`, `can_save_files`, `can_gather_evidence`) and `capabilities_of(registry)`: what the run can do, read from its tool registry and the policy of the call each time it is asked, so the guard demands only what the run could meet. Defaults hold a run to every demand. | ✅ |
| `completion_directive.py` | Internal | `BlockReasons` (what the guard found, one field per check) and `render_completion_directive()`: the model-facing instruction for each reason (for an unreachable evidence demand: say plainly the run could not check, no instruction to gather evidence; a forced finish: the final reply must state what is still unresolved) and, with no reason set, the task-aware verification checklist from this run's records. | ✅ |
| `completion_directive_middleware.py` | Internal | `CompletionDirectiveMiddleware.awrap_model_call`: appends the pending directive to the model request as the last message, only while the message it follows (the held-back draft, or the message before a removed finish-tool draft) is still the last message of the request; the conversation and the checkpoint never hold it. Placed right after the user middlewares in `build_middlewares`. | ✅ |
| `completion_guard_events.py` | Internal | The guard's two outward signals: `log_guard_decision()` writes a `completion_guard` event (held back or forced finish, reason names, rejection count, number of staged drafts — names and counts only) to the session event log, and `announce_superseded_draft()` sends the `answer_recheck` restart status so the UI drops the draft it was streaming. | ✅ |
| `completion_guard_freshness.py` | Internal | The trigger of the external-evidence gate: whether the request needs fresh outside data, from word lists (a strong cue alone; time words only beside a changing topic or a lookup ask; always-volatile facts), with exemptions for the user's own project or material and text-only transforms, plus a branch for a short question about today or right now that asks for a fact rather than advice (messages over 200 characters are pasted material and never take it). Word lists cover English, Simplified and Traditional Chinese. Pinned by a hand-labeled prompt set. | ✅ |
| `completion_guard_rerun.py` | Internal | `rerun_verification_in_sandbox()`: runs the last verification command again in the sandbox (fail-closed, 120 s timeout) when code was written after it last passed; no model call. | ✅ |
| `completion_guard_state.py` | Internal | Per-run guard state (rejection budget, forced-finish latch, whether the "could not check" disclosure was already requested, the directive pending for the next model request) and the per-turn disclosure registry (evidence tier, staged drafts), keyed by the bound message id with an LRU cap; `isolated_run_state` keeps a nested run (a child agent) from resetting or evicting its caller's turn and leaves none of its own behind; `attach_disclosure_to_event()` feeds the `message_end` event once per turn. | ✅ |
| `completion_guard_safety.py` | Internal | Effectful tool detection SSOT (`is_mutating_tool`) with static mutation/interaction-UI alias sets and registry fail-closed fallback; consumed by Mixed Message Guard and server Cron post-run verification. | ✅ |
| `deliverable_auto_staging.py` | Internal | Automatic staging and LRU preservation for unwritten deliverables in `.myrm/staged_artifacts/`. | ✅ |
| `deliverable_confidence_tier.py` | Core | DeliverableConfidenceTier SSOT (VERIFIED, ARTIFACT, RESEARCH, PLAN), deterministic physical evidence resolver (measured 0.018 ms over a 66-record turn), and the disclosure policy (`should_disclose_tier`): evidence tiers are always shown, PLAN only when the answer itself makes a completion claim. | ✅ |
| `completion_guard_checklist.py` | Internal | Verification command classification, checklist builder (including the unfinished-todo check, run only by an agent that holds `todo_write`, on the running chat's own list; the list blocks finishing only once `file_write_tool` or `file_edit_tool` has run in the run, otherwise it is a WARNING line that never blocks and is read by the model only in the checklist the guard sends when it holds an answer back for a failed verification), temporal ordering analysis. | ✅ |
| `completion_guard_external_evidence.py` | Internal | External evidence gate: whether this run's records hold successful web/browser/MCP evidence (PTC bash via ``skills.mcp_*`` and Direct FC via ``mcp__{server}__{tool}``) for a request `completion_guard_freshness` says needs it, and `can_produce_external_evidence` — whether a set of mounted tools could ever produce that evidence (a shell counts: it may import an MCP server). | ✅ |
| `deliverable_write_verifier.py` | Internal | Zero-call deliverable write claim detection and unwritten deliverable heuristic sniffer. | ✅ |
| `execution_claim_verifier.py` | Internal | Completion-claim grounding against this run's tool records: verification claims (real test runners only; dry runs and zero-test outputs never ground a pass), outbound/irreversible action claims (MCP with outbound semantics, outbound commands, outbound tool names), and code-change claims (successful writes or shell mutations). Sentence-level scan with attribution/conditional/negation/explanation exclusions and request-intent gating for bare result forms; `has_completion_claim()` exposes the claim detection for the disclosure policy. | ✅ |
| `execution_claim_lexicon.py` | Internal | Declarative lexicons for the claim verifier: claim patterns, request-side intents, strict test-runner list, outbound command and tool-name vocabulary, and evidence-shape vetoes (dry runs, zero-test output, PATH rewrites, read-only MCP calls). | ✅ |
| `query_grounding_verifier.py` | Internal | Entity state/data query intent grounding and physical evidence verification (detects business entity queries e.g. orders/tickets/logistics, supports per-entity grounding map matching against tool arguments and outputs, blocks ungrounded hallucination when query tools were omitted or unsearched entities were fabricated, and halts fake success claims when query tools failed). | ✅ |
| `ppt_outline_verifier.py` | Internal | PPT reporting plan outline quality gate — detects PPT/slide-deck delivery and enforces the 4-dimensional rubric (concise titles, explicit takeaway per slide, concrete visual/data anchor, balanced density). | ✅ |
