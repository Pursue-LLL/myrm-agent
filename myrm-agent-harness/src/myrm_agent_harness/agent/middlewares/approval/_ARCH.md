# approval/

## Overview
Tool approval subsystem — Human-in-the-Loop approval flow.

## File & Submodule Index

| File | Role | Description | I/O/P |
|------|------|-------------|-------|
| __init__.py | Package | Tool approval subsystem — Human-in-the-Loop approval flow. | — |
| batch_processor.py | Core | Batch security evaluation — `evaluate_tool_batch`. YOLO auto-approve (DENY always enforced except interactive smart-deny override). Fast-Path read-only MCP. **Pattern allowlist** auto-approve via `allowlist.find_matching_entry(..., command=shell_command, session_id=current_session_id)` when action is ASK; discriminates `ALLOWLIST_SESSION_ALLOW` vs `ALLOWLIST_AUTO_APPROVE`. Emits `SANDBOX_AUTO_BYPASS` audit traces when running in sandbox environments. `is_interactive` kwarg: when True, LLM DENY routes to `pending_approval` (with `smart_denied` extra_ctx) instead of `auto_denied`, allowing user once-override. Marks `extra_ctx["high_risk"]` for ESCALATE threats, Taint conflicts, LLM UNCERTAIN scenarios, socially irreversible actions, protected instruction mutations (`protected_instruction`), and Auto Mode Suspended (`extra_ctx["auto_mode_suspended"]`) to prevent permanent allowlisting. Supports `classify_all_shell_in_auto_mode` for full shell intent review in auto mode. Tools outside an active read-only research lease (`core/security/readonly_research_sandbox`) are denied before the permission engine runs; the lease's refusals, the engine's DENY and the non-interactive security reviews are worded by `denial_diagnostic_bridge`. | ✅ |
| _allow_always.py | Internal | `should_block_allow_always`: the unified backend safety net combining integration-mutation + protected-instruction-mutation + high_risk + smart_denied + financial + socially irreversible + suspended checks; `try_add_to_allowlist`: the shared allowlist write for both approve and edit branches, forwarding `ttl_seconds` for time-bound auto-revoking grants. | ✅ |
| _batch_decisions.py | Internal | Decision application (edit shell re-gate): the inbound half of batch approval; `_interrupt_payload.py` builds the outbound payload. Financial spend actions bind and strictly verify `action_digest` against parameter tampering and auto-inject `idempotency_key` into payment tools (Stripe). Mutable script operands revalidate content SHA-256 against approval snapshot at final boundary to prevent TOCTOU execution drift (CVE-2026-32921). The rejection branch reads the human's reason from `feedback`, stripped first: a blank or whitespace-only value is not a reason and falls back to the built-in `User rejected this action.` line. A decision's `guidance` is a separate channel read for every decision type (approve, edit, reject) and returned to the caller as a trailing `HumanMessage` carrying `additional_kwargs={"approval_guidance": True}`, which the middleware appends after the tool messages so the model can adjust course; a decision that carries only `feedback` contributes nothing here. An approved call first opens the directories it names for that call only (`grant_paths_once`, audited as `PATH_OPENED_ONCE`); the card's folder toggle then remembers them for the session (`DIRECTORY_GRANTED`). An edited call opens nothing. | ✅ |
| _interrupt_payload.py | Internal | `build_interrupt_payload`: the outbound half of batch approval. Smart-denied payloads restrict `allowedDecisions` to approve+reject only and carry `smartDenied`+`reviewerReason` for frontend rendering. High-risk scenarios (ESCALATE, Taint, LLM UNCERTAIN), socially irreversible actions (`sociallyIrreversible`), Auto Mode Suspended (`autoModeSuspended`), protected instruction mutations (`protected_instruction`), and financial transactions emit `hideAllowAlways` in reviewConfig. With a `path_policy`, a file call naming directories outside the allowed zones carries `grantDirectories` (`[{path, writable}]`, planned by `session_access.plan_directory_grants`), which is what the card lists under "also grant folder access"; the grant on resume applies the same plan, whatever language the reason is in. | ✅ |
| _batch_review.py | Internal | LLM-based security review, runtime domain tracking, and skill hook evaluation. | ✅ |
| _cron_policy.py | Internal | `resolve_cron_ask` — how an ASK is settled in a cron run, where nobody can answer it. A declared capability set pre-approves the ask (an undeclared one denies it fail-closed), except integration write mutations, network egress while the session holds SECRET (credential) taint — trusted hosts exempt — and file asks the path-zone check would not allow (outside the job's directories, sensitive or protected files). The taint and path legs are recomputed from the same pure checks the engine uses, so they hold however the ask arose and when the optional LLM reviewer is unavailable. Runs after the allowlist and the reviewer; an explicit reviewer ALLOW is not overridden. Residual by design: non-credential taint (web content to shell) and shell one-liners that read and send in a single command stay pre-approved by the declaration. | ✅ |
| evaluation/ | Core | Judges the tool calls of a model response exactly once, in a graph node of its own ahead of the node that asks a person: `ApprovalEvaluationMiddleware` runs `evaluate_tool_batch` (reviewer model, refusal counters, approval rate limit) and stores the verdicts in a private, checkpointed state key. Resuming an approval card re-runs the asking node from its first line; with the judging done earlier, the reviewer is asked once and a verdict that changes while the card is open cannot overrule the person. See [evaluation/_ARCH.md](evaluation/_ARCH.md). | ✅ |
| refusal/ | Core | How an approval refusal reaches the model: `answered_calls.py` (which calls of a model response an earlier guard already answered, and which calls the AI message keeps once some were approved, edited or refused — a refused call stays in the AI message, answered by an error ToolMessage) `answer.py` (the one constructor of the answer to a refused call, marked with who refused: `policy_denied` / `user_declined` / `approval_timeout`) and `wording.py` (who refused: `DenialCause`; the `[System: ...]` note per cause; escalation past a denial threshold). See [refusal/_ARCH.md](refusal/_ARCH.md). | ✅ |
| denial_diagnostic_bridge.py | Core | Denial diagnostic bridge connecting security auto-review denials to Dots-style 4-way adaptive resolution. `build_auto_review_denial_message(tool_name, reason, hint)` renders the structured message the model reads (reason code, allowed alternatives, the four resolution branches) and opens the diagnostic block with `core.security.model_directed_notes.DIAGNOSTIC_OPEN` and keeps no per-denial state; `infer_denial_reason_code` maps the denial text and the tool name to the reason code. | ✅ |
| guidance_delivery.py | Core | The note a human writes on an approval, delivered to the model after the tool result. A standalone gate the human answered (high-risk DOM action, privileged browser script, batch cost) reads its answer through `core.security.hitl_decision` and stashes the note with `core.context_vars.stash_approval_note`; this hook publishes the call id the tool body is running inside, dispatches the tool, then claims the note for that call and returns `Command(update={"messages": [tool_message, HumanMessage(..., additional_kwargs={"approval_guidance": True})]})`. The note cannot ride the resume payload: an `AIMessage` carrying tool calls must be followed immediately by its `ToolMessage`, so appending there produces a request the provider refuses. Reuses the `approval_guidance` marker the approval middleware already sets. | ✅ |
| intent_ledger.py | Core | User intent ledger preserving task anchors and directives for reasoning-blind approval classification. | ✅ |
| helpers.py | Core | Denial tracking (`record_denial(cause=...)`, `record_rejection` for a person's or the timer's refusal; a `cron:` session key selects the unattended wording), **allow-always four scopes** (permission/tool/exact/pattern via `derive_command_pattern`), time-bound auto-revocation (`ttl_seconds` → `expires_at`), session-scoped in-memory isolation, allowlist persistence. | ✅ |
| middleware.py | Core | `ToolApprovalMiddleware` — the node that puts the pending calls to a person and applies the answers. It reads the verdicts the evaluation node stored (`evaluation/`), builds one batch `interrupt()` payload, and merges the decisions back; nothing before `interrupt()` judges a call, because LangGraph runs this node again from its first line once the person has answered. Auto-denies approval for shadow agents (no UI channel) and for subagents without a task id. Every refusal (policy, user, timeout, cron fail-closed, rate limit) leaves the call in the AI message and answers it with an error ToolMessage, so the model reads the reason; the hook returns only the ToolMessages, or the AI message with the approved calls in their approved form after an interrupt. Calls an earlier guard already answered are not put to the user. Fires APPROVAL_CORRECTION hook for user edits only (rejections stay in the audit trail); no built-in handler is registered, the event is an extension point for user-defined hooks. `aafter_model` drops the previous call's once-only directories (`drop_once_grants`) before it judges the next response. | ✅ |
| rate_limiter.py | Core | Approval rate limiter. Independent from core approval logic for easy testing and configuration. | ✅ |
| scheduler.py | Core | HITL timeout scheduler — auto-resumes agents when approval or Web clarification requests expire. Approval uses the global decision format and marks the resume value `timed_out` so the model is told nobody answered; clarification uses `resume_value_override` (empty dict → no_answer). Idempotent resolution per key: the timer claims the key itself and never cancels its own task, while the manual path's `resolve_if_first` claims and cancels the timer, so the loser of the race is a no-op and a suspending timeout callback is not aborted. `reopen(key)` re-arms resolution when a resumed run stopped at a new interrupt that carries no timer. | ✅ |
| tiered_risk_evaluator.py | Core | Three-tier operation risk adaptive evaluator (READ / WRITE / HIGH_RISK) with dynamic brake and NEED_CONFIRMATION token generation. | ✅ |
