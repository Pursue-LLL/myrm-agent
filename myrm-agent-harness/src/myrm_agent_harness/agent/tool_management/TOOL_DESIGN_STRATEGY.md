## 一、设计原则

### 1.1 核心设计哲学

**减少可用工具数量 = 降低认知负载 = 提高决策准确性**

证据来源: [action_space.py](action_space.py), [tool_layers.py](tool_layers.py)

大语言模型在面对工具选择时，与人类面对选择困难症类似：
- 工具越多 → 动作空间越大 → 决策难度指数增长
- 工具越少 → 选项精简 → 准确率提升（零幻觉调用）
- CI 架构硬门禁保护：通过 `TestPromptTokenBudgetGate` 严格锁定 Turn-1 默认工具集（CORE+HIGH_PRIORITY 13个工具）总预算上限 $\le 6,500$ tokens，Full 模式系统提示词 $\le 2,000$ tokens，Lean 模式 $\le 1,200$ tokens 且压缩比 $\le 0.70$。

### 1.2 框架能力 vs 业务扩展（边界红线）

**术语**：对外 **「工具」= LLM 工具**（`ToolRegistry` 中的 `BaseTool`，CORE/HIGH_PRIORITY/EXTENDED/EXTERNAL）。`toolkits/` 能力包、中间件、Skill 文档、编排状态机等**非 LLM 能力**禁止称作工具。见 `tool_catalog.py` · `TOOL_MANAGEMENT_SYSTEM.md`。

**Harness 是 Agent 框架，不是业务集成大杂烩。** 混淆层级会导致 toolkits 膨胀、定位模糊、维护成本失控。

| 层级 | 路径 | 放什么 | 禁止放什么 |
|------|------|--------|------------|
| 框架通用原语 | `toolkits/` | 与具体 SaaS 无关的可复用能力 | Google Calendar API 封装、HF Inference 专用工具 |
| 框架绑定元工具 | `agent/meta_tools/` | 需要会话/Planner/HITL 的工具包装 | 某一家 Notion/Linear 的硬编码 REST |
| 业务工作流 | `assets/prebuilt_skills/` | SKILL.md + contract + allowed-tools | 新的 `@tool()` 注册 |
| 三方集成（产品） | `app/integrations/`、MCP、channels | OAuth、渠道 SDK | 搬进 harness toolkits |
| 产品 REST | `app/api/` + `services/` | HTTP 域模型 | 默认 GeneralAgent 工具 |

**禁止模式**：单一厂商 SaaS 不得作为 harness toolkit；无 OAuth 产品化的 prebuilt skill 不得上架。

**正确替代**：
- 日历类 → 用户 MCP / 未来 `integrations/oauth` + skill；看板用现有 `kanban_*` 工具
- RSS/博客监控 → `blog-monitoring` skill + `web_search_tool` + `web_fetch_tool`
- HF 推理 → `ImageGenerationTools`（LLM 适配层）或用户 MCP

新增 harness 工具前自问：**去掉 Myrm 品牌后，别的 Agent 框架是否也会需要这个模块？** 若否 → skill 或 MCP。

**关键指标: ASCS (Action Space Complexity Score)**  
科学量化工具集的认知负担，指导用户优化工具配置。

## 二、工具层级体系 (Tool Layer System)

### 2.1 四层架构设计

证据来源: [tool_layers.py:30-40](tool_layers.py)

```python
class ToolLayer(IntEnum):
    CORE = 1           # 核心层：基线工具，始终存在，不可关闭（保证终极前缀缓存）
    HIGH_PRIORITY = 2  # 高优层：标配工具，默认全局挂载（Default-ON），用户可配置关闭（搜索/记忆/技能选择）
    EXTENDED = 3       # 扩展层：harness 可选高级能力，默认关闭，按需挂载
    EXTERNAL = 4       # 外部业务层：框架外集成（server vendor / MCP direct / OpenAPI / 动态工具）
```

### 2.2 分层设计目标

**目标**: 最大化 Prompt Cache 命中率

**层级说明**:

#### 2.2.1 CORE 层 (Layer 1) - 核心层

- **特征**: 通用 Agent 基线，Turn1 eager；无产品级工具开关（Fast 模式由 converter 关闭 file/bash；`web_fetch_tool` 另受 Agent Security 能力白名单约束，见下）
- **工具数量**: **8**（`tool_layers.py:64-71`）
- **Token 消耗**: 描述合计 2,599 tokens（8 工具，macOS arm64 实测；见 `DEFAULT_AGENT_TOKEN_INVENTORY.md` §二）

| 工具名 | 常驻理由 |
|--------|----------|
| web_fetch_tool | 搜索流程必经的「读网页」一步，Fast 面没有替代路径；不依赖搜索账号、体量小；延迟它净亏且触碰缓存底线（依据见下） |
| bash_code_execute_tool, bash_process_tool, file_read/write/edit_tool, glob_tool, grep_tool | 通用工作助手基线（非 IDE 专用；file/shell 为沙箱内日常操作；bash_process 与 bash_code_execute 同挂） |

**设计原则**: 仅包含 Agent 基线工具；详细 token 逐项见 `DEFAULT_AGENT_TOKEN_INVENTORY.md` §二。

##### web_fetch 常驻依据（为何首轮 eager、不延迟）

「是否引入工具目录机制」与「引入后谁该进目录」是两个问题：前者仍在评估（§10.2），后者按三问判断（归纳自 Anthropic Tool Search 与 Claude Code SDK tool-search 官方文档，非官方原话；数据口径 2026-11-04）：

| 三问 | 判据 | Myrm 现状 | 判定 |
|------|------|-----------|------|
| 目录够大吗 | Anthropic：工具 ≥10 个、定义 >10K token、选择准确率下降、聚合 200+ MCP 工具、工具库持续增长，任一成立即可考虑；Claude Code 的 auto 模式在可延迟定义达到上下文窗口 10% 时才启用 | 默认 profile 13 个工具；含 schema 的 Turn-1 工具块：规划口径 10,214（`scripts/measure_tool_schema_tokens.py`，含每工具 65 的 wrapper 估算常数），实际序列化载荷口径约 8.7K（8,693），落在 10K 线两侧；约占 200K 窗口的 4.3%–5.1%（128K 窗口 6.8%–8.0%），未到 10%；web_fetch 自身：规划口径 274，实际序列化载荷 190–474（英文 / 中文 × 有无检索服务：英文无检索 190、中文无检索 195、英文带检索 439、中文带检索 474；默认英文无检索 190；路由提示只在浏览器工具一侧，不计入 web_fetch），约占 200K 窗口的 0.10%–0.24% | 满足可考虑条件 |
| 是头部还是长尾 | Anthropic：最常用的 3–5 个工具保持非延迟；Hermes 默认延迟清单（`hermes_cli/config_defaults.py`）刻意收录冷门、事件触发型内置工具，web 工具不在其中 | 头部：Fast 搜索的深度流程是 web_search → web_fetch → 答案自审，且 Fast 面不挂 shell 与浏览器（`services/agent/params/converter.py`）；完成守卫把它计为外部证据（`external_evidence.py` 的 `_EXTERNAL_EVIDENCE_TOOLS`）；131 个预置技能中 13 个在 allowed-tools 声明它；`file_read_tool`、`answer_user_tool` 的描述把读网页路由给它 | 头部，不应延迟 |
| 发现机制保缓存、成本摊得薄吗 | Anthropic 原生延迟以 tool_reference 内联追加、前缀不动；tools 位于缓存层级最前，改动会使其后全部缓存失效。Claude Code：不支持的模型与部署回退为首轮全量加载；每次发现多一轮往返，压缩后需重新发现 | 多供应商、无原生机制；框架 11.1 禁止追加非 Turn1 schema（§11.2、`PROMPT_CACHE_PRACTICE.md` §2.1.1）；自建三桥的抓包体量 OpenClaw 525、Hermes 606 token，均大于 web_fetch 本身，只有摊给大量冷门工具才赚 | 不成立，延迟净亏 |

补充依据：

- **CORE 而非 HIGH_PRIORITY 的分界**：web_fetch 不依赖搜索账号（`ai_agents/general_agent/tool_setup/` 的 web_fetch 分支独立于 `search_service_cfg`），`web_search_tool` 需要账号且用户可关。
- **暴露面不因常驻改变**：是否挂载由 Agent Security 能力白名单决定（`services/agent/resolve_enable_web_fetch.py`；白名单为空表示不限制，非空且不含 `net_fetch` 时不挂载；Web、Cron、Eval、Channel、Voice、Goal、Kanban 入口统一调用）。`net_fetch` 为只读、基线放行，并带逐跳 SSRF 钉扎（`toolkits/web_fetch/fetchers/target_guard.py`）；bash 属 `code_interpreter` 默认需确认，其命令内 URL 预检只防外泄、放行私网（`_security/preflight_checks/url_guard.py` 的 `check_command_url_exfiltration`），不能等价替代。
- **非英文查询**：词法检索式发现步骤对非英文查询召回差（§11.3），不宜把头部工具放在它后面。

**反转条件**（任一出现即重新评审）：

1. 含 schema 的默认 Turn-1 工具块持续高于 10K 且已无可瘦身项（规划口径下当前仍有 `bash_process_tool` 参数 schema 603、`memory_save_tool` 描述 578 等）。
2. 遥测显示某类会话的 web_fetch 占比很低：先做策略级关闭（能力白名单不含 `net_fetch`），而不是工具级延迟（该遥测尚未建立）。
3. 评测显示默认工具集的工具选择错误率上升。
4. 目标模型普遍支持原生的「延迟且保缓存」机制。
5. §10.2 要求的 >11.25K 真实服务器基准完成，且评审结论改变。

#### 2.2.2 HIGH_PRIORITY 层 (Layer 2) - 高优层

- **特征**: 默认开启（Default-ON），GUI/配置可关（User-Togglable）；组内严格按稳定 Rank 排序：搜索工具 (Rank 0) -> 记忆工具组 (Rank 10~12) -> 技能选择工具 (Rank 20)
- **工具数量**: 注册 **5** 个（`web_search_tool` + memory×3 + `skill_select_tool`）
- **默认 Turn1 bind**: web_search + memory×3 + skill_select（见 `DEFAULT_AGENT_TOKEN_INVENTORY.md` §三）
- **CI 门禁**: `validate_layer_product_consistency()` — 校验层级与默认开启策略的一致性

| 工具名 | 组内排序 | 加载条件 |
|--------|---------|----------|
| web_search_tool | Rank 0 | GUI 可关（默认开，`enabled_builtin_tools: web_search`） |
| memory_manage_tool | Rank 10 | enable_memory + `enabled_builtin_tools: memory`（默认开） |
| memory_search_tool | Rank 11 | enable_memory + `enabled_builtin_tools: memory`（默认开） |
| memory_save_tool | Rank 12 | enable_memory + `enabled_builtin_tools: memory`（默认开） |
| skill_select_tool | Rank 20 | skill_backend present（默认开） |

**不在 HIGH_PRIORITY 的 opt-in 工具**（如 `todo_write` / `planning`、`ask_question_tool` / `structured_clarify`）登记在 EXTENDED；后者虽默认开但因 HITL/cache 策略列入 `EXTENDED_DEFAULT_ON_TOOL_EXCEPTIONS`。

#### 2.2.4 EXTERNAL 层 (Layer 4) - 外部业务层

- **特征**: 框架外集成 — server vendor、MCP direct、OpenAPI、未登记动态工具
- **缓存**: 整段位于 harness 三层之后；MCP 增删不影响 CORE/HIGH_PRIORITY/EXTENDED 前缀
- **工具数量**: 登记 **5** EXTERNAL（server bootstrap；见 TOOL_COUNT 块）
- **默认**: 未在 `_TOOL_LAYERS` 登记的工具名默认 EXTERNAL + WARNING

| 工具名 | 加载条件 |
|--------|----------|
| image_tool, video_tool, tts_generate, artifact_publish, channel_notify_tool | server `_tool_layer_bootstrap.py` + 对应 skill/凭证/notify 配置 |

### 2.3 排序规则

证据来源: [tool_layers.py](tool_layers.py) · [registry.py](registry.py)

**排序算法**: CORE → HIGH_PRIORITY → EXTENDED → EXTERNAL；HIGH_PRIORITY 组内搜索优先，记忆紧随其后，技能选择承接；同层按名称字母序

**缓存原理**: Prompt Cache 是前缀匹配，CORE 工具放最前面可保证 harness 前缀稳定

**实际效果**: 
- harness 固定部分可被缓存（仅收 5-10% 费用）
- EXTERNAL 变化不破坏 harness 前缀

**诚实 ROI（按部署路径）**:

| 路径 | Turn1 是否 bind MCP/EXTERNAL | 多轮 cache 收益 | 典型用户 |
|------|------------------------------|----------------|---------|
| 默认 harness 工具 only | 否 | ≈0（无 EXTERNAL 段变化） | 大多数短对话 |
| GUI + direct MCP Turn1 | 是 | **中–高**（Turn2+ harness 前缀稳定） | 绑 GitHub 等 MCP 多轮助手 |
| PTC / Dynamic Workflow MCP | 否（Python 编排，非 LLM schema） | ≈0 | dev gate、chrome E2E |

### 2.4 层分配铁律（CI 强制执行）

证据来源: [tool_catalog.py](tool_catalog.py) `validate_layer_product_consistency()` · [scripts/validate_tool_registry.py](../../../../scripts/validate_tool_registry.py)

| 层 | 准入条件 | 反例（CI 失败） |
|----|----------|----------------|
| **CORE** | Agent baseline，无 GUI 开关，固定 8 工具 | 把 `browser_*` 登记进 CORE |
| **HIGH_PRIORITY** | product_id ∈ `DEFAULT_ENABLED_BUILTIN_TOOLS` 且非 HITL 重工具 | `todo_write`（product=`planning`，opt-in） |
| **EXTENDED** | opt-in / 多工具簇 / HITL / harness 可选能力 | 把 `web_search_tool` 登记进 EXTENDED 且 product 默认开 |
| **EXTERNAL** | server vendor / MCP / OpenAPI / 未登记动态工具 | 把 harness 静态工具登记进 EXTERNAL |

**唯一例外表** `EXTENDED_DEFAULT_ON_TOOL_EXCEPTIONS`：`ask_question_tool`（默认开 HITL/cache）。

新增 LLM 工具时必须同步：`register_tool_layer()` + product_id 映射 + 跑 `validate_tool_registry.py`（含 pre-commit `--incremental` 静态层门禁）。

### 2.5 MCP 路由（当前：Direct FC / MCP PTC）

**Harness 层当前对 MCP/OpenAPI 溢出有两种结局；是否增加新的结局仍在评估（见 §10.2）** — 证据：`agent/_factory/mcp_routing.py` · CI：`tests/architecture/test_mcp_routing_two_outcomes.py` · PTC 家族 SSOT：`toolkits/code_execution/EXECUTION_SYSTEM.md` § PTC 家族

| 结局 | 条件 | LLM 如何调用 |
|------|------|-------------|
| **Direct FC** | 单服 schema ≤ `compute_direct_threshold()`（`FALLBACK_PTC_OVERHEAD_TOKENS` 450 × `PTC_OVERHEAD_MULTIPLIER` 25 = **11,250 tok**）且 aggregate direct ≤ `AGGREGATE_DIRECT_TOKEN_BUDGET`（**15,000 tok**） | Turn1 完整 JSON Schema，`tool_call` |
| **MCP PTC** | 单服超大 **或** aggregate 超标（最大服优先 demote） | `skill_select`（L2 携带工具签名）→ `bash_code_execute` Python；`file_read(/mcp/...)` 仅在签名被缩写或需要返回结构时按需读取 |
| **OpenAPI direct** | 选中 endpoint 生成 schema ≤ `AGGREGATE_DIRECT_TOKEN_BUDGET`（**15,000 tok**） | Turn1 direct tools |
| **OpenAPI 拒绝** | enabled 但 0 tools 加载失败 | `ConfigIncompleteError`（`openapi_load_failed`）；检查 spec/认证/endpoint |
| **OpenAPI 拒绝** | schema > `AGGREGATE_DIRECT_TOKEN_BUDGET`（非 `direct_fc`） | `ConfigIncompleteError`（`openapi_direct_budget_exceeded`）；Agent 设置减少 endpoint |

**不采用的形态及其问题（评估输入）**：

1. **catalog_invoke / capability_invoke_tool** — RUNTIME 池 + Turn1 proxy gateway，schema 藏在 catalog 一行摘要里，模型盲调；准确性与 PTC 重叠且更差。
2. **多档 aggregate 阈值**（11,250 单服 + 15,000 聚合之外再加档位）— 会制造灰色地带，维护与认知成本上升；当前只有这两个数。

**评估新的集成或调用形态时需回答**：

- 现有 **Direct** 或 **MCP PTC** 能否满足？若能，增量在哪里。
- 是否牺牲参数 schema 可见性（盲调）？若是，准确性代价要实测。
- 相对现状的收益是否有实测基准（见 §10.2）。

**Profile 兼容**：`mcp_surface_mode=catalog_invoke` 解析为 `auto` 并打 WARNING（`mcp_surface.py`）。

## 三、核心/外围技能机制 (Core/Peripheral Skills)

### 3.1 设计目标

**差异化认知负载管理**

证据来源: [myrm-agent-server/app/api/agents/agent.py:644-651](myrm-agent-server/app/api/agents/agent.py)

### 3.2 核心技能 (Core Skills)
- **特征**: 常驻在模型 Prompt 中
- **认知负载**: 100%
- **适用场景**: 高频使用的技能

### 3.3 外围技能 (Peripheral Skills)
- **特征**: 按需加载，只在用户明确说需要时才注入
- **认知负载**: 50%（常驻负载减半）
- **适用场景**: 低频使用的技能

### 3.4 目录分配的真实规则（以 `catalog_display.py` 为准）

上面的「核心/外围」是**设计意图**，实际分配由 `agent/skills/runtime/catalog_display.py::resolve_catalog_display_skills()` 决定，规则与 §3.1-3.3 的描述并不完全等价，改动前必须读这段：

| 条件 | 行为 |
|---|---|
| 提供非空 `skill_configs` | 候选 = 显式 `is_core=true` 的技能，加上未显式配置且 `always=True` 的技能；显式 `is_core=false` 永远优先于 `always` |
| 无 `skill_configs`（`None` 与 `{}` 是同一种状态） | 全部可见技能都是候选 |
| 排序与预算 | `always` 在前，其后按名字，按 token 预算选择完整条目 |
| 候选总 token > `L1_CATALOG_MAX_TOKENS` (2,000) | 预算满即停止；未展示技能计入 `hidden_count`，名字列在 `<hidden_skill_names>`；被预算挤掉的候选另计 `overflow_count` |

**不按个数截断**：L1 选择由 `estimate_skill_entry_tokens` + `L1_CATALOG_MAX_TOKENS` 决定；
完整 `name + description` 放不下时不放半截描述；没有完整条目的技能以 `<hidden_skill_names>` 一行列出名字，该行有独立上限 `L1_HIDDEN_NAMES_MAX_TOKENS`（1,500，约 260 个名字），超出时写 `and N more not listed`。

**预算外技能如何到达**：
- 名字在 `<hidden_skill_names>` 里，或用户明确点名 → 直接 `skill_select_tool`；
- 只知道能力、不知道名字 → `skill_search_tool` → `skill_select_tool`；
- `skill_select_tool` 白名单、`skill_search_tool` 索引都取自全量 `filtered_skills`。

**不变量**：`hidden_count` 只表示没有完整条目，不表示不可选。评估目录改动时必须同时看
`filtered_skills`（供给侧）和 `display_skills + hidden_skills`（接收侧）。

**实测依据**：真实模型会话对照（两个小模型，全部外围技能）显示，加上名字清单后每个会话的检索次数显著减少，通过率没有显著差别；代价是首次提示多出名字行的 token（130 个技能约 780）。

### 4.3 准确度计算

```python
max_safe_score = 1500
noise_level = min(100, round((total_score / max_safe_score) * 100))
```

|------|-----:|-------:|------|
| 绿色 ✨ | noise_level ≤ 50 | > 50% | "极佳决策准确率：动作空间极度精简，Agent 能发挥最高级别的零幻觉调用" |

### 8.1 强制路由到 EXTENDED 层

证据来源: [tool_layers.py:102-116](tool_layers.py)

**设计原则**: 保护大模型 Prompt Prefix Cache

```python
def get_tool_layer(tool_name: str) -> ToolLayer:
    """获取工具层级
    
    [核心架构约束]:保护大模型 Prompt Prefix Cache
    所有动态挂载的外部工具(特别是 MCP 提供的工具,如 github_search 等)
    必须强制路由到 EXTENDED 层级(Prompt尾部).

        工具层级,未注册的工具(含所有 MCP 工具)默认为 EXTENDED(放在最后)
    """
    return _TOOL_LAYERS.get(tool_name, ToolLayer.EXTENDED)
```

原因: 外部服务往往包含多个具备极深嵌套对象的工具，保守估算值确保准确性

### 10.2 竞品 MCP 懒加载：对照与待评估项（AI / Roadmap 必读）

**当前事实**：Myrm 没有原生的工具级延迟机制，现存只有技能级 `skill_search_tool`（且仅在 `hidden_skill_count > 0` 时挂载）。对照：

- **Hermes-Agent** 有完整三桥 `tool_search` / `tool_describe` / `tool_call`，MCP 与插件工具默认延迟；
- **OpenClaw** 有 `tool-search` 与 `tool-catalog`，默认开启；
- **deepseek-harness** 有 `deferLoading` 字段进入 system prompt 组装；
- **Anthropic API** 官方提供 `defer_loading: true` + regex/BM25 搜索工具。

因此准确表述是：**我们目前只有「技能级检索 + PTC」，没有「工具级延迟加载」**。

**评估应基于下列事实与理由，而不是预设结论**：

| 不采用或已评估的形态 | 评估结论与理由 |
| --- | --- |
| `catalog_invoke` / `capability_invoke` / RUNTIME proxy gateway | 这些是**盲调**（只给工具名 + `arguments: dict`，不把真实 schema 交给模型），准确性劣于 PTC。`invoke_deferred_tool`（入参就是 `arguments: dict`）正属此类，所以不提供它**技术方向是对的** |
| 双 aggregate 阈值 | 制造灰色地带，与本节无关 |
| 新增调用范式 | 与 PTC 重叠的部分没有增量；是否有增量需要实测 |

| 应当做（新） | 说明 |
| --- | --- |
| **「搜索 → 载入真实 schema → 直调」** | 与盲调的区别是 **schema 真的进了上下文**。它与现有 Direct FC 的差别只是「schema 何时进入」，不是「有没有 schema」 |
| **先补 >11.25K 真实服务器基准** | `PTC_OVERHEAD_MULTIPLIER=25` 的 11.25K 是**理论 crossover × 0.4**（`agent/_factory/mcp_routing.py:48-57`），不是实测；Anthropic 公开门槛是 >10K。没有实测就不该动架构 |

**内置记忆工具延迟的实测（2026-11-06，英文，MiniMax-M3.1-Flash-Preview，温度 0.5）**：把 `memory_save_tool`、`memory_manage_tool` 换成一个 86 token 的 `load_tool`（枚举这两个名字，载入后才把真实定义加进请求），Turn 1 工具块从 1,508 降到 337，净省 1,171 token/轮。19 个场景各 5 次，对照同一文本的常驻版（各 10 次）：需要写入的场景成功率 67/75（89%）对 146/150（97%），单侧 Fisher p=0.016；全部场景 87/95 对 186/190，低 6.3 个点（p=0.017）。差距几乎全在「用户夸召回准 → `rate`」一个场景（1/5 对 10/10），去掉它后 86/90 对 176/180（p=0.26）。每个真要用工具的场景多一轮往返（平均 2.32 步对 1.52 步）。按各步请求的原始 prompt token 累计（未折算缓存），这类场景每条对话为 3,188 对 3,403，只少 215（6.3%），不是 1,171 乘以步数：载入后的定义和多出的一轮往返都要付。缓存没有测：载入使 tools 变化，其后的 System 与消息前缀缓存失效（`PROMPT_CACHE_PRACTICE.md` §2.1），所以 1,171 只在缓存未命中的轮次才是真节省；把载入提示写详细会缩小 `rate` 的差距，但要吃掉这笔节省（未测）。样本小、单模型、合成最小提示：只能说没有证据支持延迟这两个工具，不构成本节的结论。

**该不该做**：评估中，尚无结论。需要一次架构评审，对照实测基准明确「恢复工具级延迟」或其他新增结局相对 §2.5 现状的收益。不得再用「已领先」作为不做的理由。

SSOT：`FRAMEWORK_DESIGN_PRINCIPLES.md` §7 · `TOOL_DESIGN_STRATEGY.md` §2.5 · CI `test_mcp_routing_two_outcomes.py`
