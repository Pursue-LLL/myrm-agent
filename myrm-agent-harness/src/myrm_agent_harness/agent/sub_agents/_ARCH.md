# sub_agents/

## Overview
Sub-agent subsystem — lifecycle management and configuration loading.

Detailed design: [SUB_AGENT_SYSTEM.md](SUB_AGENT_SYSTEM.md)

## Child Tool Isolation

A child holds the parent's own tool objects, so a tool is stripped by what it does to the parent, not by who calls it:

- Bound to state only the parent can own (memory manager, schedule, plan file, goal, kanban board): blocked for every child by `DelegationCapabilityManifest.leaf_blocked_tools`; `SubagentConfig.tools` cannot restore it.
- Valid for a child but outside a read-only child's contract (workspace writes, external agent sessions, knowledge-store writes, side-effect MCP tools): stripped for read-only children in `builder.filter_tools`.
- Bound to a live session of the parent run (`browser_*`): kept, and a child's call acts on the parent's browser session; children running at the same time share it.

The tool list is only one door. `SkillAgent` also mounts tools itself whatever `tools=` says: the default meta tools (file, search, shell and `bash_process_tool`), `todo_write` when planning is on or the workspace already holds todos, and `skill_manage_tool` / the wiki tools when their backends are configured. What those can do is decided where they run:

- File and shell executors enforce the child's capability handle. `delegate_task` and the verifier round bind one; for every other read-only spawn (dynamic workflow) `SubagentManager.spawn_child` binds the READ-only floor.
- `bash_process_tool` jobs are scoped to the session a child shares with its parent, so every action except `list` / `output` / `wait` checks the EXECUTE capability itself.
- A delegated child never resumes the workspace's todos (`SkillAgent` checks `get_is_subagent()`, which the executor sets before the child runs), so a workspace that already holds todos never makes it mount `todo_write`; a child's own list lives under its task id, apart from the parent's.

`tests/agent/sub_agents/test_child_tool_isolation_contract.py` classifies every side-effecting tool of the safety table with the mechanism that decides it; a new tool fails it until it is classified.

## Child Run Isolation

A child runs inline in its parent's delegating tool call, so it shares the context the parent's per-run guards live in, and every run starts by resetting the guards it finds there in place. `executor_attempt_mixin` therefore runs each child attempt inside `agent/_internals/_agent_helpers.child_run_scope(task_id)`: the child gets its own LoopGuard (kept in the session registry under its task id so an approval resume finds it again; `SubagentManager` drops it once the task is terminal, not while it waits for approval), ToolTurnBudgetGuard, ContextBudgetGuard, terminal-error registry and completion-guard turn state (refusal budget, forced-finish latch, evidence ledger, disclosure: `completion_guard/state.isolated_run_state` binds a temporary turn id so the child's opening reset cannot reach the parent's entry, and drops whatever the child left under its own id), and the parent's come back untouched. Without it a delegation silently emptied the parent's tool-call history, and the completion guard stopped asking a parent that wrote code, delegated and finished to verify it, or gave a parent that kept delegating a fresh refusal budget each time.

A guard that resets in place needs an isolated counterpart in `isolated_run_guards` (the guard-isolation half that `child_run_scope` and `ephemeral_run_scope` share); guards that rebind on reset (taint, privacy, audit, denial, replan, plan-confirm) do not, and the executor still reads the child's taint tracker after the run to propagate labels to the parent.

`tests/agent/sub_agents/test_child_run_scope.py` pins the scope; `test_delegation_keeps_completion_guard.py` runs a real parent through the real executor attempt.
